# 74. HITL 的触发条件设计

Day 73 讲了 HITL 的三种介入模式。本节讨论**何时触发 HITL**：**常见触发条件**（高风险动作前、置信度低、失败/异常、业务规则、定时复核）、**按场景选择触发点**（审批型/修正型/接管型分别适合在什么时机触发），以及**触发频率与体验**的权衡（避免过度打断与漏触发）。

## 一、常见触发条件：高风险动作前、置信度低、失败/异常、业务规则、定时复核

### 1. 高风险动作前（多用于审批型）

- **含义**：Agent 即将执行“一旦执行则影响大或不可逆”的动作（如发邮件、支付、删除、审批通过）时，**先触发 HITL**，等人批准后再执行。
- **实现**：为工具或动作打标（如 `requires_approval: true`），或在执行前根据“工具名 + 参数”判断是否属于高风险列表；若属于则暂停并进入审批流程。

### 2. 置信度低（可用于审批或修正）

- **含义**：模型对当前决策**不确定**（如输出中带“可能”“不确定”，或置信度分数低于阈值）时，触发 HITL，由人确认或修正。
- **实现**：若使用带置信度的接口，可设阈值；或对模型输出做简单规则检测（如包含“不确定”等词），再触发人工确认或修正流程。

### 3. 失败/异常（多用于修正或接管）

- **含义**：某步执行**失败**（工具报错、超时、业务校验不通过）或出现**异常结果**（如格式错误、与预期不符）时，触发 HITL：由人修正结果后重试，或直接接管。
- **实现**：与 Week 9 反思结合：当反思输出 `stop_type=human_required` 或“需人工修正”时，进入修正型或接管型 HITL；也可在工具返回错误时直接触发。

### 4. 业务规则（金额/权限等）（多用于审批型）

- **含义**：满足某些**业务规则**时强制 HITL，例如：金额超过 N 元需审批、涉及某类权限需二次确认、或跨部门操作需会签。
- **实现**：在执行前或执行后根据“参数 + 业务规则”判断（如 `amount > 10000`、`action in SENSITIVE_ACTIONS`），满足则触发审批或复核。

### 5. 定时复核（可选）

- **含义**：对**已自动执行**的一批操作，按时间或数量做**定期人工抽检或复核**，发现问题时走修正或接管。属于“事后 HITL”，可与事中 HITL 并存。
- **实现**：异步任务或队列，定期将“待复核”记录推给人，人复核后可将结果写回（如标记通过、或触发修正流程）。

### 6. 小结表

| 触发条件         | 典型用途  | 说明                         |
| ---------------- | --------- | ---------------------------- |
| **高风险动作前** | 审批型    | 执行前暂停，等人批准         |
| **置信度低**     | 审批/修正 | 模型不确定时让人确认或修正   |
| **失败/异常**    | 修正/接管 | 执行失败或结果异常时让人介入 |
| **业务规则**     | 审批型    | 金额、权限等满足条件即触发   |
| **定时复核**     | 抽检/修正 | 对已执行操作做事后复核       |

## 二、按场景选择触发点：审批型多在执行前，修正型多在结果异常时，接管型多在连续失败或用户请求时

### 1. 审批型（Approval）

- **最佳触发点**：**执行前**。在 Agent 决定调用某工具且该工具被标记为“需审批”时，不执行，先进入审批流程；人通过后再执行。
- 若在执行后才审批，则“执行”已发生，审批只能起到事后补救作用，与审批型设计初衷不符。

### 2. 修正型（Correction）

- **最佳触发点**：**执行后、结果可用时**。例如某步工具已返回，但校验发现结果异常或不符合预期；或模型生成了回复，但需要人改一版再发出。此时触发修正型 HITL，人修改结果或输入后写回，Agent 继续。

### 3. 接管型（Takeover）

- **最佳触发点**：**异常或用户主动时**。例如：反思输出“需人工介入”、连续失败达到上限、或用户明确说“转人工”“要人工处理”。此时暂停 Agent 自动执行，把当前状态与上下文给人，由人接管后续操作。

### 4. 小结

| 模式           | 推荐触发点                 | 说明                       |
| -------------- | -------------------------- | -------------------------- |
| **Approval**   | 执行前                     | 先审批再执行，避免误执行   |
| **Correction** | 执行后、结果异常时         | 有结果可修正，再继续或重试 |
| **Takeover**   | 连续失败/用户请求/规则判定 | 停止自动执行，交给人完成   |

## 三、触发频率与体验：避免过度打断与漏触发之间的权衡

### 1. 过度打断

- **现象**：触发过于频繁，用户或运营反复被要求“点一下”“确认一下”，体验差，且可能对 HITL 麻木，随便点通过。
- **缓解**：提高触发门槛（如仅真正高风险才审批）；合并审批（多步合并为一次审批）；或根据用户/场景做差异化（如高信任用户减少审批次数）。

### 2. 漏触发

- **现象**：本应触发 HITL 的场景没有触发，导致误执行或无法兜底，合规与责任风险大。
- **缓解**：对“必须人参与”的动作用**白名单**强制触发（如所有支付类、删除类必审批）；对失败与异常设**兜底规则**（如连续失败 N 次必转接管）。

### 3. 权衡建议

- **合规与责任优先**：凡规定必须人参与的，宁可多触发，不要漏触发。
- **体验优化**：在保证合规的前提下，通过规则细化、用户分级、界面简化减少无效打断；并做好“为何需要你确认”的说明，提升接受度。
