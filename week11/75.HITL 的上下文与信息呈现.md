# 75. HITL 的上下文与信息呈现

Day 74 讲了 HITL 的触发条件设计。本节讨论**人介入时系统应呈现什么**：**人类介入时必须看到的信息**（当前意图、即将执行的动作/参数、相关上下文与风险提示），以及**错误示例与正确示例**（信息过载/过少、缺少决策依据 vs 简洁可操作的摘要与关键字段高亮）。

## 一、人类介入时必须看到的信息：当前意图、即将执行的动作/参数、相关上下文与风险提示

### 1. 当前意图

- **含义**：用户或业务**想要达成什么**（如“帮用户查订单并回复”），以及当前这一步在整体流程中的**角色**（如“正在执行：查询订单”）。
- **作用**：让人快速理解“为什么会有这一步”“若批准/拒绝会怎样”，避免在信息真空下做决定。

### 2. 即将执行的动作/参数

- **含义**：若为**审批型**，需明确展示**将要执行的具体动作**（如调用的工具名、API）以及**参数**（如订单号、金额、收件人）。若为**修正型**，需展示**当前结果或输出**供人修改。
- **作用**：人需要根据“具体做什么、参数是什么”来决定通过/拒绝/修改，或直接修正内容；缺少动作与参数则无法做出有效决策。

### 3. 相关上下文与风险提示

- **相关上下文**：与当前决策相关的**最少必要信息**，例如：用户原始请求、前一步的结果（若影响本步）、业务规则摘要（如“金额超 1 万需审批”）。不必塞入整段对话或全量日志，以免信息过载。
- **风险提示**：若本步涉及**高风险**（如支付、删除、对外发送），应明确标出（如“高风险：将向外部发送邮件”“金额：¥10,000”），便于人重点判断。

### 4. 小结表

| 信息类型       | 内容概要                             | 用途                     |
| -------------- | ------------------------------------ | ------------------------ |
| **当前意图**   | 用户/业务目标、本步在流程中的角色    | 理解“为何要决策”         |
| **动作/参数**  | 将要执行的动作与参数，或待修正的结果 | 做出通过/拒绝/修改/修正  |
| **相关上下文** | 最少必要的请求、前序结果、规则摘要   | 辅助判断                 |
| **风险提示**   | 高风险动作、金额、敏感操作等         | 引起注意、合规与责任意识 |

## 二、错误示例与正确示例：信息过载/过少、缺少决策依据；简洁可操作的摘要与关键字段高亮

### 1. 错误示例

#### 信息过载

- **表现**：把整段对话历史、全部 tool_calls、原始 API 响应都堆给人，没有摘要与重点。
- **问题**：人难以在短时间内找到“要批准的是什么、参数是什么”，决策效率低，也容易漏看关键信息。

#### 信息过少

- **表现**：只写“请确认是否执行”，不写“执行什么、参数是什么、有什么风险”。
- **问题**：人无法做出有依据的决策，只能盲目点通过或拒绝，责任与合规都无法保障。

#### 缺少决策依据

- **表现**：没有“当前意图”“风险提示”，或动作/参数被折叠、不显眼。
- **问题**：人不知道“若通过会怎样、若拒绝会怎样”，无法与业务规则或合规要求对照。

### 2. 正确示例

#### 简洁可操作的摘要

- **审批型**：用一两句话说明“当前要执行什么”（如“将调用「发送邮件」工具”），下面用**结构化字段**列出：收件人、主题、正文摘要、是否带附件。再附一句“用户原始请求：……”（可折叠）。
- **修正型**：展示“当前结果”的摘要或关键字段，并提供**可编辑区域**（如文本框、表单），让人直接改；旁边简短说明“请修正后提交，Agent 将基于修正继续”。

#### 关键字段高亮

- 对**金额、收件人、操作类型、风险等级**等做**高亮或单独一行**，让人一眼看到最关键的信息；次要信息（如 request_id、时间戳）可收起或放在次要位置。

### 3. 对比小结

| 维度         | 错误示例                             | 正确示例                           |
| ------------ | ------------------------------------ | ---------------------------------- |
| **信息量**   | 过载（全量日志）或过少（仅“请确认”） | 摘要 + 关键字段，次要信息可折叠    |
| **决策依据** | 缺少意图、动作、参数、风险           | 意图 + 动作/参数 + 风险提示齐全    |
| **可操作**   | 不知道改哪里、点哪里                 | 明确“通过/拒绝/修改”按钮、可编辑区 |
| **重点**     | 无重点，关键信息淹没在长文中         | 关键字段高亮、结构化展示           |

### 4. 实战中的落地

在 **`week11/76_code/agent_with_hitl_demo.py`** 中，审批型 HITL 触发时会打印：**当前意图**（用户目标）、**待执行动作**（工具名与参数）、以及**风险提示**（若为敏感工具）；人通过输入 `y/n/edit` 做出决策，脚本根据决策继续执行或注入拒绝原因。可作为“最小可呈现信息”的参考，再在真实产品中扩展为 UI 与高亮。
