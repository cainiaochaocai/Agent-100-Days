# 73. HITL 的三种介入模式

Day 72 明确了 HITL 的定义及与人工兜底的区别。本节具体讲 **HITL 的三种介入模式**：**Approval（审批型）**、**Correction（修正型）**、**Takeover（接管型）**——分别对应“执行前需人批准”“执行后由人修正”“人直接接管控制权”的三种人机协作方式。

## 一、Approval（审批型）：执行前需人批准，通过/拒绝/修改后再继续

### 1. 含义

- 在 Agent **即将执行**某类动作（如发邮件、下单、删数据）之前，**先暂停**，把“将要执行的动作与参数”呈现给人，由人选择：**通过**（继续执行）、**拒绝**（不执行，并可选说明原因）、或**修改**（改参数后再执行）。
- 人未批准前，该动作**不会执行**；批准后，Agent 再继续执行（或按修改后的参数执行）。

### 2. 典型场景

- **高风险动作**：发邮件、支付、审批通过、数据导出等，业务要求必须经人确认。
- **合规要求**：某些操作按规定需人工审批或签字。
- **敏感参数**：例如金额、收件人、范围等，由人做最后校验。

### 3. 流程要点

- **触发**：当 Agent 决定调用某“需审批”工具或满足“审批型 HITL”的触发条件时，不直接执行，而是进入“等待审批”状态。
- **呈现**：把人需要决策的信息（意图、工具名、参数、风险提示）清晰展示。
- **决策写回**：通过 → 执行该动作并继续；拒绝 → 将拒绝原因注入上下文，Agent 根据原因调整或结束；修改 → 用修改后的参数执行并继续。

### 4. 小结

| 要点         | 内容                                               |
| ------------ | -------------------------------------------------- |
| **时机**     | 执行前                                             |
| **人做什么** | 批准 / 拒绝 / 修改参数                             |
| **写回**     | 通过则执行；拒绝则原因入上下文；修改则用新参数执行 |

## 二、Correction（修正型）：执行后由人修正结果或输入，Agent 根据修正继续或重试

### 1. 含义

- Agent **已执行**某步（如调用了工具、生成了回复），但结果**不符合预期**或**有误**；此时由**人修正**（改结果内容、或改下一步的输入），系统将修正后的内容写回，Agent **根据修正继续**或**重试**该步。
- 人不是“代替系统执行”，而是“纠正系统的输出或输入”，让后续流程基于正确信息继续。

### 2. 典型场景

- **结果错误**：工具返回或模型理解错了，人纠正后让 Agent 用正确结果继续推理。
- **格式/内容不符合要求**：人生成或修改一段内容，再交回给 Agent 作为下一步的输入。
- **标注与反馈**：人标注“哪里错了、应该怎样”，系统将标注作为修正信号，驱动重试或后续逻辑。

### 3. 流程要点

- **触发**：执行后校验失败、或业务规则判定“需人工修正”（如置信度低、关键字段异常）。
- **呈现**：把“当前结果/输出”以及“可编辑或可替换”的入口给人。
- **决策写回**：人提交修正后的内容；系统将其写回（如替换该步的 ToolMessage 或注入一条“修正：…”），Agent 在下一轮基于修正后的上下文继续或重试。

### 4. 小结

| 要点         | 内容                                          |
| ------------ | --------------------------------------------- |
| **时机**     | 执行后                                        |
| **人做什么** | 修正结果或输入、标注错误、提供正确内容        |
| **写回**     | 修正内容替换或注入上下文，Agent 据此继续/重试 |

## 三、Takeover（接管型）：人直接接管控制权，Agent 暂停或转为辅助，由人完成剩余动作

### 1. 含义

- 当系统判定“不应继续由 Agent 自动执行”（如连续失败、用户明确要求人工、或反思输出“需人工介入”）时，**人接管控制权**：Agent 暂停或仅作辅助（如只提供建议），**剩余动作由人完成**（人自己操作业务系统、或通过专门的人工操作界面完成任务）。
- 与审批、修正不同：这里**执行主体从 Agent 变为人**，Agent 不再自动执行后续敏感或复杂步骤。

### 2. 典型场景

- **连续失败**：反思或规则判定“再自动重试无意义”，转交给人处理。
- **用户请求**：用户说“转人工”“我要人工客服”，触发接管。
- **异常与合规**：遇到无法自动处理的异常或合规要求，必须由人完成后续操作。

### 3. 流程要点

- **触发**：规则或反思输出“需人工接管”；或用户主动请求。
- **呈现**：把当前状态、历史、失败原因或用户诉求整理给人，并提供“人可执行”的入口（如工单、操作界面、或明确说明“请人工完成 X”）。
- **写回**：人完成操作后，可将结果写回系统（如“已人工处理，结果：…”），用于闭环记录或后续流程；Agent 本轮回合结束，不再自动继续该任务链。

### 4. 小结

| 要点         | 内容                                          |
| ------------ | --------------------------------------------- |
| **时机**     | 异常时、用户请求时、或规则/反思判定需人接管时 |
| **人做什么** | 直接执行剩余动作，Agent 暂停或仅辅助          |
| **写回**     | 可选：人将处理结果写回，用于记录或闭环        |

## 四、三种模式对比表

| 模式           | 时机        | 人的角色           | Agent 后续行为                       |
| -------------- | ----------- | ------------------ | ------------------------------------ |
| **Approval**   | 执行前      | 批准/拒绝/修改参数 | 按人决策执行或不执行、或用新参数执行 |
| **Correction** | 执行后      | 修正结果或输入     | 基于修正继续或重试                   |
| **Takeover**   | 异常/请求时 | 接管并执行剩余动作 | 暂停或仅辅助，由人完成               |
