# 33. 重排序 (Rerank)

上一节我们学了检索：用向量检索（或混合检索）从知识库里捞出 Top-K 个 chunk。但**初筛虽然快，往往不够准**——向量相似度只能衡量“方向是否接近”，无法精确判断“这段话是否真的在回答这个问题”。重排序（Rerank）就是在初筛之后，对 Top-K 再做一次**精细化打分**，把真正相关的块排到前面，甚至只保留高分块再交给 LLM，从而提升答案质量、减少 token 消耗和干扰。

本节围绕三块学习内容展开：**Rerank 的必要性**、**主流重排序模型的应用（BGE-Reranker / Cohere Rerank API）**、**上下文压缩（Context Compression）**。

## 一、Rerank 的必要性：为什么初筛不够准

### 1. 初筛（Retrieval）在做什么、缺什么

- **做法**：用 Query 和文档块的 **Embedding** 做相似度计算（如余弦相似度），按分数取 Top-K。计算是**对称的**：Query 和 Doc 各自编码成向量，两者之间只做一次相似度运算，速度很快，适合在海量块里做粗筛。
- **局限**：这种模型（Bi-Encoder / 双塔）没有“同时看到”问题和某一段落，无法建模**问题与段落之间的细粒度匹配关系**。例如问题问“报销上限是多少”，文档里既有“报销流程”也有“报销上限 5000 元”，两段都可能因为都含“报销”而得到相近的向量分，初筛难以把“上限 5000”精准排到最前。

所以：**初筛快、适合做第一轮筛选，但排序不够精细。**

### 2. Rerank 在做什么：Cross-Encoder 精细化打分

- **思路**：把 **Query 和每一个候选段落拼在一起**，送进一个专门做“相关性打分”的模型（**Cross-Encoder**），让模型**同时看到问题和该段文字**，输出一个相关性分数（或分类标签）。对 Top-K 的每条都打一次分，再按分数重新排序。
- **特点**：Cross-Encoder 能利用“问题 + 段落”的联合信息，判断“这段话是否在回答这个问题”，因此**更准**；但要对 K 个候选各做一次前向计算，**比向量检索慢**，所以通常只对**初筛后的 Top-K（如 20 ～ 50 条）**做 Rerank，而不是对全库做。

流程可以概括为：

```text
向量检索（或混合检索）→ 取 Top-K（如 20）→ Rerank 模型对每条 (Query, Doc) 打分 → 按 Rerank 分数重排 → 取新的 Top-N（如 5）交给 LLM
```

理解这一点，就明白 Rerank 的定位：**在“快”的初筛之后，用“准”的模型做二次排序，在效果和成本之间取得平衡。**

## 二、主流重排序模型应用：BGE-Reranker 与 Cohere Rerank API

实践中常用两类方式：**自建 Rerank 模型（如 BGE-Reranker）** 和 **调用云 API（如 Cohere Rerank）**。前者可控、可离线；后者免运维、多语言支持好。

### 1. BGE-Reranker（本地 / 自建）

BGE-Reranker 是 BAAI 开源的 Cross-Encoder 模型，输入为「query + 文档」对，输出相关性分数，适合对初筛后的候选做重排。

**安装与基本用法**（以 `FlagEmbedding` 为例）：

```python
from FlagEmbedding import FlagReranker

reranker = FlagReranker("BAAI/bge-reranker-base", use_fp16=True)

query = "公司报销上限是多少？"
docs = [
    "员工差旅报销需在返回后 30 日内提交……",
    "报销上限为每人每年 5000 元，超出部分需特批。",
    "报销流程：先填写 OA 表单……",
]

# 输入 (query, doc) 对，返回分数（越高越相关）
pairs = [(query, d) for d in docs]
scores = reranker.compute_score(pairs)  # 若多条，返回 list

# 按分数排序，取 Top-N
if isinstance(scores, list):
    doc_scores = list(zip(docs, scores))
else:
    doc_scores = [(docs[0], scores)]
doc_scores.sort(key=lambda x: -x[1])
top_docs = [d for d, s in doc_scores[:3]]
```

- **模型选择**：`bge-reranker-base` 与 `bge-reranker-large` 等，体积与精度不同，按显存和延迟需求选择。
- **注意**：Reranker 输入是「query + 单段 doc」的 pair，对 Top-K 条候选逐条调用即可；输出分数可用于排序，也可设定阈值做过滤。

### 2. Cohere Rerank API（云端）

Cohere 提供 Rerank 接口：你传入一个 query 和一个文档列表，接口返回按相关性排序后的结果（或带分数），无需自建模型。

**基本调用方式**（示例，具体以官方文档为准）：

```python
import cohere

co = cohere.Client(api_key="YOUR_API_KEY")

response = co.rerank(
    model="rerank-english-v2.0",  # 或 rerank-multilingual-v2.0
    query="公司报销上限是多少？",
    documents=[
        "员工差旅报销需在返回后 30 日内提交……",
        "报销上限为每人每年 5000 元……",
        "报销流程：先填写 OA 表单……",
    ],
    top_n=3,
)

# 按 rank 顺序使用
for item in response.results:
    idx = item.index
    doc = documents[idx]
    score = item.relevance_score
```

- **优点**：免部署、多语言模型可选、适合快速上线。
- **注意**：需要 API Key、按调用计费；文档需在 API 允许的长度内。

无论是 BGE-Reranker 还是 Cohere，**流程一致**：初筛 Top-K → 对 K 条调用 Rerank → 按新分数取 Top-N 再送入 LLM，即可明显提升检索精度。

## 三、上下文压缩（Context Compression）：重排后只保留最有价值的块

Rerank 之后我们得到了按相关性从高到低排列的候选。若把**所有** Top-K 都塞进 Prompt，会带来两方面的浪费：**token 消耗大**、**低相关块干扰模型**。上下文压缩（Context Compression）的做法是：**在重排后剔除低分块，只保留最有价值的若干段**，既省 token，又降低噪音。

### 1. 为什么要压缩

- **Token 消耗**：上下文越长，调用 LLM 的成本越高，且容易触达上下文长度上限。
- **信号与噪音**：排名靠后的块往往与问题关系较弱，全部放进 Prompt 会稀释关键信息，增加模型“答偏”或引用无关句子的概率。

因此，在 Rerank 之后再做一步“**只留高相关**”的筛选，是常见且推荐的做法。

### 2. 常见做法

| 方式        | 说明                                                           |
| --------- | ------------------------------------------------------------ |
| **按排名截断** | 重排后只取新的 Top-N（如前 3 ～ 5 条），其余直接丢弃。实现简单、效果稳定。                  |
| **按分数阈值** | 设定 Rerank 分数阈值，只保留高于阈值的块；低于阈值的视为不相关，不送入 LLM。适合对“可解释性”有要求的场景。 |
| **混合**    | 先按分数过滤（如低于某阈值去掉），再在剩余块中按分数取 Top-N，兼顾质量与数量上限。                 |

压缩后的结果再组装成 Prompt（例如“根据以下参考内容回答问题”+ 仅包含高相关块），即可在**不增加检索量的前提下**提升答案质量。

### 3. 与 Rerank 的配合

推荐流水线为：

```text
检索 Top-K（如 20）→ Rerank 对 20 条打分并重排 → Context Compression（按分数或 Top-N 只保留 3～5 条）→ 将保留的段落组装为上下文，交给 LLM 生成
```

这样既利用了 Rerank 的精度，又通过压缩控制了上下文长度和噪音，是 RAG 中非常常见的一环。



## 小结

| 学习点              | 要点                                                                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| **Rerank 的必要性**  | 初筛（向量/混合检索）快但不够准；用 Cross-Encoder 对 Top-K 的 (Query, Doc) 逐条打分并重排，可显著提升排序精度。                                 |
| **主流 Rerank 应用** | 自建可用 **BGE-Reranker**（如 FlagEmbedding）；云端可用 **Cohere Rerank API**。流程均为：初筛 Top-K → Rerank 打分 → 按新分数取 Top-N。 |
| **上下文压缩**        | 重排后剔除低分块，仅保留高分或 Top-N 段，减少 token 消耗并降低对模型的干扰；常与 Rerank 串联使用。                                               |

Rerank + 上下文压缩，是在检索之后、生成之前的“**质量闸门**”：既让 LLM 只看到最相关的几段，又控制上下文长度。下一节我们将学习**问题改写与答案生成**，包括如何用 LLM 改写用户提问以提升检索效果，以及如何设计 Prompt 与引用归属。
