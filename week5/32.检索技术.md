# 32.检索技术 (Retrieval)

前几节我们完成了「文档加载 → 清洗 → 分块 → 向量化」，知识已经变成一块块带向量的文本。接下来要解决的是：**用户提问时，如何从海量块里快速、精准地捞出最相关的那几条？** 这就是检索（Retrieval）要做的事。

检索是知识库的「大脑门」：选错向量库或检索策略，再好的分块和 Embedding 也会像大海捞针；做对了，模型就能**秒抓重点**，回答又快又准。

本节围绕三块内容展开：**向量库选型与增删改查**、**混合检索（语义 + 关键词）**、**多向量检索（Multi-vector）**。

## 一、向量库（Vector Store）选型与基础操作

向量库专门做一件事：**存向量、按相似度查**。你把 chunk 的 embedding 存进去，查询时给它一个「问题向量」，它返回最相似的若干条（Top-K），并带上你存的元数据（如原文、来源）。选型决定了能撑多大体量、多高并发，以及你要不要自己运维。

### 1. 常用向量库对比

| 名称           | 特点             | 适用场景              |
| ------------ | -------------- | ----------------- |
| **FAISS**    | 本地、开源、单机、无服务端  | 小到中型知识库、快速原型、离线实验 |
| **Milvus**   | 分布式、高性能、可扩展    | 海量数据、高 QPS、生产级    |
| **Pinecone** | 云托管、自动扩缩容、按量计费 | 不想运维、快速上线、弹性规模    |

- **FAISS**：Facebook 开源，适合本地或单机部署，接口简单，很多框架（如 LangChain）直接集成；数据量在百万级以内、QPS 不高时很够用。
- **Milvus**：面向大规模向量检索，支持分布式与多种索引类型，适合企业级、超大规模知识库。
- **Pinecone**：完全托管，你只管写入和查询，适合快速验证和不想管基础设施的场景。

选型时重点看：**数据量级、是否要分布式、能否接受自建与运维**。多数 RAG 原型用 FAISS 即可；上线后若数据与并发上来，再考虑 Milvus 或 Pinecone。

### 2. 基础操作：增删改查（CRUD）

无论用哪种向量库，逻辑上都是四类操作：**增（Insert）、删（Delete）、改（Update）、查（Query）**。下面用 **FAISS + 本地列表** 做最小可运行示例，便于理解流程；实际项目可换成 LangChain 的 FAISS / Milvus / Pinecone 封装。

**增（Insert）**：把 chunk 的 embedding 和对应原文（及可选 metadata）写入向量库。

```python
import numpy as np
import faiss
from typing import List, Dict

# 假设已有 embeddings 和 texts（分块后的原文）
def build_faiss_index(embeddings: np.ndarray, texts: List[str], metadatas: List[Dict] = None):
    dim = embeddings.shape[1]
    index = faiss.IndexFlatIP(dim)   # 内积检索（若向量已归一化，等价于余弦相似度）
    index.add(embeddings.astype("float32"))
    return index, texts, metadatas or [{}] * len(texts)
```

**查（Query）**：用「问题向量」检索 Top-K，并取回原文。

```python
def query_faiss(index, texts, metadatas, query_embedding: np.ndarray, top_k: int = 5):
    scores, indices = index.search(query_embedding.astype("float32"), top_k)
    return [
        {"text": texts[i], "metadata": metadatas[i], "score": float(scores[0][j])}
        for j, i in enumerate(indices[0])
    ]
```

**删（Delete）**：FAISS 的 `IndexFlat*` 不支持单条删除，常见做法是**按 ID 过滤后重建索引**，或使用支持删除的索引类型（如 `IndexIDMap` + 维护 id→ 向量 的映射，删除时标记 id，查询后过滤）。Milvus / Pinecone 等通常提供按 ID 删除接口。

**改（Update）**：多数向量库的「改」等价于**先删后增**：删除旧 id 的向量，再插入新向量与 metadata。保证同一 chunk 只保留最新一条即可。

## 二、混合检索（Hybrid Search）：语义 + 关键词

单纯靠**向量检索**有一个明显短板：对**专有名词、缩写、数字、型号**等，语义 Embedding 往往不够准。例如用户问「EAR 的适用条件」，文档里写的是「Export Administration Regulations」；若模型把 "EAR" 理解成 "ear（耳朵）"，语义向量就会偏。反过来，**关键词检索**（如 BM25）对这类精确词非常敏感，但对同义改写、换说法就不敏感。

**混合检索（Hybrid Search）** 的做法是：同时做**语义向量检索**和**关键词检索（如 BM25）**，再把两路结果融合排序，兼顾「意思相近」和「词面匹配」。

### 1. BM25 简要原理

BM25 是一种基于**词频（TF）和逆文档频率（IDF）** 的排序函数：某个词在文档里出现越多、且在全体文档里出现越少，得分越高。它对「精确词」敏感，适合专有名词、缩写、编号。不要求手写公式，会用现成库即可，例如 Python 的 `rank_bm25`。

### 2. 融合方式

常见两种：

- **加权分数融合**：对向量相似度与 BM25 分数分别做归一化（如 min-max 或 z-score），再 `α * norm_vector_score + (1-α) * norm_bm25_score`，按融合分排序。
- **倒数排名融合（RRF）**：不依赖分数尺度，只利用排名。对每条文档，若在向量检索中排第 k1 名、在 BM25 中排第 k2 名，则 RRF 得分 = `1/(k1+60) + 1/(k2+60)`（常数 60 可调）。两路结果合并去重后按 RRF 排序。

RRF 实现简单、对分数尺度不敏感，工程上很常用。

### 3. 简单实现思路

```python
# 混合检索流程示意
# 1. 向量检索：query_embedding -> vector_store.search(top_k=20)，得到 [(doc_id, score), ...]
# 2. BM25 检索：query 文本 -> bm25.get_scores(query) 后取 Top-20 的 doc_id
# 3. RRF 融合：两路结果按 doc_id 合并，RRF(doc) = sum 1/(rank + k)
from rank_bm25 import BM25Okapi

def rrf_fusion(vector_results, bm25_top_ids, k=60):
    """vector_results / bm25_top_ids 均为 (doc_id, ...) 或 doc_id 列表，按排名加分"""
    rrf_scores = {}
    for rank, doc_id in enumerate(vector_results):  # vector_results 为 doc_id 列表
        rrf_scores[doc_id] = rrf_scores.get(doc_id, 0) + 1 / (rank + k)
    for rank, doc_id in enumerate(bm25_top_ids):
        rrf_scores[doc_id] = rrf_scores.get(doc_id, 0) + 1 / (rank + k)
    return sorted(rrf_scores.items(), key=lambda x: -x[1])[:5]  # 返回 Top-5 doc_id
```

在**金融、法规、专利、内部术语**等对专有名词要求高的场景，建议默认上混合检索，能明显减少「明明文档里有这个词却检不出来」的情况。



## 三、多向量检索（Multi-vector）：提升复杂提问的匹配率

一个 chunk 里往往包含**多个信息点**（例如：适用对象、条件、例外、处罚）。用户可能只从其中一个角度问（「这条的适用对象是谁？」），若检索时只用一个向量代表整个 chunk，可能因为「问题表述」和「chunk 原文」的表述方式不同，导致相似度不够高，被排到后面甚至漏检。

**多向量检索**的思路是：**对同一个 chunk 生成多个「概括性问题」或「假设性问题」，分别做 Embedding 存进去**；检索时用用户问题与**所有**这些向量做相似度计算，只要有一个命中，该 chunk 就有机会进入 Top-K。这样可以从不同角度「钩住」同一个块，提高复杂提问的匹配率。

### 1. 具体做法

- **索引阶段**：对每个 chunk，用 LLM 生成若干条「可能被用户问到的问法」或「该段落的子问题」，例如：
  - 适用对象是谁？
  - 有哪些限制条件？
  - 违反后的处罚是什么？
    每条问法单独做 Embedding，在向量库中与 chunk 的 doc_id 关联（可存为多条记录，doc_id 相同；或一条 doc 对应多向量，检索时按 doc 去重）。
- **检索阶段**：用户问题做一次 Embedding，在向量库中检索 Top-K（K 可稍大，如 20）。按 **doc_id 去重**，同一 chunk 只保留得分最高的那条（或对同一 chunk 的多个向量得分取 max / 平均），再按最终得分排序，得到最终 Top-K 个 chunk。

这样，即使用户只问「适用对象」，只要有一条「适用对象是谁？」的概括性向量被存过，就能把对应 chunk 拉上来。

### 2. 适用场景与注意点

- **适合**：法规、政策、产品文档、FAQ 等「一个段落多维度信息」的 RAG；用户问题角度多样时效果提升明显。
- **代价**：存储与索引时间成倍增加（一个 chunk 变多条向量），检索时计算量也更大；需要控制「每 chunk 问题数」和总向量规模。
- 可与 **HyDE（假设性文档生成）** 结合：用 LLM 根据用户问题生成一段「假设性答案」，对这段答案做 Embedding 再去检索，有时比直接用问题向量更贴文档表述，本质也是「多一种向量视角」。

## 小结

| 主题        | 要点                                                             |
| --------- | -------------------------------------------------------------- |
| **向量库选型** | FAISS 适合本地与原型，Milvus/Pinecone 适合大规模与生产；检索的稳定性依赖清晰的增删改查与索引更新策略。 |
| **混合检索**  | 向量检索 + BM25（或其它关键词检索），用加权或 RRF 融合，解决专有名词、缩写、数字匹配不准的问题。         |
| **多向量检索** | 同一 chunk 对应多个概括性问题向量，检索时多角度匹配、按 doc 去重排序，提升复杂提问的匹配率。           |

一句话：**Chunking 是把知识切成模型能读的块，Retrieval 是教系统在知识海洋里找到对的块。** 选对向量库、用好混合检索和多向量，RAG 才能对用户问题做到**快速、精准、可控**的回答。下一节我们将学习**重排序（Rerank）**，在初筛检索之后再做一次精细打分，进一步压榨准确率。
