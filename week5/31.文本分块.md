# 31. 文本分块 (Chunking)

如果说 **Loaders / ETL / Metadata** 是把“知识变干净”，那 **Chunking（文本分块）** 在做一件更隐蔽、却更关键的事：

> **把知识变成“模型能用、检索能准”的形状。**

很多 RAG 效果差，不是检索算法不行，而是**切块切错了**——要么语义被拦腰砍断，要么块太大太小，检索和生成都受影响。

本节围绕三块学习内容展开：**分块策略的选择**、**重叠窗口（Overlap）设计**、**分块粒度对检索的影响**。

## 一、分块策略的选择：固定长度 vs 语义切分

分块的核心不是“切多长”，而是**按什么逻辑切**。不同策略在“语义完整性”和“可控性”之间做权衡，同时还要考虑**模型上下文窗口**能装下多少内容。

### 1. 固定长度切分

最常见的新手做法是：**每 N 字符（或 N 个 token）一刀切**，例如 500 / 1000 字符一块。

| 优点                      | 缺点                 |
| ----------------------- | ------------------ |
| 实现简单、长度可控、便于估算 token 占用 | 不关心段落、句子边界，容易从中间砍断 |

带来的问题很典型：

- 一段完整论证被从中间切断
- 表格和解释分离、定义和例子分离、标题和正文分离
- 检索到的 chunk 常常是“半句话 + 半句话”，模型拿到的是**语义残骸**

Embedding 时，这种“残骸”的向量会掺杂前后不完整的信息，检索既容易漏、也容易带进无关内容。

### 2. 语义切分（如递归字符切分）

更好的方式是**按语义边界切**，在“到长度就切”之前，先尊重文档结构。**递归字符切分（Recursive Character Text Splitter）** 是常用的一种：

- 不是“满 N 字符就切”，而是**按分隔符优先级**依次尝试：先按大块（段落、换行）切，切完若某段仍超长，再按句子、空格、字符逐级细分。
- 逻辑可以概括为：

```text
段落（\n\n）→ 换行（\n）→ 句子（. ）→ 空格 → 字符
```

这样在同样 1000 字符的约束下：

- **固定切分**：可能得到“随机截断”的文本
- **语义切分**：更可能得到“一个完整小知识单元”（如一段论证、一个列表、一个定义+例子）

语义完整的块，Embedding 更稳定，检索命中后模型也更容易理解。

### 3. 与模型上下文窗口的平衡点

分块还要考虑**模型上下文窗口**：chunk 太大，单块就占满窗口，留给“问题 + 多块检索结果”的空间变少；chunk 太小，信息碎片化，检索到的多块之间难以拼成完整答案。

实践中需要在两者之间找平衡：

- **语义完整性**：尽量按段落、句子切，保证每一块是“可独立理解”的单元。
- **上下文窗口**：单块不宜过长（例如一般控制在几百到一千多字符），以便一次能放入多个 chunk + 用户问题 + 系统提示。

常见做法是：先定一个**目标 chunk 长度区间**（如 600 ～ 1200 字符），再选用**递归字符切分**在该长度内尽量按语义边界切；若文档结构清晰，可优先用“段落 + 换行”作为分隔符，减少在句子中间动刀。

## 二、重叠窗口（Overlap）设计：用重复字符保持连续性

即便用了语义切分，仍有一个无法避免的问题：**关键信息刚好落在切分边界上**，前半句在 Chunk A 结尾，后半句在 Chunk B 开头，单独看任一块都不完整。

### 1. 问题示例

```text
Chunk A 结尾：……因此 EAR 的核心判断依据是
Chunk B 开头：ECCN 的技术参数和最终用途。
```

用户问“EAR 的判断依据是什么？”时，检索可能只命中 Chunk A 或 Chunk B，模型都拿不到完整信息。

### 2. Overlap 在做什么

**Overlap（重叠窗口）** 的做法是：在相邻 chunk 之间**保留一段重复的字符**，让后一块的**开头**重复前一块的**结尾**。

例如设置 80 ～ 150 字符的重叠：

```text
Chunk A: ……因此 EAR 的核心判断依据是
Chunk B: 核心判断依据是 ECCN 的技术参数和最终用途。……
```

这样“核心判断依据是 ECCN 的技术参数和最终用途”会同时出现在两个块里，检索到其中任意一块，模型都能看到完整逻辑。

### 3. 如何设置“重复字符”

- **长度**：一般取 **chunk_size 的 10%～ 20%**，或固定 **80 ～ 150 字符**。太小起不到缓冲作用，太大则重复过多、浪费 token 并拉长上下文。
- **实现**：多数分块库都提供 `chunk_overlap`（或类似）参数。例如 LangChain 的 `RecursiveCharacterTextSplitter`：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=150,   # 相邻块之间重叠 150 字符
    length_function=len,
    separators=["\n\n", "\n", "。", " ", ""]
)
chunks = splitter.split_text(long_text)
```

- **效果**：
  1. 检索时不会因为“切在关键词上”而丢失关键上下文。
  2. LLM 在阅读多块时，有重叠区作为“缓冲区”，理解更连贯。

Overlap 本质是在**人为模拟上下文记忆**，用少量重复换回语义连贯性。

## 三、分块粒度对检索的影响：过粗与过细都会出问题

Chunk 的**粒度**（块有多大、多碎）会直接影响检索质量和生成质量：过粗会引入冗余和噪音，过细会导致上下文缺失。

### 1. 颗粒度过粗（如 2000+ 字符一大块）

| 现象                  | 后果                        |
| ------------------- | ------------------------- |
| 一个 chunk 里混入多个主题或段落 | 向量被“平均化”，检索时难以精确对准用户问题    |
| 命中后整块塞给模型           | 噪音多、重点难抓，模型容易答偏或漏答        |
| token 占用大           | 同样 Top-K 下，能放的块数变少，信息覆盖变窄 |

结果是：**检索到了，但模型读不懂重点**，或“答了但答的不是最相关的那几句”。

### 2. 颗粒度过细（如 100 ～ 200 字符一块）

| 现象             | 后果                        |
| -------------- | ------------------------- |
| 定义、条件、结论被拆到不同块 | 检索可能只命中其中一块，缺少前提或结论       |
| 上下文断裂          | 模型需要“拼图式”理解，容易幻觉或推理错误     |
| 块数暴增           | 向量库变大、检索候选多，且单块信息过少，排序不稳定 |

结果是：**检索很精准到某一句，但信息不完整**，模型难以基于单块给出可靠答案。

### 3. 如何把握粒度

- **过粗**：适当减小 `chunk_size`，或加强语义切分（更细的分隔符），让一块尽量对应“一个主题、一段完整论述”。
- **过细**：适当增大 `chunk_size`，或放宽切分优先级，避免在句子、短语级别切碎。
- **经验区间**：多数知识库场景下，**600 ～ 1200 字符**一块、**80 ～ 150 字符** Overlap、配合**递归语义切分**，能在“语义完整”和“上下文窗口/检索精度”之间取得较好平衡。



## 小结

| 学习点         | 要点                                                                               |
| ----------- | -------------------------------------------------------------------------------- |
| **分块策略**    | 固定长度简单但易破坏语义；优先用语义切分（如递归字符切分），并在语义完整性与模型上下文窗口之间找平衡。                              |
| **Overlap** | 通过设置 80 ～ 150 字符（或 chunk 的 10%～ 20%）的重叠，让相邻块在边界处重复一段内容，防止关键信息在切分点丢失，提升检索与生成的连贯性。 |
| **分块粒度**    | 过粗导致冗余噪音、难以抓重点；过细导致上下文缺失、易幻觉。需根据文档类型和检索效果调节 chunk_size 与切分方式。                    |

Chunking 做对之后，同样的向量库和模型，命中率和回答质量都会明显提升，因为模型面对的不再是碎片化文本，而是**一个个完整的小知识单元**。下一节我们将学习**检索技术（Retrieval）**，在这些块的基础上做向量检索与混合检索。
