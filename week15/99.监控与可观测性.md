# 99. 监控与可观测性

Week 12-14 我们搭建了完整的 Agent 平台，并实现了两个垂直场景 Agent。本节讲**监控与可观测性**：**指标收集**（请求量、延迟、错误率、成本）、**日志与 trace**（结构化日志、分布式 trace、调用链追踪），以及**接入 Langfuse**（Langfuse 的 trace 记录、成本统计、性能分析）。

## 一、指标收集：请求量、延迟、错误率、成本

### 1. 请求量

- **含义**：统计**单位时间内的请求数**（如每分钟、每小时、每天），按 Agent、通道、用户等维度统计。
- **指标**：
  - `requests_total`：总请求数
  - `requests_per_minute`：每分钟请求数
  - `requests_by_agent`：按 Agent 统计请求数
  - `requests_by_channel`：按通道统计请求数
- **作用**：了解系统负载、识别热点 Agent、容量规划。

### 2. 延迟

- **含义**：统计**请求的响应时间**（从 Gateway 接收请求到返回响应的总时长），以及各阶段的延迟（路由、LLM 调用、工具执行）。
- **指标**：
  - `latency_p50`、`latency_p95`、`latency_p99`：延迟分位数
  - `latency_by_agent`：按 Agent 统计延迟
  - `latency_by_stage`：按阶段统计延迟（路由、LLM、工具）
- **作用**：识别性能瓶颈、优化慢查询、SLA 监控。

### 3. 错误率

- **含义**：统计**请求失败率**（如 LLM 调用失败、工具执行失败、路由失败），按错误类型分类。
- **指标**：
  - `error_rate`：错误率（错误数 / 总请求数）
  - `error_by_type`：按错误类型统计（LLM 错误、工具错误、路由错误）
  - `error_by_agent`：按 Agent 统计错误率
- **作用**：快速发现系统问题、定位错误来源、质量监控。

### 4. 成本

- **含义**：统计**LLM 调用的成本**（按模型、按 token 数、按请求数），以及工具调用的成本（如 API 调用费用）。
- **指标**：
  - `cost_total`：总成本
  - `cost_by_model`：按模型统计成本
  - `cost_by_agent`：按 Agent 统计成本
  - `cost_per_request`：平均每请求成本
- **作用**：成本控制、预算管理、优化高成本 Agent。

### 5. 小结表

| 指标类型    | 指标示例                              | 作用            |
| ------- | --------------------------------- | ------------- |
| **请求量** | requests_total, requests_by_agent | 了解系统负载、容量规划   |
| **延迟**  | latency_p95, latency_by_stage     | 识别性能瓶颈、SLA 监控 |
| **错误率** | error_rate, error_by_type         | 快速发现问题、质量监控   |
| **成本**  | cost_total, cost_by_model         | 成本控制、预算管理     |

## 二、日志与 trace：结构化日志、分布式 trace、调用链追踪

### 1. 结构化日志

- **含义**：日志以**结构化格式**（JSON）记录，包含固定字段（时间戳、级别、模块、消息、上下文）。

- **格式**：
  
  ```json
  {
    "timestamp": "2025-02-17T10:00:00Z",
    "level": "INFO",
    "module": "gateway",
    "message": "Request received",
    "user_id": "user_123",
    "session_id": "session_456",
    "agent_id": "deep_research_agent"
  }
  ```

- **作用**：便于日志查询、过滤、聚合、告警。

### 2. 分布式 trace

- **含义**：一个请求经过**多个服务/组件**（Gateway → Router → Runtime → LLM → Tool），需要追踪整个调用链。
- **实现**：使用 **trace_id**（全局唯一）关联所有相关日志，每个组件记录 trace_id，形成调用链。
- **格式**：每个日志包含 `trace_id`，查询时按 trace_id 聚合，可以看到完整的调用链。

### 3. 调用链追踪

- **含义**：追踪一次请求的**完整调用链**：Gateway → Router → Runtime → LLM → Tool → Runtime → Gateway。
- **信息**：每个节点的输入、输出、延迟、错误。
- **作用**：快速定位问题（哪个节点出错）、性能分析（哪个节点慢）、理解请求流程。

### 4. 小结表

| 内容            | 含义               | 实现方式             |
| ------------- | ---------------- | ---------------- |
| **结构化日志**     | JSON 格式日志，固定字段   | 日志库（如 structlog） |
| **分布式 trace** | trace_id 关联多组件日志 | trace_id 传递与记录   |
| **调用链追踪**     | 完整调用链的输入输出延迟     | trace_id 聚合查询    |

## 三、接入 Langfuse：Langfuse 的 trace 记录、成本统计、性能分析

### 1. Langfuse 简介

- **含义**：Langfuse 是一个**开源的可观测性平台**，专门用于 LLM 应用，支持 trace 记录、成本统计、性能分析。
- **功能**：
  - **Trace 记录**：自动记录 LLM 调用、工具调用、Agent 执行流程。
  - **成本统计**：根据模型与 token 数自动计算成本。
  - **性能分析**：分析延迟、错误率、token 使用等。

### 2. Trace 记录

- **接入方式**：在 Runtime 的 LLM 调用处接入 Langfuse（如用 LangChain 的 LangfuseCallbackHandler）。
- **记录内容**：
  - LLM 调用（输入、输出、token 数、延迟）
  - 工具调用（工具名、参数、结果、延迟）
  - Agent 执行流程（步骤、决策、错误）
- **查询**：在 Langfuse UI 中查询 trace，查看完整的执行流程。

### 3. 成本统计

- **自动计算**：Langfuse 根据模型与 token 数自动计算成本（如 OpenAI GPT-4 的定价）。
- **统计维度**：按模型、按 Agent、按用户、按时间统计成本。
- **预算告警**：设置预算阈值，超预算时告警。

### 4. 性能分析

- **延迟分析**：分析各阶段的延迟（LLM 调用、工具执行），识别瓶颈。
- **错误分析**：分析错误类型、错误率、错误趋势。
- **Token 分析**：分析 token 使用量（输入、输出），优化 prompt 或上下文长度。

### 5. 接入步骤

- **步骤 1**：安装 Langfuse（`pip install langfuse`）。
- **步骤 2**：配置 Langfuse（API key、project name）。
- **步骤 3**：在 Runtime 中接入 Langfuse Callback（如 LangChain 的 `LangfuseCallbackHandler`）。
- **步骤 4**：启动平台，Langfuse 自动记录 trace。

### 6. 小结表

| 功能           | 含义                 | 作用        |
| ------------ | ------------------ | --------- |
| **Trace 记录** | 自动记录 LLM 调用、工具调用   | 完整的执行流程追踪 |
| **成本统计**     | 根据模型与 token 自动计算成本 | 成本控制、预算管理 |
| **性能分析**     | 分析延迟、错误率、token 使用  | 性能优化、问题定位 |

## 四、实战中的实现

在 **`week15/105_code/production_platform_demo.py`** 中已实现完整示例：

- **指标收集**：`MetricsCollector` 类统计 `requests_total`、`errors_total`、`cost_total`，维护延迟样本并计算 `latency_p50`/`latency_p95`、`error_rate`，按 `agent_id` 与 `error_type` 分组；`Gateway.handle_request` 每次请求结束后调用 `metrics.record()`。
- **结构化日志**：`structured_log(level, message, trace_id=..., user_id=..., agent_id=..., latency_ms=...)` 输出 JSON 行，便于检索与聚合。
- **分布式 trace**：每次请求生成唯一 `trace_id`，在日志与审计中贯穿传递，便于按 trace_id 串联调用链。
- **Langfuse 接入**：可将 LangChain 的 `LangfuseCallbackHandler` 传入 LLM 的 `invoke()`，自动上报 trace 与成本；Demo 中未强制依赖，可按需在 Runtime 中增加。
