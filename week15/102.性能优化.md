# 102. 性能优化

Day 101 讲了安全与权限控制。本节讲**性能优化**：**缓存策略**（结果缓存、LLM 响应缓存、工具结果缓存）、**并发控制**（请求队列、限流、超时控制），以及**数据库优化与 LLM 调用优化**（索引优化、连接池、LLM 批处理、流式响应）。

## 一、缓存策略：结果缓存、LLM 响应缓存、工具结果缓存

### 1. 结果缓存

- **含义**：缓存**相同请求的结果**（如相同的用户问题、相同的 SQL 查询），避免重复计算。
- **缓存 key**：请求的 hash（如用户问题 + 上下文 hash），或 SQL 语句的 hash。
- **缓存时间**：根据数据更新频率设置（如实时数据缓存 1 分钟，历史数据缓存 1 小时）。
- **实现**：用 Redis 或内存缓存（如 Python 的 `functools.lru_cache`），Gateway 或 Runtime 中检查缓存，命中则直接返回。

### 2. LLM 响应缓存

- **含义**：缓存**相同 prompt 的 LLM 响应**（如相同的用户问题 + 相同的上下文），避免重复调用 LLM。
- **缓存 key**：prompt 的 hash（如 messages 的 hash）。
- **缓存时间**：LLM 响应通常可以缓存较长时间（如 1 小时或 1 天），因为相同 prompt 的响应通常不变。
- **实现**：在 Runtime 的 LLM 调用处检查缓存，命中则直接返回缓存的响应。

### 3. 工具结果缓存

- **含义**：缓存**工具执行的结果**（如相同的 SQL 查询结果、相同的搜索查询结果），避免重复执行工具。
- **缓存 key**：工具名 + 参数的 hash。
- **缓存时间**：根据工具结果的更新频率设置（如搜索查询缓存 5 分钟，数据库查询缓存 1 分钟）。
- **实现**：在 ToolExecutor 中检查缓存，命中则直接返回缓存的结果。

### 4. 缓存失效

- **含义**：当数据更新时，**相关缓存失效**（如新订单产生，相关 BI 查询缓存失效）。
- **实现**：
  - **TTL 过期**：缓存项带过期时间，过期后自动失效。
  - **主动失效**：数据更新时，主动删除相关缓存（如用缓存 key 的前缀匹配，删除所有相关缓存）。

### 5. 小结表

| 缓存类型     | 缓存内容                 | 缓存时间                     |
| ------------ | ------------------------ | ---------------------------- |
| **结果缓存** | 相同请求的结果           | 根据数据更新频率（1 分钟-1 小时） |
| **LLM 响应缓存** | 相同 prompt 的 LLM 响应 | 较长时间（1 小时-1 天）     |
| **工具结果缓存** | 工具执行的结果           | 根据工具更新频率（1 分钟-5 分钟） |

## 二、并发控制：请求队列、限流、超时控制

### 1. 请求队列

- **含义**：当请求量超过系统处理能力时，将请求**放入队列**，按顺序处理。
- **实现**：
  - **内存队列**：用 Python 的 `queue.Queue` 或 `asyncio.Queue`。
  - **消息队列**：用 Redis Queue、RabbitMQ、Kafka 等消息队列。
- **作用**：平滑流量峰值，避免系统过载。

### 2. 限流

- **含义**：限制**单位时间内的请求数**（如每秒最多 10 个请求），超过限制则拒绝或排队。
- **算法**：
  - **令牌桶**：系统以固定速率生成令牌，请求消耗令牌，无令牌则拒绝。
  - **漏桶**：请求以固定速率处理，超过速率则拒绝。
- **实现**：用 Redis 或内存计数器，Gateway 中检查限流，超过限制则返回 `429 Too Many Requests`。

### 3. 超时控制

- **含义**：设置**请求的超时时间**（如 30 秒），超过超时时间则取消请求并返回错误。
- **实现**：
  - **请求级超时**：Gateway 设置请求超时（如 30 秒），超时则返回错误。
  - **组件级超时**：各组件（LLM 调用、工具执行）设置超时，超时则取消。
- **作用**：避免长时间等待，快速失败，释放资源。

### 4. 小结表

| 控制项       | 含义                     | 实现方式                         |
| ------------ | ------------------------ | -------------------------------- |
| **请求队列** | 请求排队，按顺序处理     | 内存队列或消息队列               |
| **限流**     | 限制单位时间内的请求数   | 令牌桶或漏桶算法                 |
| **超时控制** | 设置请求的超时时间       | 请求级超时或组件级超时           |

## 三、数据库优化与 LLM 调用优化：索引优化、连接池、LLM 批处理、流式响应

### 1. 数据库优化

- **索引优化**：为**常用查询字段**添加索引（如会话表的 `session_id`、消息表的 `session_id + timestamp`），加速查询。
- **连接池**：使用**数据库连接池**（如 SQLAlchemy 的连接池），复用连接，避免频繁创建连接。
- **查询优化**：优化 SQL 查询（如避免全表扫描、使用 LIMIT 限制结果数、避免 N+1 查询）。

### 2. LLM 调用优化

- **批处理**：将**多个请求合并**成一批调用 LLM（如 LangChain 的 `batch`），减少 API 调用次数。
- **流式响应**：使用**流式响应**（如 `stream=True`），逐 token 返回，提升用户体验（用户不需要等待全部生成完）。
- **模型选择**：根据任务复杂度选择**合适的模型**（如简单任务用 GPT-3.5，复杂任务用 GPT-4），平衡质量与成本。

### 3. 异步处理

- **含义**：对于**耗时操作**（如 LLM 调用、工具执行），使用异步处理（如 `asyncio`），不阻塞其他请求。
- **实现**：Gateway 与 Runtime 使用异步框架（如 FastAPI、aiohttp），LLM 调用与工具执行异步化。

### 4. 小结表

| 优化项       | 优化内容                 | 实现方式                         |
| ------------ | ------------------------ | -------------------------------- |
| **数据库优化** | 索引、连接池、查询优化   | 添加索引、使用连接池、优化 SQL  |
| **LLM 调用优化** | 批处理、流式响应、模型选择 | 批量调用、流式返回、选择合适的模型 |
| **异步处理** | 耗时操作异步化           | 使用异步框架（FastAPI、asyncio） |

## 四、实战中的实现

在 **`week15/105_code/production_platform_demo.py`** 中已实现完整示例：

- **缓存策略**：`ResponseCache` 以 `(user_id, message)` 的 hash 为 key、TTL 与 max_size 可配置；Gateway 在限流通过后先查缓存，命中则直接返回并打标 `cached: true`，未命中再执行 Runtime 并在返回前写入缓存。
- **限流**：`TokenBucketRateLimiter` 实现令牌桶（max_tokens、refill_per_sec），按 key（如 user_id）消耗令牌；Gateway 在请求入口检查 `rate_limiter.allow(user_id)`，不通过则返回 `rate_limit` 错误。
- **超时**：Gateway 构造函数接受 `request_timeout_sec`，可在后续用 `signal` 或线程包装 handle_request 实现请求级超时；当前 Demo 未强制中断 LLM 调用，可按需在 Runtime 层为 LLM 设置 timeout 参数。
- **扩展**：Redis 版缓存与限流、数据库连接池与索引、LLM 批处理与流式响应可在同一架构上替换或叠加实现。
