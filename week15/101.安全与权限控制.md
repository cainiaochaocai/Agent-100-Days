# 101. 安全与权限控制

Day 100 讲了评估与测试。本节讲**安全与权限控制**：**API 密钥管理**（密钥存储、轮换、访问控制）、**用户权限**（角色与权限模型、资源访问控制），以及**数据隔离与审计日志**（多租户数据隔离、操作审计、合规要求）。

## 一、API 密钥管理：密钥存储、轮换、访问控制

### 1. 密钥存储

- **含义**：API 密钥（如 OpenAI API key、数据库密码）需要**安全存储**，不能明文存储在代码或配置文件中。
- **方式**：
  - **环境变量**：密钥存储在环境变量中（如 `OPENAI_API_KEY`），代码读取环境变量。
  - **密钥管理服务**：使用专门的密钥管理服务（如 AWS Secrets Manager、HashiCorp Vault），代码从服务获取密钥。
  - **加密存储**：若必须存储在文件，应加密存储（如用加密工具加密配置文件）。
- **最佳实践**：**永远不要**将密钥提交到代码仓库（用 `.gitignore` 忽略配置文件）。

### 2. 密钥轮换

- **含义**：定期**更换 API 密钥**（如每 90 天），降低密钥泄露风险。
- **实现**：
  - **自动轮换**：密钥管理服务支持自动轮换（如 AWS Secrets Manager）。
  - **手动轮换**：管理员手动更新密钥，系统支持“新旧密钥并存期”（过渡期）。
- **作用**：即使密钥泄露，定期轮换可以限制影响范围。

### 3. 访问控制

- **含义**：控制**谁可以访问哪些密钥**（如只有管理员可以访问生产环境的 API 密钥）。
- **实现**：
  - **角色权限**：不同角色（管理员、开发者、只读用户）有不同的密钥访问权限。
  - **密钥范围**：密钥可以标记“用途范围”（如“仅用于开发环境”“仅用于特定 Agent”），限制使用范围。

### 4. 小结表

| 内容         | 含义                     | 实现方式                         |
| ------------ | ------------------------ | -------------------------------- |
| **密钥存储** | 安全存储 API 密钥        | 环境变量、密钥管理服务、加密存储 |
| **密钥轮换** | 定期更换密钥             | 自动轮换或手动轮换               |
| **访问控制** | 控制密钥访问权限         | 角色权限、密钥范围               |

## 二、用户权限：角色与权限模型、资源访问控制

### 1. 角色与权限模型

- **角色**：定义不同的**用户角色**（如管理员、开发者、普通用户、只读用户）。
- **权限**：定义不同的**权限**（如“创建 Agent”“删除 Agent”“查看日志”“执行查询”）。
- **模型**：
  - **RBAC（基于角色的访问控制）**：用户分配角色，角色有权限，用户继承角色的权限。
  - **ABAC（基于属性的访问控制）**：权限基于用户属性（如部门、项目）动态决定。
- **实现**：可以用数据库表存储角色与权限关系，Gateway 在请求时检查用户权限。

### 2. 资源访问控制

- **含义**：控制用户**可以访问哪些资源**（如哪些 Agent、哪些数据表、哪些通道）。
- **实现**：
  - **资源白名单**：用户只能访问白名单中的资源（如用户 A 只能访问 `chatbi_agent`，不能访问 `deep_research_agent`）。
  - **资源级权限**：资源可以设置“所有者”“协作者”“只读用户”，不同角色有不同的操作权限。
- **示例**：ChatBI Agent 中，用户只能查询自己部门的数据（行级权限，Day 96）。

### 3. 权限检查

- **位置**：在 Gateway 的 `handle_request` 中检查用户权限。
- **流程**：
  1. 获取用户信息（从请求中提取 user_id）。
  2. 查询用户角色与权限（从数据库或缓存）。
  3. 检查权限（如用户是否有权限访问目标 Agent、是否有权限执行该操作）。
  4. 若权限不足，返回错误（如 `403 Forbidden`）。

### 4. 小结表

| 内容         | 含义                     | 实现方式                         |
| ------------ | ------------------------ | -------------------------------- |
| **角色与权限模型** | RBAC 或 ABAC             | 数据库表存储角色与权限关系       |
| **资源访问控制** | 控制用户可以访问哪些资源 | 资源白名单、资源级权限           |
| **权限检查** | Gateway 中检查用户权限   | 查询用户权限 → 检查权限 → 拒绝或允许 |

## 三、数据隔离与审计日志：多租户数据隔离、操作审计、合规要求

### 1. 多租户数据隔离

- **含义**：不同租户（如不同公司、不同部门）的**数据完全隔离**，不能互相访问。
- **实现**：
  - **数据隔离**：数据库层面隔离（如每个租户有独立的数据库或 schema），或应用层面隔离（查询时自动添加租户过滤条件）。
  - **会话隔离**：不同租户的会话隔离（如会话 ID 包含租户标识）。
  - **资源隔离**：不同租户的 Agent、工具、记忆隔离。
- **作用**：保证数据安全，符合合规要求（如 GDPR、SOC 2）。

### 2. 操作审计

- **含义**：记录**所有敏感操作**（如创建 Agent、删除数据、修改权限），供后续审计。
- **记录内容**：
  - 操作类型（create、delete、update）
  - 操作对象（Agent ID、资源 ID）
  - 操作者（用户 ID、角色）
  - 操作时间
  - 操作结果（成功/失败）
  - 操作详情（参数、结果）
- **存储**：审计日志存储在**不可篡改**的存储中（如数据库的审计表、日志文件、专门的审计系统）。

### 3. 合规要求

- **GDPR**：欧盟数据保护法规，要求数据主体有权访问、删除、更正个人数据。
- **SOC 2**：安全审计标准，要求有访问控制、数据加密、审计日志。
- **实现**：
  - **数据访问**：用户有权查询自己的数据（如会话历史、工具调用记录）。
  - **数据删除**：用户有权删除自己的数据（如删除会话、删除记忆）。
  - **审计日志**：记录所有数据访问与操作，供审计。

### 4. 小结表

| 内容         | 含义                     | 实现方式                         |
| ------------ | ------------------------ | -------------------------------- |
| **多租户数据隔离** | 不同租户的数据完全隔离   | 数据库隔离或应用层隔离           |
| **操作审计** | 记录所有敏感操作         | 审计日志表或专门的审计系统       |
| **合规要求** | GDPR、SOC 2 等合规要求  | 数据访问、删除、审计日志         |

## 四、实战中的实现

在 **`week15/105_code/production_platform_demo.py`** 中已实现完整示例：

- **API 密钥管理**：通过 `os.getenv("OPENAI_API_KEY")` 从环境变量读取，未配置时启动失败并提示，密钥不落代码与仓库。
- **用户权限（RBAC）**：`USER_ALLOWED_AGENTS` 配置用户可访问的 Agent 白名单（如 `admin` 全部、`analyst` 仅 general+chatbi、`researcher` 仅 general+deep_research）；`check_agent_access(user_id, agent_id)` 在 Gateway 中于路由之后、执行之前校验，无权限则返回 `forbidden` 并写入审计。
- **审计日志**：`AuditLog` 类记录每次请求的 `user_id`、`action`（如 chat）、`agent_id`、`session_id`、`trace_id`，支持 `recent(n)` 查询；Gateway 在请求完成与权限拒绝时均调用 `audit_log.log()`。
