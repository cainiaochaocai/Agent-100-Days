# 68. 任务分解的失败模式与修复

Day 65–67 讲了线性、树状、并行与汇合三种分解策略。本节集中梳理**任务分解的常见失败**（分解过粗/过细、漏子任务、依赖错序、重复执行、汇合冲突）以及**修复策略**（重分解、插入校验与重试、显式依赖与执行顺序、去重与合并规则），并与实战脚本中的处理方式对应。

## 一、常见失败：分解过粗/过细、漏子任务、依赖错序、重复执行、汇合冲突

### 1. 分解过粗

- **表现**：子任务仍然是一个“大意图”，无法对应到单次工具调用或单轮可完成的动作，执行时模型又要在内部“再想一步”，容易混乱或漏步。
- **例**：“准备出差”只拆成一步，没有细化为订票、订酒店等。
- **修复**：重分解时要求“每步对应一个可调用的能力或一次明确决策”；或设定最小粒度（如至少拆成 N 步）。

### 2. 分解过细

- **表现**：子任务过多，步数膨胀，延迟与成本高；且中间某步失败概率增大，整体脆弱。
- **例**：把“查三地天气”拆成 10 步（每步只查一个城市的一个字段）。
- **修复**：合并可一次完成的子任务；或设定最大步数上限，超过则合并最后几步。

### 3. 漏子任务

- **表现**：分解结果中**漏掉**用户目标里的某一块，最终汇总时缺少关键信息。
- **例**：用户要“天气 + 订单 + 总结”，分解只得到 [天气, 总结]，漏了订单。
- **修复**：分解后用 checklist 或规则校验“用户目标中的关键动词/实体是否都有对应子任务”；漏了则重分解或补一步。

### 4. 依赖错序

- **表现**：本应先 A 再 B，却先执行了 B，导致 B 缺少输入或结果错误。
- **例**：先“总结”再“查天气”，总结时没有天气数据。
- **修复**：显式依赖与执行顺序（见下）；分解时让模型输出顺序或依赖关系，执行器按拓扑序或固定顺序执行。

### 5. 重复执行

- **表现**：同一子任务被执行多次（如重复查同一订单），浪费步数与成本。
- **例**：分解结果中有两条“查订单 ORD001”，或执行阶段未去重。
- **修复**：分解后对子任务列表去重（相同描述或相同语义合并为一步）；或执行时用“已完成的子任务集合”做幂等判断。

### 6. 汇合冲突

- **表现**：多路结果在汇合时**冲突**（如同一字段多个值）或**重复**（多段文字重复同一信息），最终回复质量差。
- **例**：两个分支都查了同一订单，汇总时出现两次相同内容。
- **修复**：定义去重与合并规则（按 key 合并、或“以第一次出现为准”）；汇合前做简单规范化或摘要。

### 7. 小结表

| 失败类型     | 表现                 | 修复方向                    |
| ------------ | -------------------- | --------------------------- |
| **分解过粗** | 子任务仍不可直接执行 | 重分解、设定最小粒度        |
| **分解过细** | 步数爆炸、成本高     | 合并子任务、最大步数上限    |
| **漏子任务** | 汇总缺关键信息       | checklist、重分解或补步     |
| **依赖错序** | 先执行了依赖方       | 显式依赖、按拓扑序/顺序执行 |
| **重复执行** | 同一子任务多次执行   | 去重、幂等判断              |
| **汇合冲突** | 重复或冲突内容       | 去重与合并规则、按 key 合并 |

## 二、修复策略：重分解、插入校验与重试、显式依赖与执行顺序、去重与合并规则

### 1. 重分解

- 当检测到“分解过粗、漏子任务或明显不合理”时，可**再次调用分解模块**（如 LLM），输入“当前分解结果 + 失败原因或用户目标”，要求输出新的子任务列表。
- 可设**重分解次数上限**，避免无限循环。

### 2. 插入校验与重试

- **校验**：每步执行完后简单校验（如工具是否返回错误、是否为空）；若失败则触发重试或反思（Week 9）。
- **重试**：对单步失败可重试 1 ～ 2 次；仍失败则标记该步失败，汇总时说明“某步未完成”或进入降级策略。

### 3. 显式依赖与执行顺序

- 分解时不仅输出“子任务列表”，还可输出**顺序**或**依赖关系**（如“步骤 3 依赖 1、2”）；执行器按**拓扑序**或**固定顺序**执行，保证不会错序。
- 线性场景下用列表顺序即可；树状/并行场景用 DAG 或“可并行组 + 汇合点”描述。

### 4. 去重与合并规则

- **子任务去重**：分解后对语义相同或描述相同的项合并。
- **结果合并**：汇合时按“主题/key”去重，或规定“同一 key 只保留第一次/最新一次”；必要时用 LLM 做“去重与归纳”的汇总。

## 三、实战中的对应

在 **`week10/69_code/task_decomposition_agent_demo.py`** 中：

- **分解**：由 LLM 生成子任务列表，prompt 中要求“每步可单独执行、不要漏掉用户目标中的关键动作”，对应“避免过粗与漏子任务”。
- **执行顺序**：按列表顺序线性执行，每步传入前序结果，对应“显式顺序”。
