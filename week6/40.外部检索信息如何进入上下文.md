# 40. 外部检索信息如何进入上下文

在 RAG 或带检索的 Agent 里，**外部检索到的文档/段落**会作为“参考内容”注入到一次 LLM 调用的 Context 中。注入多少、以什么形式、放在什么位置，会直接影响答案质量和推理稳定性。本节围绕四块学习内容：**检索结果不是越多越好**、**分片与上下文的关系**、**检索结果放在什么位置最合理**、**为什么外部信息会“干扰推理”**。

## 一、检索结果不是越多越好

直觉上会认为“多塞几条检索结果，信息更全”；但在有限 context 内，**检索结果不是越多越好**。

### 1. Token 与噪音

- 每多一条检索结果，就多占一块 token。Top-K 越大（如 K=20），总长可能远超留给“参考内容”的预算，挤占 System、历史与当前问题的空间，或直接触发截断。
- 检索返回的条目**质量不均**：排名靠后的往往与当前问题关系较弱。全部塞进去会把**低相关、甚至无关**的段落一并交给模型，形成噪音，稀释真正相关的部分。

### 2. 边际收益递减

- 前几条（如 Top-3 ～ 5）通常已经覆盖了“最相关”的证据；再往后，多数是重复或弱相关，对“答对这道题”的边际贡献很小，却线性增加 token 与干扰。
- 因此：**在保证“关键证据不丢”的前提下，少而精通常优于多而杂。** 常见做法是：检索阶段取稍大的 K（如 20），经 **Rerank + 上下文压缩** 后只保留 Top-3 ～ 5 条再注入 Context。

### 3. 建议

- 为“参考内容”设** token 或条数上限**（如最多 5 条、或总长不超过 2000 token），避免无脑全塞。
- 优先保留 **Rerank 分数高、与当前问题明显相关** 的段落；低于某分数或明显无关的，宁可少给也不要堆上去。

**示例：塞 10 条 vs 只塞 Top-3，体感差在哪**

我们试过：用户问“差旅报销上限是多少？多久内要提交？”，检索取 K=10，10 条全塞进参考内容，约 3000+ token。结果模型回答泛泛总结“报销制度要求……”，**5000 元**和**30 日内**要么没提，要么藏在长段里不显眼。后来改成检索仍取 K=10，经 Rerank 后只保留分数最高的 3 条（约 900 token）再注入，同样的 System 和问题，模型回答里明确出现“上限 5000 元/年”“需在返回后 30 日内提交”。**少塞几条、把低相关的砍掉，关键证据反而更突出**，模型也更容易对准问题作答。建议给参考内容设个硬上限（如最多 5 条或 2000 token），避免“多就是好”的惯性。

## 二、分片与上下文的关系

RAG 中的“检索结果”通常来自**事先分好的文档块（chunk）**。这些**分片**与**上下文**的关系可以概括为：

### 1. 分片是上下文中的“一块”

- 每个 chunk 是文档的一个**片段**；注入 Context 时，每条检索结果就是**一段连续文本**。Context 里能放多少条，取决于：**单条平均长度 × 条数** 是否超过你留给“参考内容”的 token 预算。
- **Chunk 越大**：单条信息多，但单条占 token 多，能放的**条数**就少，覆盖的“文档范围”可能变窄。**Chunk 越小**：单条省 token，能放更多条，但单条可能缺上下文，且条数过多会回到“检索结果过多”的噪音问题。

### 2. 平衡点

- 在**分块策略**（如 Day 31）已定的前提下，注入上下文时要做的是：**在 token 预算内，优先放最相关的若干条，并保证每条在 Context 里是完整、可读的**（不截断到半句）。
- 若单条 chunk 很长，可考虑：只取**与问题最相关的子段**再注入（如用 Rerank 或关键词高亮截取），而不是整块照搬，以省 token 并减少无关句子的干扰。

### 3. 小结

> **分片决定了“检索粒度”和“单条长度”；上下文决定了“能装多少条、装哪些条”。** 两者要一起考虑：既不让单条过长占满预算，也不让条数过多导致噪音；用 Rerank + 条数/长度上限控制最终进入 Context 的分片。

**示例：参考内容预算固定时，chunk 大小怎么影响“能装几条”**

假设留给参考内容的 token 预算是 1500。若单条 chunk 平均约 250 token（约 500 字），最多能放 6 条，能覆盖的文档范围较广，但单条若被切得太碎，可能缺前半句或后半句。若单条 chunk 平均约 500 token（约 1000 字），最多放 3 条，单条更完整，但覆盖的“文档面”变窄，且某一条里可能只有一两句和当前问题直接相关，其余都是噪音。**折中做法**：chunk 按 Day 31 的策略切好后，注入时若某条特别长且只有中间几句贴题，就只取那几句作为“子段”注入，而不是整块照搬。例如某 chunk 共 800 字，其中“差旅报销每人每年上限 5000 元，需在返回后 30 日内提交 OA”这两句是答案，就只把这两句连同来源标注放进 Context，既省 token 又减少无关句子的干扰。

## 三、检索结果放在什么位置最合理

在**同一次调用**里，检索结果与 System、历史、当前问题的**相对顺序**会影响模型行为（Day 37 已说明顺序的重要性）。下面给出更针对“外部检索信息”的放置建议。

### 1. 推荐结构

- **System** 放在最前（角色、规则、输出格式）。
- **对话历史**（若有）按时间顺序排在中间。
- **检索结果**作为“参考内容”放在**当前用户问题之前**、**历史之后**，即：模型先看到历史，再看到“为这一轮准备的参考内容”，最后看到“当前问题”。
- **当前用户问题**放在**最后**（或紧接在参考内容之后），作为本次生成的“锚点”。

这样做的原因：

- 模型对**靠后**内容更敏感，把**当前问题**放在最后，便于模型以问题为锚点生成，并优先从紧挨着问题的“参考内容”里找依据。
- 检索结果集中在**一块**、且位于**当前问题之前**，既避免被大段历史“夹在中间”稀释，又避免把问题埋在长文档后面导致模型“看不到问题”。

### 2. 若检索结果很多

- 把**最相关的 1 ～ 2 条**放在**最靠近当前问题**的位置（参考内容块的末尾），其余按相关度或顺序排在前；这样高相关证据在注意力上更占优。
- 或对参考内容做**摘要/压缩**后再放，控制总长，避免中间一大坨长文稀释问题与高相关段。

### 3. 小结

> **检索结果放在“当前问题之前”、并尽量让最相关段落靠近当前问题**，是较稳妥的放置方式；同时控制参考内容的总条数与总长，避免占满或冲淡 Context。

**示例：参考内容块“内部顺序”也会影响答案**

同样是 3 条检索结果 + 用户问题“报销上限和提交期限是多少”。**做法 A**：3 条按检索顺序排（可能第 1 条讲流程、第 2 条讲上限、第 3 条讲期限），用户问题放在最后。**做法 B**：把 Rerank 分数最高、直接写“5000 元”和“30 日内”的那一条放在**参考内容的最后一条**，紧挨用户问题，其余两条在前。我们对比过：做法 B 下模型更容易在首句就给出“上限 5000 元，30 日内提交”，且引用对；做法 A 下有时会先复述流程再说到数字，或偶尔漏掉“30 日”。所以**参考内容内部也要排个序**：最相关、最贴题的那 1 ～ 2 条放在块末尾，紧挨【用户问题】，效果更稳。

## 四、为什么外部信息会“干扰推理”

即便检索结果与当前问题相关，**外部信息**仍可能对推理产生干扰，主要体现在以下几类。

### 1. 内容冲突

- 不同来源或不同 chunk 之间可能**说法不一致**（如不同版本的文档、不同章节的矛盾描述）。模型若同时看到多条冲突信息，可能混淆、折中或随机选一条，导致答案不一致或错误。
- **应对**：尽量保证注入的几条**来源一致或已做冲突检测**；或在 System 中要求“若参考内容有冲突，以某来源/某时间为准”或“指出存在冲突并分别说明”。

### 2. 无关或弱相关段落被“误用”

- 检索可能带回**表面相关、实则不答本题**的段落（如同词不同义）。模型有时会**错误引用**这些段落作答，看起来“有据可查”，实则答非所问。
- **应对**：用 Rerank 和分数阈值过滤低相关块；在 Prompt 中要求“仅依据与问题直接相关的句子作答，无关段落可忽略”。

### 3. 权威/新近偏好

- 模型可能对**某位置或某类表述**更敏感（如更信“最后一条”或“带数字的那条”），从而忽略更准确但位置或表述不占优的段落。
- **应对**：把**最相关、最权威**的 1 ～ 2 条放在更靠后的位置（紧挨当前问题）；或对关键证据做简短强调（如“以下为最相关依据：……”）。

### 4. 长度与注意力稀释

- 参考内容**过长**时，模型注意力被摊薄，真正关键的一两句容易被忽略，推理会偏向“印象”而非“精确依据”。
- **应对**：控制注入条数与总长；对长 chunk 只取**与问题最相关的子段**；或先摘要再注入，保留要点即可。

概括一下：

> **外部信息会通过“冲突、误引用、位置偏好、长度稀释”等方式干扰推理。** 通过控制数量、顺序、相关度过滤和冲突处理，可以减轻这些干扰。

**示例：四类干扰在真实对话里长什么样**

- **内容冲突**：知识库里既有《报销制度 2023 版》（写 5000 元/年），也有《报销制度 2024 版》（写 6000 元/年），两条都被检索进来一起注入。用户问“今年报销上限多少”，模型同时看到 5000 和 6000，可能答“约 5000 ～ 6000”或随机选一个，而不是“以最新版为准 6000”。应对：注入前尽量保证同一问题只保留同一版本，或在 System 里写“若参考内容有冲突，以日期最新/某来源为准”。

- **无关段落被误用**：用户问“报销**上限**是多少”，检索带回了“报销**流程**”段落（里面有大段“登录 OA、填写表单、提交审批……”），因为都含“报销”向量相似。模型有时会照着流程答一通，最后才带一句“具体上限见制度”，甚至漏掉 5000。应对：用 Rerank 和分数阈值把“流程”这类弱相关条压下去；Prompt 里写“仅依据与问题直接相关的句子作答”。

- **长度稀释**：参考内容塞了 5 条长段落，总共 2500 token，其中“需在返回后 30 日内提交”这句藏在第 3 条中间。模型注意力被摊薄，回答里只说了“需尽快提交”“按制度办理”，**30 日**没出现。应对：控制条数和总长；或对长 chunk 只取与问题最相关的子句再注入，让关键句更显眼。

- **位置/权威偏好**：写“5000”的那条排在第 1 条，写“6000（2024 版）”的那条排在第 5 条、紧挨用户问题。部分模型更“信”靠后的内容，可能直接答 6000 而忽略 5000；或反过来更信“第一条”。应对：把**最权威、最相关**的一条（如最新版的关键句）放在参考内容块**末尾**，紧挨问题，并在 System 里约定“以参考内容中最新/指定来源为准”。

## 五、基于文件系统的上下文工程

在真实项目里，很常见的一类外部信息其实是：**本地文件系统里的内容**，比如：

- 项目里的 `README`、`docs/`、`AGENTS.md`、`skills/` 目录；
- 业务规则放在一堆 Markdown / YAML 里；
- 代码本身（比如想让助手“读配置、看路由”）。

这些内容本质上也是“外部检索信息”，只是数据源从“向量库/搜索引擎”换成了“文件系统”。要让它们进上下文，思路可以照搬本节：**先选片段，再控长度，再决定放哪儿**。

### 1. 固定文件：按需直接注入

最简单的一类，是**固定几份文件几乎每次都要参考**，比如：

- 某个 Agent 的 `SKILL.md`；
- 团队约定写在 `AGENTS.md` 里；
- 某模块使用说明 `docs/feature-x.md`。

做法很直接：

1. 启动时或第一次用到时，把这些文件读出来（必要时做简单分块或摘要）；\n2. 当某类请求触发时，把相应片段作为「【参考内容】」注入到本轮 Context 里，放在用户问题前面。

示例：

```python
from pathlib import Path

BASE = Path(__file__).resolve().parent.parent  # 项目根目录

def load_skill_doc() -> str:
    text = (BASE / "skills" / "my-skill" / "SKILL.md").read_text(encoding="utf-8")
    # 如有需要可只取开头说明部分，或做一次摘要
    return text
```

之后在构造本轮 `HumanMessage` 时，把这段文字拼进【参考内容】，就和 RAG 的“检索结果”一模一样，只是检索步骤从“向量库”换成了“按路径直读文件”。

### 2. 动态文件检索：把文件系统当「简单向量库」

再复杂一点，是**根据用户问题，动态在文件系统里找相关内容**。不一定非得上向量库，可以先用关键词/路径/正则做一版轻量级检索：

- 根据路径/文件名筛选：只在 `docs/`、`specs/`、`skills/` 里找；
- 用关键词匹配：简单用 `rg` / Python 正则找含某些词的段落；
- 若项目已接了 Embedding/向量库，也可以把文件内容定期同步到向量库再按正常 RAG 流程来。

无论你怎么「查文件」，**一旦选出了若干段文本**（例如某个 `AGENTS.md` 里的一个章节、某个 `config.md` 的一小段），就可以把它们当成 RAG 的 chunk 一样处理：

- 根据长度和相关度，选 Top-3 ～ 5 段；
- 控制总 token 不超过预留预算（比如 1000 ～ 1500）；
- 拼成「【参考内容】\n…」注入到当前轮的 user 消息前面。

这就是「基于文件系统的上下文工程」：**你只是多了一层「从哪里读、怎么筛选」的逻辑，进 Context 的形态还是那几段参考文本**。

### 3. 仍然要遵守前面几节的原则

无论外部信息来自文件系统还是远程检索接口，一旦进了 Context，它就受同样的约束：

- **数量与长度**：不要把整个仓库的文件都塞进一轮请求里；照样要设条数和 token 上限，必要时做摘要或结构化摘要（Day 39）。
- **位置**：文件片段一旦当成“参考内容”，仍建议放在**当前问题之前**，并让最相关那几条靠近问题（Day 37、40）。
- **冲突与干扰**：不同版本的文档、旧 README 与新规范冲突时，照样会让模型纠结，需在注入逻辑或 System 里约定「以哪个为准」（本节前半部分）。

可以简单记一句：**「文件系统」只是外部信息的一个来源，进 Context 之后，该遵守的上下文工程规则一条都不能少。**

## 小结

| 学习点                         | 要点                                                                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **检索结果不是越多越好**       | 多则占 token、引入噪音、边际收益递减；建议设条数/长度上限，经 Rerank 与压缩后只保留 Top-3 ～ 5 条高相关结果再注入。                      |
| **分片与上下文的关系**         | 分片决定单条长度与检索粒度；上下文决定能装多少条、装哪些条；需在 token 预算内平衡条数与单条长度，优先最相关、必要时做子段截取。          |
| **检索结果放在什么位置最合理** | 放在**当前问题之前**，最相关 1 ～ 2 条**靠近当前问题**；System 最前，历史居中，参考内容 + 当前问题靠后，避免参考内容被夹在长段中间稀释。 |
| **为什么外部信息会干扰推理**   | 冲突信息、无关段落被误引用、权威/位置偏好、过长导致注意力稀释；可通过过滤、条数控制、顺序设计和冲突规则减轻。                            |
