# 39. 上下文裁剪与压缩策略

上一节说明了多轮对话的线性膨胀、不能全塞的原因、历史的真实价值以及常见失败模式。本节落到**具体策略**：如何对历史（以及必要时对注入内容）做**裁剪与压缩**，在有限 token 内既保留连贯性又控制长度。围绕四块学习内容：**裁剪 vs 摘要 vs 重写**、**时间窗口策略**、**语义摘要策略**、**结构化摘要**。

## 一、裁剪 vs 摘要 vs 重写

对“过长的上下文”做瘦身，常见有三种思路：**裁剪（Trim）**、**摘要（Summarize）**、**重写（Rewrite）**。三者目标都是减 token，但手段和保留的信息形态不同。

| 方式                | 做法                                                                              | 优点                              | 缺点                                   | 适用场景                                         |
| ----------------- | ------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------ | -------------------------------------------- |
| **裁剪（Trim）**      | 直接**丢弃**一部分内容（如最早 N 轮、或超过某长度的前缀/后缀）。                                            | 实现简单、无额外调用、确定性地减 token。         | 被裁掉的内容**完全不可见**，若含关键前提或指代会丢失。        | 历史明显冗余、或确定“只保留最近 K 轮”就够用时。                   |
| **摘要（Summarize）** | 用 LLM（或规则）把一段内容**压缩成更短的概括**，用摘要替代原文进 Context。                                   | 保留“说了什么”的梗概，信息密度高；远期历史可压成几句话说清。 | 需要额外 LLM 调用与成本；摘要会丢失细节，不适合必须逐字参照的内容。 | 较早的历史、大段检索结果、长工具输出等，需要“知道有这回事”但不必全文保留时。      |
| **重写（Rewrite）**   | 不简单删或压，而是**重新组织**：如把多轮合并成一条“会话要点”、或把 user/assistant 对改写成“用户问了 X，助手答了 Y”的第三人称叙述。 | 可兼顾连贯与压缩，有时比纯裁或纯摘要更易读。          | 实现复杂、通常也依赖 LLM，有成本和延迟。               | 希望保留“谁说了什么”的结构、又不想占满 token 时；或做“会话状态”的定期快照时。 |

实践中常**组合使用**：

- **时间窗口**内：保留最近几轮**原文**（不裁、不摘）。
- 超出窗口的**更早历史**：先做**摘要**（或**结构化摘要**），再与最近几轮一起拼成 Context；若总长仍超限，再对“最早的一段摘要”或最早几轮做**裁剪**。

这样既避免“全塞”，又避免“只留当前一句”导致指代丢失，下一小节起分别说明时间窗口、语义摘要和结构化摘要的具体做法。

**示例：同一段历史，三种方式分别会变成什么样**

假设已有 8 轮对话，当前是第 9 轮，总历史约 2800 token，你只想给历史留 1000 token 预算：

- **纯裁剪**：只保留最近 3 轮（约 1050 token），第 1 ～ 6 轮整段删掉。实现快，但若用户在第 2 轮说过“不要用英文”，第 9 轮模型就看不到了，可能又用英文答。
- **摘要**：把第 1 ～ 6 轮拼成一段交给 LLM，得到类似：“用户先问了报销上限（助手答 5000/年、30 日内提交），又问了住宿标准（助手答 300/晚），用户要求回答简洁。”约 80 token，再拼上第 7、8 轮原文（约 700），一共约 780，还在预算内，且“用户要求简洁”这种约束还在摘要里。
- **重写**：把第 1 ～ 6 轮改写成几条第三人称句，如“用户问报销上限 → 助手答 5000、30 日；用户问住宿标准 → 助手答 300/晚；用户提出简洁回答。”再与第 7、8 轮原文拼接。比摘要更保留“谁说了什么”的结构，但实现和调参成本更高。

实际落地时，多数会采用**窗口内原文 + 窗口外摘要**：例如最近 3 轮原文保留，第 1 ～ 6 轮用上面那段摘要替代，这样既有指代（最近 3 轮），又有前情和约束（摘要），还省 token。

## 二、时间窗口策略

**时间窗口策略**的含义是：只保留**最近一段时间或最近若干轮**的完整内容，更早的一律不进入 Context（或先压成摘要再进）。实现简单、可预测，是多数多轮对话的基线策略。

### 1. 按轮数：保留最近 K 轮

- **做法**：只把**最近 K 轮**的 user/assistant 对放进 Context（如 K=3、5、10），更早的整轮丢弃或单独做摘要。
- **优点**：不依赖时间戳，实现容易；轮数固定，token 上界可估。
- **注意**：若某轮特别长（如用户贴了大段文档），单轮就可能占很多 token，需配合单条长度上限或截断。

### 2. 按 token 数：保留最近 N token

- **做法**：从**当前轮往前**数，累计 user+assistant 的 token 数，直到总历史 token 达到上限 N（如 2000、4000），更早的丢弃或摘要。
- **优点**：总历史长度受控，便于为 System、当前输入、RAG 预留空间。
- **注意**：可能在某轮中间“截断”，导致该轮不完整；通常按**整轮**为单位裁（裁到“再往前一轮就超 N”为止），避免半轮截断。

### 3. 按时间：保留最近 T 分钟/小时

- **做法**：若每条消息有时间戳，只保留**最近 T 时间内**的对话，更早的丢弃或摘要。
- **适用**：对“会话时效”有要求的场景（如客服只关心本小时内）；若对话稀疏，可能实际保留轮数很少。

**小结**：时间窗口策略的核心是**划定“完整保留”的边界**，边界外的交给“不保留”或“摘要/结构化后再保留”。通常用**按轮数**或**按 token 数**即可，按时间可作为补充条件。

**示例：按轮数 vs 按 token 数，各会得到什么**

**按轮数 K=3**：到第 5 轮时，请求里的历史只包含第 3、4、5 轮的 user/assistant（第 1、2 轮不进入 Context）。实现时就是“取 messages 末尾 3 对”，逻辑简单；但若第 4 轮用户贴了一整份 PDF 原文，单轮就 2000 token，3 轮加起来可能爆掉你的历史预算，这时要再加一层“单轮最大长度”或截断。

**按 token 数 N=2000**：从当前轮往前数，第 5 轮 400、第 4 轮 350、第 3 轮 400、第 2 轮 500、第 1 轮 400，累计到第 2 轮时已 2050，超过 2000，于是只保留第 3、4、5 轮（共 1150），第 1、2 轮整轮丢弃或交给摘要。这样总历史 token 稳定在 N 以内，便于给 System 和 RAG 留空间。注意按**整轮**裁，不要在第 2 轮中间切一刀，否则该轮不完整，指代容易乱。

## 三、语义摘要策略

**语义摘要**是指用 LLM（或摘要模型）把一段或多段对话（或长文档）**压缩成简短概括**，保留主要事实、结论和约束，用这段概括替代原文进入 Context，从而大幅减少 token。

### 1. 典型用法

- **对象**：超出“时间窗口”的**更早历史**、或某次注入的**长检索/长工具结果**。
- **方式**：将待压缩内容拼成一段文本，用固定 Prompt 调用 LLM，例如：“请将以下对话压缩成 3 ～ 5 句话的摘要，保留：用户主要问题、助手的关键结论、用户明确提出的约束或偏好。”
- **结果**：用返回的摘要替代原文，放入 Context；后续轮次只看到摘要，看不到逐字内容。

### 2. 何时做摘要

- **滑动摘要**：每轮或每 K 轮结束后，对“当前窗口外的历史”做一次摘要，下一轮把**摘要 + 窗口内原文**作为历史。
- **按需摘要**：当检测到“总 token 快超限”时，对最早的一段历史做摘要，再裁掉原文、只留摘要。

### 3. 注意点

- 摘要会**丢失细节**，不适合“必须逐字引用”的内容；适合“知道发生过什么、有什么结论”即可的远期历史。
- Prompt 里最好明确**要保留的要素**（如：关键数字、用户明确说不要/要的、已达成的一致），减少摘要丢关键信息。
- 摘要本身也占 token，若历史极长，可做**分层摘要**：最早一段 → 摘要 A，稍近一段 → 摘要 B，再与最近几轮原文拼接。

**示例：一段 5 轮对话，摘要前 vs 摘要后**

**原文（节选，约 600 token）**：用户问报销上限 → 助手答 5000/年、30 日内提交；用户问住宿标准 → 助手答 300/晚、需发票；用户说“后面用简洁的话”；用户问海外出差是否一样 → 助手答需单独申请；用户问“那刚才说的 30 日呢”。

**摘要后（约 120 token）**：“用户问了差旅报销上限（5000/年、30 日内提交）和住宿标准（300/晚）；用户要求后续回答简洁；又问了海外出差（需单独申请）并追问 30 日是否适用海外。助手已逐一回答。”后续轮次只把这段摘要放进 Context，模型能知道“前面聊过什么、用户要简洁、30 日指的是提交期限”，但看不到逐字原文。若你在摘要 Prompt 里写了“保留用户明确要求（如简洁）和关键数字”，这类信息就不容易丢。**做滑动摘要时**，可以在每 5 轮后对“当前窗口外的部分”跑一次上述摘要，下一轮用「摘要 + 最近 5 轮原文」作为历史，既控长又保留前情。

## 四、结构化摘要

**结构化摘要**不产出大段自然语言，而是把历史（或长文档）中的**关键信息抽成结构化形式**：如键值对、列表、简短条目，便于模型快速扫描且省 token。

### 1. 形式示例

- **要点列表**：如“用户要求：不要用英文；已讨论方案：A、B；用户选定：B。”
- **键值/表格**：如 `{ "报销上限": "5000", "提交期限": "30日" }` 或类似简表。
- **会话状态快照**：如“当前话题：报销流程；待澄清：是否含海外；用户偏好：简洁回答。”

### 2. 做法

- 用 LLM 按固定模板抽取：例如“从以下对话中提取：1) 用户明确要求 2) 已给出的关键数字或事实 3) 当前未决问题。用简短条目列出。”
- 或结合规则：从 assistant 中抽“结论句”、从 user 中抽“问句关键词”，再拼成几条短句。

### 3. 与语义摘要的对比

| 维度    | 语义摘要       | 结构化摘要             |
| ----- | ---------- | ----------------- |
| 输出形态  | 一段连贯的短文本   | 列表、键值、条目          |
| 可读性   | 更接近自然语言    | 更偏“数据”，便于程序与模型解析  |
| 适用    | 需要“故事线”的概括 | 需要“事实/约束/状态”的快速检索 |
| Token | 中等         | 通常更短、更紧凑          |

两者可并存：**远期历史**先做语义摘要得到“发生了什么”，再从中**抽一层结构化摘要**（关键数字、约束、决定），一起放入 Context；最近几轮仍保留原文。这样模型既能看到“前情提要”，又能快速抓住关键约束与事实。

**示例：同一段对话，语义摘要 vs 结构化摘要**

沿用上面“报销 + 住宿 + 简洁 + 海外”的那段对话：

- **语义摘要**（一段话）：用户问了差旅报销上限（5000/年、30 日内提交）和住宿标准（300/晚）；用户要求后续回答简洁；又问了海外出差（需单独申请）并追问 30 日是否适用海外。助手已逐一回答。
- **结构化摘要**（要点/快照）：
  - 关键事实：报销上限 5000/年、提交 30 日内、住宿 300/晚、海外需单独申请。
  - 用户约束：回答要简洁。
  - 当前话题：30 日是否适用海外（待助手明确）。

同一批信息，语义摘要适合“让模型读一段前情”；结构化摘要适合“让模型快速扫到数字和约束”，且通常更省 token。实践中可以**先做语义摘要，再让 LLM 从摘要里抽成上面这种条目**，两条一起放进 Context，最近几轮仍保留原文，模型既有故事线又有可检索的要点。



## 小结

| 学习点                | 要点                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------- |
| **裁剪 vs 摘要 vs 重写** | **裁剪**直接丢弃，简单但易丢关键信息；**摘要**用 LLM 压成短概括，保留梗概；**重写**重新组织多轮为要点或叙述。实践中常组合：窗口内保留原文，窗口外摘要或结构化后再保留。 |
| **时间窗口策略**         | 只保留最近 K 轮 / 最近 N token / 最近 T 时间；实现简单，是基线策略；窗口外内容可丢弃或交摘要/结构化处理。                              |
| **语义摘要策略**         | 用 LLM 把远期历史或长内容压成几句话，保留主要事实与约束；可滑动或按需执行；注意明确“要保留的要素”并控制摘要长度。                                 |
| **结构化摘要**          | 把历史抽成要点列表、键值、状态快照等，省 token 且便于模型抓取关键信息；可与语义摘要配合使用。                                           |
