# 38. 多轮对话与上下文增长问题

上一节讲了上下文的**组成、优先级和顺序**。在多轮对话里，每一轮都会往 Context 里追加新的 user 和 assistant 消息，于是**总 token 数随轮次线性增长**。若不加以控制，“全部塞进去”既不可行，也会损害推理质量。本节说明**多轮对话如何膨胀**、**为什么不能全塞**、**历史对当前推理的真实价值**，以及**常见失败模式**，为下一节的裁剪与压缩策略打基础。

## 一、多轮对话是如何线性膨胀的

多轮对话的典型形态是：每次用户发一条消息、模型回一条，下一轮请求时要把**之前所有轮**的 user/assistant 都放进 Context，模型才能“看到”完整对话。

因此：

- **第 1 轮**：Context ≈ System + 第 1 轮 user + 第 1 轮 assistant
- **第 2 轮**：Context ≈ System + 第 1 轮 user + 第 1 轮 assistant + 第 2 轮 user + 第 2 轮 assistant
- **第 N 轮**：Context ≈ System +（第 1 轮 user + assistant）+ … +（第 N 轮 user + assistant）

每多一轮，就**多出一轮 user + assistant 的 token**。若每轮平均 200 ～ 500 token，10 轮就是 2000 ～ 5000 token 仅用于历史，再算上 System、当前问题、RAG/工具等，总 Context 会很快逼近甚至超过模型的 context window。

可以粗略理解为：

> **总 token ≈ System + (每轮平均 token × 轮数) + 当前轮输入 + 注入内容（RAG/工具等）**

轮数线性增加，总 token 也**近似线性增加**。这就是多轮对话下上下文的**线性膨胀**。

**示例：用数字直观感受“线性膨胀”**

假设：System 固定 400 token，每轮 user+assistant 平均 350 token，当前轮用户输入 50 token，本轮没有 RAG。则：

| 轮次     | 历史 token（累计） | 总 Context（System + 历史 + 当前） |
| -------- | ------------------ | ---------------------------------- |
| 第 1 轮  | 350                | 400 + 350 + 50 = **800**           |
| 第 5 轮  | 1750               | 400 + 1750 + 50 = **2200**         |
| 第 10 轮 | 3500               | 400 + 3500 + 50 = **3950**         |
| 第 15 轮 | 5250               | 400 + 5250 + 50 = **5700**         |
| 第 20 轮 | 7000               | 400 + 7000 + 50 = **7450**         |

若模型 context window 是 **8K**，到第 20 轮仅“System + 历史 + 当前”就已接近上限；若本轮还有 RAG 检索结果（例如 2000 token），总长会直接超 8K。**体会**：轮数每增加一倍，历史部分大约也翻一倍，这就是“线性膨胀”；不做裁剪或压缩，长对话必然触顶。

## 二、为什么不能“全部塞进去”

即使“想把所有历史都保留”，也会遇到硬约束和效果问题，所以不能无脑全塞。

### 1. Token 窗口硬约束

模型的 context window 有上限（如 8K、32K、128K）。总 token 一旦超过，API 会报错或服务端从一端截断。轮次一多，历史很容易顶到上限，**不裁就塞不进去**。

### 2. 成本与延迟

输入 token 通常按量计费，历史越长，单次请求越贵。同时，序列越长，模型前向计算越慢，延迟上升。无限制保留全部历史，**成本与延迟都会线性甚至更差地增长**。

### 3. 有效信息被稀释

即使没超限，把几十轮对话都塞进去，**关键信息会淹没在长序列里**。模型对位置敏感，中间大段历史会分散注意力，当前问题和最近几轮的重要信息容易被“稀释”，导致答非所问或漏掉前提。

### 4. “越早”的历史价值往往越低

多数场景下，**当前轮主要依赖最近 1 ～ 3 轮**（指代消解、话题延续、刚说过的约束）。很早之前的轮次，对“这一轮该怎么答”的影响有限，却占用大量 token。全部保留等于用大量 token 换很少的边际收益。

因此：

> **不能也不该“全部塞进去”。** 必须在保留对话连贯性的前提下，对历史做**有选择的保留、裁剪或压缩**，把 token 预算留给当前问题、规则和高相关证据。

**示例：8K 窗口下“全塞”会怎样**

继续用上面的假设（每轮约 350 token，System 400，当前 50）。若每轮还注入 RAG 约 1500 token（例如 3 条检索结果），则第 10 轮时：历史 3500 + System 400 + 当前 50 + RAG 1500 = **5450**，仍在 8K 内；但第 15 轮：历史 5250 + 400 + 50 + 1500 = **7200**，已接近 8K，再往后就会超限。服务端通常从**最早**的历史截断，于是第 1、2 轮的内容模型再也看不到——若用户在第 1 轮说过“请用简洁回答”或“不要用英文”，后面轮次模型就可能“忘记”这些约束。**体会**：全塞的后果不仅是“可能报错”，更是“最早的重要信息被截掉”，导致行为违背用户之前的明确要求。

从**成本与延迟**角度：若输入按 token 计费，第 1 次请求约 800 token，第 10 次约 5450 token，单次请求成本约是第 1 次的 6 ～ 7 倍；序列变长，推理时间也会明显增加，用户体感延迟上升。**全塞**在窗口、成本、延迟上都会很快遇到瓶颈。

## 三、历史对话对当前推理的真实价值

要合理裁剪或压缩历史，需要先想清楚：**历史对当前推理的真实价值**主要体现在哪里。

| 价值类型               | 说明                                                                                   | 典型位置                                                               |
| ---------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **当前话题与指代**     | 用户说“那上面那个方案呢”“再详细说说”时，依赖前文才能知道“那个”指什么、“详细”指哪件事。 | 通常来自**最近 1 ～ 2 轮**。                                           |
| **已达成的一致与约束** | “按你刚才说的格式”“不要用英文”等，是前面轮次里用户或模型已经说过的要求。               | 多在**最近几轮**。                                                     |
| **长线事实与背景**     | 少数场景下，很早之前提到的公司名、时间、数字等会贯穿全程。                             | 分散在历史中，但**出现频率低**；可摘要为少量“会话要点”而不必保留全文。 |

概括一下：

- **近期几轮**：对理解“当前在聊什么、用户指的是什么、要遵守什么”**价值高**，应优先保留或至少保留摘要。
- **远期历史**：对“这一轮怎么答”的边际价值**递减**，更多是背景；可压缩成简短摘要、或只保留关键实体/结论，为 token 腾出空间。

所以“历史对当前推理的真实价值”**并不均匀**：越近的轮次权重越大，越远的越适合压缩或丢弃。裁剪与压缩策略（下一节）就是基于这一认识来设计“保留谁、怎么压、裁掉谁”的。

**示例：指代与约束为什么依赖“近期历史”**

**指代依赖**：第 1 轮用户问“介绍一下方案 A 和方案 B 的区别”，助手分别概括了 A、B；第 2 轮用户说“**那上面那个方案呢？能再详细说说吗**”。若第 2 轮请求里**没有第 1 轮**，模型就不知道“那个”指 A 还是 B，“详细说说”指哪一块，只能答非所问或要求用户重复。**近期 1 ～ 2 轮**正是提供这类指代信息的来源。

**约束依赖**：第 1 轮用户明确说“**后面请都用简洁的话回答**”；第 3 轮用户问了一个新问题。若为省 token 把第 1 轮裁掉，第 3 轮请求里模型看不到“简洁回答”的要求，可能用大段文字回答，违背用户早前设定。因此即使用“从旧到新”裁剪，也要注意**关键约束**是否在将被裁掉的轮次里；若在，需要把该约束摘要进 System 或保留在最近几轮中。

**体会**：历史的价值不是均匀的——“当前在聊什么、用户指的是什么、要遵守什么”大多集中在最近几轮；远期历史更多是背景，可用摘要替代全文。

## 四、常见失败模式

多轮对话里，若对上下文增长不加控制或控制不当，容易出现以下失败模式。

| 失败模式          | 原因                                                                   | 表现                                                                                   |
| ----------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **超长截断**      | 历史全塞，总 token 超限，服务端从一端（多为最早）截断。                | 模型看不到被截掉的内容，可能忘记早期约定、指代错误、或重复问过的问题。                 |
| **指代/话题丢失** | 为省 token 只保留“当前一条 user”，历史全删。                           | 用户说“那个方案”“再解释一下”时，模型不知道“那个”“一下”指什么，答非所问或要求用户重复。 |
| **旧话题干扰**    | 保留了很多轮但未做摘要，中间大段是已结束的旧话题。                     | 模型被旧内容干扰，混淆话题，或在回答里引用早已切换掉的上下文。                         |
| **关键前提被裁**  | 裁剪时按“从旧到新”删，但某条关键约束（如“不要用专业术语”）在较早轮次。 | 当前回答违背用户之前明确提出的要求。                                                   |
| **成本/延迟爆炸** | 无限制保留全量历史。                                                   | 单次请求 token 过多，成本高、延迟大，甚至超时。                                        |

避免这些失败，需要：

- **控制总长度**：不超 context window，并预留输出与 RAG/工具空间。
- **保留“最小必要历史”**：至少保留最近 1 ～ 2 轮完整或高保真摘要，保证指代与话题连贯。
- **对更早历史做压缩或摘要**：用简短“会话要点”“关键事实”替代大段原文，而不是要么全留要么全删。

这些就是下一节**上下文裁剪与压缩策略**要解决的具体问题。

**示例：两种失败模式的真实场景**

**超长截断**：用户在第 2 轮说“后面都用英文回答”，助手确认。之后又聊了 10 轮（报销、请假等），到第 12 轮时，请求里塞满了全部历史，总 token 超限，服务端把**最早几轮**截掉。模型再也看不到“用英文回答”这句，第 12 轮回复又变成中文，用户会感到“说好的规则怎么又变了”。对应表格中的“忘记早期约定”。

**指代/话题丢失**：用户第 1 轮问“公司差旅报销上限是多少？”助手答“5000 元/年”；第 2 轮用户只发了一句“**再解释一下**”。若为省 token 只把“再解释一下”发给模型、**不带第 1 轮**，模型不知道要解释的是“上限”“流程”还是“特批条件”，只能泛泛回应或说“请说明您想了解哪方面”。对应表格中的“答非所问或要求用户重复”。

**体会**：失败模式不是理论罗列，而是真实对话里会出现的现象；控制总长、保留最小必要历史、对更早历史做压缩，就是在避免这些具体问题。

## 小结

| 学习点                       | 要点                                                                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **多轮对话如何膨胀**         | 每轮追加 user + assistant，总 token 随轮次近似**线性增长**；公式可理解为 System + 每轮平均 token× 轮数 + 当前输入 + 注入内容。 |
| **为什么不能全部塞进去**     | 受 token 窗口限制、成本与延迟上升、长序列稀释关键信息、远期历史边际价值低；必须在保留连贯性的前提下做有选择的保留与压缩。      |
| **历史对当前推理的真实价值** | 近期 1 ～ 2 轮对指代、话题、约束价值高；远期更多是背景，可摘要或精简；越近的轮次权重越大。                                     |
| **常见失败模式**             | 超长截断、指代/话题丢失、旧话题干扰、关键前提被裁、成本/延迟爆炸；应对思路是控制总长、保留最小必要历史、对更早历史做压缩。     |
