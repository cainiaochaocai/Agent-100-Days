# 37. 上下文的组成结构

上一节说了 Context 就是**一次调用里模型能看到的全部输入**，而且受 token 上限卡着。真要动手做裁剪、压缩或拼 Prompt，还得先弄明白三件事：**一次调用里通常会塞进哪些东西**、**真不够用时先动谁、后动谁**、**顺序有没有讲究**。

## 一、一次调用里通常有哪些信息

做 Agent 或 RAG 时，一次请求里往往会带上这几类东西。不同框架对“角色”的命名可能不一样，但本质上都能对上号：

| 类别                      | 说明                                    | 典型形式                                    |
| ------------------------- | --------------------------------------- | ------------------------------------------- |
| **System Prompt**         | 角色、格式、规矩，一般每轮都一样        | 单独的 `system`，或塞在第一条 `user` 里     |
| **对话历史**              | 之前的几轮 user/assistant，让多轮能接上 | 交替的 user / assistant 消息                |
| **当前轮用户输入**        | 这一轮用户到底在问什么                  | 一条或几条 `user`                           |
| **注入的检索结果（RAG）** | 从知识库里捞出来的段落                  | 常拼成一条 user，比如【参考内容】+ 几段原文 |
| **工具调用与结果**        | 模型之前调了啥工具、返回了啥            | `tool` / `tool_result`，或塞在 assistant 里 |
| **其他**                  | 时间、用户 ID、会话 ID 等               | 一般写在 System 或某条 user 开头            |

单轮、没历史、也没调工具时，往往就三样：System、参考内容、用户问题。一旦变成多轮 + RAG + 工具，这几类会一起出现，顺序也要你自个儿排。**建议养成习惯**：每次拼请求前想一下，这一轮里每类有没有、大概占多少 token、摆在哪——后面做裁剪时才不会乱。

**一次 RAG 请求实际长什么样**

单轮 RAG 时，发出去的大致就是这样一坨：

```text
[system]
你是公司知识库助手。仅根据【参考内容】回答，无法从资料得出时请说明。

[user]
【参考内容】
[1] 来源：报销制度.pdf 第3页
差旅报销每人每年上限 5000 元，超出需特批……
[2] 来源：报销制度.pdf 第5页
报销需在返回后 30 日内提交 OA……

【用户问题】
公司差旅报销上限是多少？多久内要提交？
```

模型这一轮能看到的就这些，没有“上一轮”也没有“上次工具结果”。如果用户下一句问“那住宿标准呢？”，你得在**下一次请求**里重新带上 System、参考内容（或新检索的）、用户问题，还要不要带上一轮的对话，取决于你要不要模型理解“那”指啥——很多人踩的坑就是忘了把历史塞进去，模型就接不上话了。

**多轮 + 工具时多出来的是啥**

用户先问“北京明天天气”，模型调了天气接口拿到“晴，15 ～ 22℃”；用户再问“那上海呢？”。

第二次请求里，除了 System 和当前这句“那上海呢？”，你还得把第一轮的 user + assistant（里头的工具调用和结果）一起塞进去，模型才知道“上海”是在问天气。如果这一轮模型又调了工具，下一轮请求里你又得把这一轮的 tool 结果带上。**核心就是**：模型不会自动“记得”上一轮，你请求里没写的它都看不到，历史和工具结果都是你每次亲手塞进去的。

## 二、不同信息的优先级

token 不够用、必须砍东西的时候，**先动谁、后动谁**直接决定效果。常用的顺序是这样的：

| 优先级   | 信息类型                        | 建议                                                   |
| -------- | ------------------------------- | ------------------------------------------------------ |
| **最高** | 当前轮用户输入                  | 不能砍，砍了模型不知道要答啥                           |
| **高**   | System 里的核心规则             | 角色、禁止项、输出格式尽量留，可以写短一点，别整段删   |
| **高**   | 和当前问题强相关的检索/工具结果 | 最贴题的那几条留着，关系不大的裁掉或压成一句           |
| **中**   | 最近 1 ～ 2 轮对话              | 指代、话题连贯靠这个，留一点；再早的可以摘要或丢       |
| **较低** | 更早的对话历史                  | 对“这一轮怎么答”帮助不大，占地方多，优先裁             |
| **较低** | 无关或弱相关的检索/工具内容     | 和当前问题关系弱的，直接裁或一句带过，把空间留给有用的 |

说白了就是：**当前问题 > 核心规则和强相关证据 > 近期历史 > 更早的历史和杂项**。裁的时候按这个顺序来，先保住“当前问啥 + 规矩 + 关键证据”，再在剩的预算里放近期几轮，最后才考虑更早的历史或低相关段落。

**Token 吃紧时按优先级动手**

举个具体例子：context 上限 4000，你拼出来 System 500、历史 8 轮 2500、检索 5 条 1200、当前问题 200，一共 4400，超了。

那就按上面顺序来：当前问题 200 不动；System 从 500 压到 300 左右（角色和“仅据参考内容回答”留着，啰嗦的示例删掉）；检索 5 条里只留和“报销上限、提交期限”最相关的 2 条，大概 600 token，剩下 3 条要么删要么一句摘要；历史只留最近 2 轮（约 800），够接“那上海呢？”的指代就行，前面 6 轮整段删掉，或者压成一句“用户之前问了北京天气，助手已回复”。算下来 300 + 600 + 800 + 200 = 1900，还在预算内，该留的也都在。真还不够就继续压 System 或只留最近 1 轮。**这点在真正做裁剪时特别有用**：优先级表不是摆设，就是“必须砍时先动谁、后动谁”的实操顺序。

## 三、顺序是否重要

重要。很多模型对**谁在前谁在后**是有反应的，常见几种情况：

- 对**靠后**的内容更敏感，生成时更容易跟着“最后看到”的指令或事实走。
- 对**最前面**的一段（比如 System、第一条 user）权重高，适合放总则、角色、格式。
- **中间**如果塞了一大坨，注意力容易散，关键信息埋在中间容易被弱化。

所以拼 Context 时我们一般这样摆：

| 目标                     | 做法                                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 让模型记住角色和规矩     | System 或核心指令放**最前**                                                                                            |
| 让模型清楚“这一轮要答啥” | **当前用户问题**放**靠后**（比如在参考内容后面、或最后一条 user），方便以问题为锚点生成                                |
| 检索结果怎么摆           | 放在当前问题**前面**当参考内容；如果检索条数多，把最相关的一两条放在参考内容的**末尾**，离问题近一点，少被中间长段冲淡 |
| 历史                     | 按时间顺序（旧的在前，新的在后），裁的时候先裁最早的，保留最近几轮                                                     |

不同模型、不同 API 会有细微差别，但**顺序会影响到模型行为**这点基本通用。拼的时候有意识地把“最想让它遵守和参考”的东西放在有利位置（开头或紧挨当前问题），别把关键信息塞在长段中间或很早的历史里。

**顺序摆错会怎样**

如果把 5 条检索结果（三千来字）全堆在最前面，用户问题「公司差旅报销上限是多少？多久内要提交？」放在最后一行。结果模型生成时注意力更多在前面的长文档上，最后那句问题没被当成“本轮的答题锚点”，回答就泛泛总结一通，**上限 5000、30 日内**这种关键信息反而漏了。

如果改成 System 最前，接着【参考内容】（最相关的一两条放在参考内容的末尾），**最后**再跟【用户问题】。这样模型读到最后时，眼前是“问题 + 刚看过的相关段落”，更容易对着问题从参考里抽答案。**同一批信息，顺序换一下，效果会差一截**，所以“当前问题”和“最相关证据”尽量靠后、挨着放，会稳很多。

## 小结

- **一次调用里通常有啥**：System、对话历史、当前用户输入、RAG 检索结果、工具调用与结果、以及时间/用户等杂项；单轮可能只有其中几类。
- **优先级**：当前问题与核心规则最高，高相关检索/工具结果次之，近期历史再次，更早历史和低相关内容优先裁。
- **顺序**：模型对位置敏感，建议 System 靠前、当前问题靠后、高相关检索靠近问题，历史按时间序且裁的时候先裁最早的。
