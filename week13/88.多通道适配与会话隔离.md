## 一、多通道的会话管理：每个通道独立的会话 ID、会话状态隔离、跨通道共享（可选）

### 1. 会话 ID 的生成规则

- **独立会话**：每个通道的**每个用户**有独立的会话 ID，格式如 `{channel}_{user_id}_{timestamp}` 或 `{channel}_{user_id}_{session_index}`。
- **示例**：CLI 用户 `cli_user` 的会话 ID 为 `cli_cli_user_001`；Web 用户 `web_user_123` 的会话 ID 为 `web_web_user_123_001`。
- **作用**：不同通道的会话**完全隔离**，CLI 的对话历史不会影响 Web 的上下文。

### 2. 会话状态隔离

- **含义**：每个通道的会话状态（对话历史、当前 Agent、工具调用记录）**独立存储与查询**，不共享。
- **实现**：SessionManager 在存储会话时，用 `channel + user_id + session_id` 作为 key，不同通道的会话数据分开存储。
- **好处**：用户在不同通道（如 CLI 和 Web）可以有**不同的对话上下文**，不会互相干扰。

### 3. 跨通道共享（可选）

- **场景**：某些场景下，用户希望**跨通道共享会话**（如 CLI 开始对话，Web 继续对话）。
- **实现**：Gateway 支持“共享会话模式”，用户可以在不同通道使用**同一个会话 ID**，Gateway 根据会话 ID 而非通道标识加载会话。
- **限制**：共享会话需要用户**显式指定**（如传入共享的 session_id），默认仍是隔离的。

### 4. 小结表

| 模式         | 会话 ID 规则                     | 状态隔离 | 适用场景                 |
| ------------ | -------------------------------- | -------- | ------------------------ |
| **独立会话** | `{channel}_{user_id}_{index}`    | 完全隔离 | 默认模式，不同通道独立   |
| **共享会话** | 用户显式指定共享的 session_id   | 共享状态 | 跨通道继续对话           |

## 二、通道适配层：将不同通道的消息格式统一为平台内部格式

### 1. 平台内部格式

- **统一格式**：Gateway 内部使用统一的请求格式
  ```python
  {
      "user_id": str,
      "channel": str,  # "cli", "web", "telegram" 等
      "message": str,
      "session_id": str | None,
      "metadata": dict,  # 可选：时间戳、用户信息等
  }
  ```

### 2. 通道适配

- **CLI 适配**：CLIChannelPlugin 的 `receive()` 返回 `(user_id, message, session_id)`，Gateway 将其转换为统一格式。
- **Web 适配**：WebChannelPlugin 接收 HTTP 请求（JSON body），提取 `user_id`、`message`、`session_id`，转换为统一格式。
- **Telegram 适配**（可选）：TelegramChannelPlugin 接收 Telegram webhook，提取用户 ID、消息文本，转换为统一格式。

### 3. 响应适配

- **统一响应格式**：
  ```python
  {
      "response": str,
      "session_id": str,
      "metadata": dict,  # 可选：工具调用记录、Agent ID 等
  }
  ```
- **通道适配**：Gateway 返回统一格式，各 ChannelPlugin 的 `send()` 将其转换为通道特定格式（CLI 直接 print，Web 返回 JSON，Telegram 调用 API）。

### 4. 小结与 OpenClaw 对照

| 层         | 职责                         | 格式           |
| ---------- | ---------------------------- | -------------- |
| **通道层** | 接收/发送通道特定格式的消息  | CLI/Web/Telegram 格式 |
| **适配层** | 转换通道格式 ↔ 平台内部格式  | 统一请求/响应格式 |
| **Gateway** | 处理统一格式的请求/响应      | 平台内部格式   |

**OpenClaw 对照**：通道适配器负责**入站路由**（外部消息 → 平台内部）与**出站发送**（平台响应 → 通道格式），二者解耦便于对接 WhatsApp、Telegram、Discord、飞书等；见 [通道适配器框架](https://openclaw-docs.dx3n.cn/beginner-openclaw-guide/04-%E9%80%9A%E9%81%93%E9%80%82%E9%85%8D%E5%99%A8%E6%A1%86%E6%9E%B6%E4%B8%8E%E8%B4%A6%E5%8F%B7%E7%94%9F%E5%91%BD%E5%91%A8%E6%9C%9F)。

## 四、代码示例：多通道统一走 Gateway（week13/90_code/platform_with_plugins_demo.py）

CLI 与 Web 都调用同一 `gateway.handle_request(user_id, channel, message, session_id)`，仅 `channel` 与「谁调 receive / 谁调 send」不同；会话 ID 由 Gateway 在首轮创建时生成（含 channel 前缀），实现按通道隔离。

**CLI 入口**：Channel 的 receive → Gateway → Channel 的 send。

```python
def main_cli() -> None:
    gateway, pm = create_platform()
    channel_plugin = pm.get_channel("cli")
    session_id = None
    while True:
        user_id, message, _ = channel_plugin.receive()
        if message.lower() in ("quit", "exit", "q"):
            break
        result = gateway.handle_request(user_id, "cli", message, session_id)
        session_id = result.get("session_id")
        channel_plugin.send(user_id, result.get("response", ""))
```

**Web 入口**：HTTP 请求体即「入站」；响应 JSON 即「出站」。

```python
@app.route("/api/chat", methods=["POST"])
def chat():
    data = request.get_json(force=True, silent=True) or {}
    user_id = data.get("user_id", "web_user")
    message = data.get("message", "")
    session_id = data.get("session_id")
    result = gateway.handle_request(user_id, "web", message, session_id)
    return jsonify(result)
```

## 三、状态同步：多通道下的状态一致性、冲突处理、最终一致性策略

### 1. 状态一致性

- **问题**：若用户同时在多个通道（如 CLI 和 Web）使用同一会话，两个通道可能**同时修改会话状态**（如更新当前 Agent、追加对话历史），导致冲突。
- **策略**：
  - **单通道模式**：默认每个通道独立会话，不共享状态，避免冲突。
  - **共享会话锁**：若使用共享会话，Gateway 对会话加锁，同一时间只有一个通道可以修改状态。

### 2. 冲突处理

- **写冲突**：两个通道同时写入会话状态（如同时追加对话历史）。
- **处理**：
  - **最后写入获胜**：后写入的覆盖先写入的（简单但可能丢失数据）。
  - **合并策略**：对话历史按时间戳合并，工具调用记录去重合并。
  - **版本控制**：会话状态带版本号，写入时检查版本，冲突时拒绝写入并提示用户。

### 3. 最终一致性策略

- **含义**：多通道下，状态更新可能**异步传播**（如 CLI 更新状态，Web 稍后才看到），但最终会一致。
- **实现**：
  - **事件通知**：Gateway 更新会话状态后，通知所有使用该会话的通道（如 WebSocket 推送）。
  - **定期同步**：各通道定期查询会话状态，同步最新状态。
  - **用户触发**：用户切换通道时，主动查询并同步会话状态。

### 4. 简化实现（Day 90 实战）

- **Day 90 先实现单通道模式**：每个通道独立会话，不共享状态，避免冲突与同步的复杂性。
- **共享会话作为扩展点**：Week 14-15 再考虑实现共享会话与状态同步。

### 5. 小结表

| 策略         | 含义                     | 适用场景           |
| ------------ | ------------------------ | ------------------ |
| **单通道模式** | 每个通道独立会话，不共享 | 默认模式，简单可靠 |
| **共享会话锁** | 共享会话加锁，避免冲突   | 需要跨通道共享时   |
| **最终一致性** | 状态异步传播，最终一致   | 多通道共享会话时   |
