# 思考 & 补充学习资料

#### 反思问题

- 插件系统的扩展性如何验证？新增插件是否无需修改核心代码？
- 多通道下的会话隔离与共享策略是否合理？如何平衡隔离与复用？
- 状态持久化的性能与一致性如何权衡？如何设计数据模型以支持快速查询与恢复？

## 本周实战经验小结

- **插件接口**：Provider / Tool / Memory / Channel 四类抽象基类，PluginManager 统一注册与获取；Runtime 只依赖接口，不依赖具体实现。
- **Provider**：封装 LLM（invoke、bind_tools），便于切换模型或 API；**ToolPlugin**：get_tools() + execute()，新增工具只需新插件并 register_tool_plugin。
- **Memory**：retrieve(user_id, query) 在 build_context 时注入 System 或首条前；**Channel**：receive() 返回 (user_id, message, session_id)，send() 由 Gateway 在得到响应后调用。
- **多通道**：同一 Gateway.handle_request(user_id, channel, message, session_id)；session_id 含 channel 前缀，按通道隔离；CLI 用 channel_plugin.receive/send，Web 用 HTTP 请求体与 jsonify。
- **运行**：`--channel cli` 或 `--channel web`（Web 需 flask）；完整代码见 `week13/90_code/platform_with_plugins_demo.py`。
