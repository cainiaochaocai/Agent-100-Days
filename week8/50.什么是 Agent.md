# 50. 什么是 Agent

前面几周我们学了**提示词、工具调用、RAG、上下文工程、记忆系统**——这些都是构建“更智能的 AI 应用”的组件。当这些组件被组织成**能够自主做多步推理、调用工具、并根据结果再决策**的系统时，就进入了 **Agent（智能体）** 的范畴。

业界对 Agent 的表述侧重点不同，但内核一致：**OpenAI** 将 Agent 描述为一个能够**结合模型能力、工具接口和策略**，**自主感知、决策、执行并优化任务**的系统；**Claude** 则强调 Agent 的**目标导向**与**环境交互**——它不仅理解和生成信息，还能**根据反馈持续改进自己的行为**。

一个简洁的类比是：**LLM 是大脑，Agent 是拥有这颗大脑的执行体**。LLM 像“超级聪明的搜索引擎 + 内容生成器”：能理解问题、生成答案，但**不会主动操作**。Agent 则是“既懂事又会动手的智能助手”：不仅理解和生成内容，还能**主动执行任务**，并根据反馈**优化行为**。本节先厘清 **Agent 的准确定义**（与纯 LLM 调用、脚本/工作流的区别）、**核心特征**（感知、决策、行动、循环与自主性）、以及**为什么需要 Agent**（从“一问一答”到“多步规划与执行”，并结合一个具体场景说明）。

## 一、Agent 的准确定义：与“纯 LLM 调用”“脚本/工作流”的区别

### 1. 纯 LLM 调用（单次 / 多轮对话）

- **是什么**：用户发一句话，系统把这句话（加上可选的 System prompt、历史、RAG 结果）塞进一次 LLM 请求，拿到一条回复就返回。没有“根据回复再决定下一步”的循环，也没有在运行时选择“调用哪个工具、传什么参数”。**LLM 只负责理解并生成内容，不负责实际操作。**
- **特点**：输入 → 一次推理 → 输出；流程固定，不根据中间结果改变行为。多轮对话只是“把历史拼进下一轮的输入”，每轮仍是“一次调用、一次回复”。
- **典型**：客服问答、翻译、摘要、简单聊天。若 RAG/工具是在**调用前**由规则或代码决定“查什么、调什么”，再一次性把结果塞进 prompt，仍算“增强的 LLM 调用”，而不是 Agent。

### 2. 脚本 / 工作流（固定流程）

- **是什么**：步骤顺序、分支条件、调用的 API 或工具，都由**开发者事先写好**。数据怎么流转、下一步执行哪一步，由代码或配置决定，**不是由 LLM 在运行时决定**。
- **特点**：可多步、可调工具，但“下一步做什么”不依赖 LLM 的推理结果；LLM 若出现，通常只负责其中某一步的“生成文本”，不负责“选动作、选工具”。
- **典型**：固定审批流、定时报表、按模板填表后调 API。和 Agent 的差别在于：**没有“由模型根据当前状态决定下一步”的闭环**。

### 3. Agent：由模型在运行中“决策”的多步系统

- **是什么**：系统在运行过程中，**把“当前状态”（用户目标、已有信息、工具结果等）交给 LLM**，由 LLM **输出“下一步做什么”**（例如调用某工具、传某参数，或结束并返回）。执行完这一步后，**把执行结果再次交给 LLM**，由它决定继续还是结束。如此**循环**，直到模型认为任务完成或达到终止条件。
- **与上面两者的区别**：
  - 相对**纯 LLM 调用**：Agent 有**多轮“推理 → 行动 → 观察 → 再推理”的循环**，且“行动”（如选工具、填参数）由模型输出驱动。
  - 相对**脚本/工作流**：下一步做什么**不是写死的**，而是**由 LLM 根据当前上下文在运行时决定**，具有**自主性**。

可归纳为：

> **Agent = 在运行中依赖 LLM（或类似模型）进行“感知 → 决策 → 行动”，并根据行动结果再次感知与决策，形成闭环的多步系统。**

### 4. 小结表

| 类型            | 谁决定“下一步做什么”             | 是否多步循环                          | 是否由模型选工具/动作         |
| --------------- | -------------------------------- | ------------------------------------- | ----------------------------- |
| **纯 LLM 调用** | 无“下一步”，一次进一次出         | 无（多轮只是多轮单次调用）            | 否                            |
| **脚本/工作流** | 开发者写死的流程                 | 可多步，但流程固定                    | 否（或仅某步用 LLM 生成文本） |
| **Agent**       | **LLM 根据当前状态在运行时决定** | **是**（推理 → 行动 → 观察 → 再推理） | **是**                        |

## 二、Agent 的核心特征：感知、决策、行动、循环与自主性

可以从五个维度理解 Agent 的“核心特征”；它们也对应业界所说的**主动执行、智能决策、持续优化**。

### 1. 感知（Perception）

- **含义**：获取“当前状态”与“环境信息”的能力。包括用户输入、对话历史、工具/API 的返回结果、从记忆或 RAG 检索到的内容等。
- **在实现里**：这些信息被组织成 **Context**（如 messages、检索块），在每一轮决策前提供给 LLM，相当于 Agent 的“所见所闻”。

### 2. 决策（Decision）

- **含义**：根据当前感知到的信息，**选择下一步动作**。例如：调用哪个工具、传入什么参数、是否结束任务、如何组织最终回复。
- **在实现里**：通常由 LLM 输出**结构化内容**（如 tool_calls、或“下一步计划”的文本），由运行时解析并执行。决策权在**模型**，而不是写死在代码里。

### 3. 行动（Action）

- **含义**：把决策落到实处——真正调用工具、查数据库、发请求等，并拿到**执行结果**。
- **在实现里**：由框架或应用根据 LLM 的 tool_calls 调用相应 Tool，把返回结果再交给 LLM，形成“观察”。

### 4. 循环（Loop）

- **含义**：**感知 → 决策 → 行动 → 再感知 → 再决策 → …** 的循环，直到模型输出“任务完成”或达到最大步数/超时等终止条件。
- **在实现里**：Agent 运行时通常有一个 **run loop**：每轮把“历史 + 本轮工具结果”拼成 messages，调用 LLM，若没有新的 tool_calls 则结束，若有则执行工具后进入下一轮。

### 5. 自主性与持续优化（Autonomy & Improvement）

- **自主性**：在**给定目标与边界**的前提下，“下一步做什么”由 Agent（通过 LLM）**在运行中自行决定**，而不是由开发者把每一步都写好。边界通过 System Prompt、工具列表、权限、最大步数等约束。
- **持续优化**：对应 Claude 强调的“根据反馈改进行为”——Agent 可以结合执行结果、用户反馈或记忆，在后续任务中调整策略（例如下次报告怎么写、先查哪类数据），实现**持续优化**。

### 6. 小结表

| 特征                  | 含义                                 | 在实现中的体现                                    |
| --------------------- | ------------------------------------ | ------------------------------------------------- |
| **感知**              | 获取当前状态与环境信息               | 用户输入、历史、工具结果、RAG/记忆 → 组成 Context |
| **决策**              | 根据当前信息选择下一步动作           | LLM 输出 tool_calls 或计划，由运行时解析          |
| **行动**              | 执行选定的动作并拿到结果             | 调用 Tool/API，返回结果                           |
| **循环**              | 感知 → 决策 → 行动 → 再感知…         | Agent run loop，直到结束或终止条件                |
| **自主性 / 持续优化** | 在边界内由模型决定；根据反馈改进行为 | 不写死步骤；记忆与反馈可影响后续策略              |

## 三、为什么需要 Agent：从“一问一答”到“多步规划与执行”

### 1. “一问一答”的局限

- **单次调用**只能基于“当前这一次”的输入和已塞进 Context 的内容给出回复。若任务需要**先查 A、再根据 A 的结果查 B、再根据 B 做计算**，单次调用要么无法完成，要么需要你**事先**把 A、B、计算都写好并一次性塞进 prompt（那就变成脚本，且难以应对动态分支）。
- **多轮对话**可以“用户问一句、系统答一句、用户再问、再答”，但“下一句问什么”依赖**用户**；若希望**系统主动**去查、去算、再汇总回答，就需要系统自己能发起多步动作——这就是 Agent 要解决的问题。

### 2. 一个具体场景：每周整理周会报告

用**每周整理周会报告**对比三种方式，能直观看到 Agent 的差异：

- **没有 LLM 时**：需要自己整理本周数据与项目进展，筛选重要内容，整理成报告，排版，再发送。全程人工。
- **有 LLM 时**：可以把整理好的数据和项目进展扔给 LLM，让它生成报告文案；但**复制粘贴、选择收件人、点击发送**等操作仍要你手动完成。LLM 只负责**理解并生成内容**，不负责**实际操作**。
- **有 Agent 时**：你只需说“整理本周报告并发送”。Agent 会**自动**从 CRM 拉数据、从 Jira/Notion 或本地文件夹取项目进度，用 LLM 生成报告，再**自动发送**出去；还可以根据反馈（如“下次重点突出风险项”）**优化下一次的报告生成策略**。就像一位懂事的智能助理：你只说需求，它完成整个流程，并会总结经验、下次做得更好。

可见，Agent 的价值不仅在于**理解和生成信息**，更在于**主动执行、智能决策和持续优化**。

### 3. Agent 能做什么（归纳）

- **多步规划与执行**：用户给一个目标，Agent 可以**自己决定**先查什么、再算什么、再生成什么、再执行什么，而不需要用户分多轮一句句问。
- **按需使用工具**：在运行时根据**当前推理结果**选择“现在该用哪个工具、参数是什么”，而不是在开发时把全部可能路径都写死。
- **适应不确定性与异常**：某一步失败或返回异常时，Agent 可以根据“当前状态”决定重试、换一种方式、或向用户说明失败原因。
- **持续优化**：结合记忆与反馈，在后续任务中调整策略，越用越贴合需求。

### 4. 何时用 Agent、何时不用

- **适合用 Agent**：任务需要多步、步骤依赖上一步结果、或需要“根据情况选不同工具/不同路径”的开放决策；希望系统**主动执行**并能在反馈中**优化**。
- **不必上 Agent**：单次问答、固定流程、对延迟和成本极其敏感且步骤可完全预见的场景，用纯 LLM 调用或脚本往往更简单、更可控。

> **Agent 的价值在于：在“目标明确、边界清晰”的前提下，把“如何拆解、如何选工具、如何组合结果”交给模型在运行中决策，从而支持主动执行、智能决策与持续优化。对开发者而言，需要从关注“流程怎么一步步写死”，转换到关注“目标、方法与策略怎么设定”，让 Agent 在边界内自主完成闭环。**

| 学习点               | 要点                                                                                                                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent 的准确定义** | 与纯 LLM 调用（只理解与生成）、脚本/工作流（流程写死）不同，Agent 在运行中由 LLM 根据当前状态**决定下一步**，形成“感知 → 决策 → 行动 → 再感知”的闭环；可概括为：LLM 是大脑，Agent 是拥有这颗大脑的执行体。 |
| **核心特征**         | 感知、决策、行动、循环、自主性；并支持**根据反馈持续优化**，对应“主动执行、智能决策、持续优化”。                                                                                                           |
| **为什么需要 Agent** | 从“一问一答”到“多步规划与执行”：以周会报告为例，LLM 只生成内容，Agent 能自动拉数据、生成、发送并优化策略；开发者需从关注**流程**转换到关注**方法与策略**。                                                 |
