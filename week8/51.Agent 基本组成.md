# 51. Agent 基本组成

Day 50 明确了 Agent 的定义与核心特征：由 LLM 在运行中决策下一步，形成“感知 → 决策 → 行动”的闭环。本节把 Agent 拆成**可实现的组成部分**：**大脑（LLM）**、**工具（Tools）**、**技能（Skills）**、**记忆与上下文**、**规划与执行循环**（ReAct、Plan-and-Execute 等），并说明**各组成部分如何协同**——用一次典型调用的数据流串起来。

## 一、大脑（LLM）：推理与决策

### 1. 角色

在 Agent 架构里，**LLM 是“大脑”**：负责根据当前输入（用户目标、历史、工具返回等）进行**推理**，并**输出下一步决策**——例如调用哪个工具、传什么参数，或结束任务并给出最终回复。

- **推理**：理解任务、拆解步骤、判断“还缺什么信息、该做什么动作”。
- **决策**：以结构化形式输出“动作”（如 `tool_calls`），或自然语言形式的“计划”“结论”，由运行时解析并执行。

### 2. 输入与输出

- **输入**：通常是一组 **messages**，包括 System（角色与规则）、用户消息、历史对话、以及**上一轮或之前各轮的工具调用结果**（以 tool 或 assistant 消息形式注入）。即 Day 50 所说的“感知”内容，都通过 Context 喂给 LLM。
- **输出**：可能是（1）**纯文本回复**（无 tool_calls），表示“本步只说话、不调用工具”或“任务结束”；（2）**带 tool_calls 的 assistant 消息**，表示“请执行这些工具调用”；（3）部分框架还支持“中间推理”文本 + tool_calls，供调试与约束。

### 3. 小结

| 维度     | 说明                                              |
| ------ | ----------------------------------------------- |
| **角色** | 推理（理解任务、缺什么、该做什么）与决策（输出下一步动作或结束）。               |
| **输入** | System prompt + 用户消息 + 历史 + 工具结果等，组成当前 Context。 |
| **输出** | 文本回复和/或 tool_calls；无 tool_calls 时通常表示结束或仅需自然语言。 |

## 二、工具（Tools）：感知与行动的外延

### 1. 角色

**工具（Tools）** 是 Agent **感知与行动的外延**：LLM 不能直接查数据库、调 API、读文件，只能通过“调用工具”来获取信息或改变环境。工具把**外部能力**封装成**名称 + 参数 + 返回值**，供 LLM 在决策时选择并填入参数，由运行时真正执行。

- **感知**：例如“查天气”“查订单”“检索知识库”——工具返回的结果成为 Agent 的“观察”，进入下一轮 Context。
- **行动**：例如“发邮件”“创建工单”“写文件”——工具执行后，执行结果同样作为观察反馈给 LLM。

### 2. 工具的描述与绑定

- **描述**：每个工具需要有**名称**和**说明**（description），有时还有**参数 schema**（名称、类型、是否必填等）。LLM 根据这些描述决定“什么时候用哪个工具、传什么参数”；描述不清会导致误用或不用。
- **绑定**：在 Agent 运行时，把“当前可用工具列表”注入 System 或单独消息（如 function/tool 定义），LLM 在输出中通过 `tool_calls` 指定要调用的工具与参数；运行时根据名称找到对应实现并执行，把结果再塞回 messages。

### 3. 小结

| 维度       | 说明                                                           |
| -------- | ------------------------------------------------------------ |
| **角色**   | 扩展感知（查数据、检索）与行动（写库、发请求）；LLM 通过“选工具 + 填参数”与之交互。               |
| **形式**   | 名称 + 描述 + 参数 schema；运行时解析 tool_calls 并执行，结果作为“观察”回填 Context。 |
| **设计要点** | 描述要清晰、粒度适中，便于模型选对、填对；工具过多时需考虑检索或分层。                          |

## 三、技能（Skills）：从工具到“会做事”的能力模块

工具解决了“**调哪个接口**”，但**调航班 API 不代表会做旅游规划、调数据库不代表会做商业分析**。真正的能力还需要知道：什么时候该查什么、查完如何筛选、信息冲突怎么办、怎么组合成结果、错了如何补救等。**技能（Skill）** 就是在工具之上的一层**可复用的“专家能力模块”**：把专业知识、操作流程和执行指导打包，让 Agent 不仅“会调工具”，更“会做成一件事”。（Week 4 的 Day 27 已详细展开，此处仅纳入组成视角。）

### 1. 技能与工具的关系

- **工具**：单次能力封装，名称 + 参数 + 返回值；Agent 通过 tool_calls 选择并调用。
- **技能**：**指令（怎么做）+ 所用工具（scripts）+ 交付规范（templates）** 的组合；通常用文件夹组织（如 `SKILL.md` + `resources/scripts` + `resources/templates`），在“相关任务”被触发时加载，指导 Agent 按步骤调用多个工具并产出标准交付物。
- **层级**：工具 / 技能 / 智能体 是常见划分——工具是原子能力，技能是“做成一类事”的方法，Agent 是拥有大脑并调度技能与工具的执行体。

### 2. 技能在 Agent 中的体现

- **元信息（Metadata）**：技能名称、描述、适用场景，可常驻或优先进入 Context，供 Agent 判断“当前任务是否与该技能相关”。
- **指令（Instructions）**：技能被选中时加载，包含执行步骤、工作流、注意事项，注入 System 或参考块，让 LLM 知道“遇到这类任务该怎么做”，而不仅靠模型自己猜。
- **资源（Resources）**：脚本（对应可注册为 Agent 的工具）、模板（定义输出格式）等，按需加载，避免一次性塞满 Context。这种**渐进式披露（Progressive Disclosure）** 便于 Agent 挂载很多技能又不爆 token。

### 3. 小结

| 维度            | 说明                                        |
| ------------- | ----------------------------------------- |
| **定位**        | 工具之上的一层；解决“怎么做成一件事”，而不仅是“调哪个接口”。          |
| **典型内容**      | 元信息（名片）+ 指令（步骤与流程）+ 资源（脚本/模板）；文件夹组织。      |
| **在 Agent 中** | 技能指令与可选工具注入 Context；按任务相关性触发加载，指导多步执行与交付。 |

## 四、记忆与上下文：状态与历史的承载

### 1. 角色

**记忆与上下文** 承载 Agent 的**状态与历史**，使“当前这一步”的 LLM 能“看到”之前发生了什么、用户是谁、有哪些长期信息可用。

- **上下文（Context）**：本轮调用时**塞进 LLM 的可见内容**，包括 System、用户消息、对话历史、本轮及之前各轮的工具输入输出。对应 Week 6 的“上下文工程”；受 token 限制，通常只保留最近若干轮或摘要。
- **记忆（Memory）**：**跨轮、跨会话持久化**的信息，如用户偏好、历史摘要、任务进度。在需要时**检索并注入**到 Context，对应 Week 7 的记忆系统。

### 2. 在 Agent 中的位置

- 每一轮**决策前**：把“当前会话历史 + 检索到的记忆 + 上一轮工具结果”拼成 messages，再交给 LLM，因此**记忆与上下文共同构成“感知”的输入**。
- 每一轮**决策后**：可根据策略把本轮对话或关键信息**写入记忆**，供后续会话使用。上下文则通常由框架按“最近 K 轮”或“全量截断”自动维护。

### 3. 小结

| 维度            | 说明                                        |
| ------------- | ----------------------------------------- |
| **上下文**       | 本拍可见的 System、历史消息、工具结果；受 token 限制，需裁剪/摘要。 |
| **记忆**        | 跨会话持久化；按需检索后注入 Context，供 LLM 做个性化与连贯决策。   |
| **在 Agent 中** | 二者共同组成“感知”输入；写记忆在决策后、按策略触发。               |

## 五、规划与执行循环：ReAct、Plan-and-Execute 等范式简介

“规划与执行循环”指 **LLM 如何与工具、状态配合** 的**控制流范式**。常见几种如下。

### 1. ReAct（Reasoning + Acting）

- **思路**：每轮 LLM 既可以**推理**（输出一段 Thought/推理文本），也可以**行动**（输出 tool_calls）。运行时把**上一轮的工具结果**作为“Observation”拼进下一轮输入，LLM 再决定下一步 Thought 和/或 Action，直到输出最终答案。
- **特点**：**交织**的“想一步、做一步”；实现简单，适合多数通用 Agent。很多框架的默认 Agent 循环就是 ReAct 风格。

### 2. Plan-and-Execute（先规划再执行）

- **思路**：先让 LLM **一次性或分阶段给出“计划”**（如步骤 1、2、3），再**按计划逐步执行**工具或子任务；每步执行结果可再反馈给 LLM，用于调整后续步骤或生成最终回答。
- **特点**：规划与执行**相对分离**，适合步骤清晰、需要“先想清楚再动手”的任务；对复杂动态分支有时不如 ReAct 灵活。

### 3. 其他变体

- **Reflexion / 反思**：执行后让 LLM 对结果做“反思”，决定是否重试、换策略（Week 9 会展开）。
- **多 Agent 协作**：多个 Agent 分工（如一个规划、一个执行、一个校验），通过消息或共享状态协同。

### 4. 小结表

| 范式                   | 核心思路              | 适用场景       |
| -------------------- | ----------------- | ---------- |
| **ReAct**            | 每轮可推理 + 行动，观察后再推理 | 通用、步骤可动态调整 |
| **Plan-and-Execute** | 先出计划，再按步执行        | 步骤清晰、需先规划  |
| **反思 / 多 Agent**     | 执行后反思或多角色分工       | 提高鲁棒性、复杂任务 |

## 六、各组成部分如何协同：一次典型 Agent 调用的数据流

下面用**一次典型 Agent 调用**把大脑、工具、技能、记忆与上下文、循环串起来。

### 1. 初始化与输入

- 用户输入一条**目标**（如“查一下北京明天天气，并推荐要不要带伞”）。
- 系统准备**当前 Context**：System（含角色、规则、可用工具描述）、**若按技能组织则还可包含当前相关技能的元信息或指令**、可选记忆检索结果、用户消息。此时尚无工具结果。

### 2. 第一轮：LLM 决策

- 将上述 messages 调用 **LLM**。
- LLM 输出：例如 **tool_calls** = [{ name: "get_weather", arguments: { city: "北京", date: "明天" } }]。
- 运行时解析 tool_calls，**执行工具** `get_weather`，得到结果（如“北京明天晴，25°C”）。

### 3. 第二轮：注入观察，再决策

- 将**上一轮的 assistant 消息（含 tool_calls）** 和 **tool 结果消息（Observation）** 追加到 messages，再次调用 **LLM**。
- LLM 看到“北京明天晴”，决定不再调工具，**直接输出最终回复**：“明天北京晴天 25°C，一般不用带伞；若你容易晒伤可带遮阳伞。”
- 本轮无 tool_calls → **循环结束**，将该回复返回给用户。

### 4. 可选：写记忆

- 若配置了记忆系统，可在对话结束或关键节点，把“用户问过北京天气、助手给过建议”等**写入记忆**，供后续会话检索。

### 5. 数据流简图（文字）

```text
用户输入
    ↓
[拼 Context：System + 技能(可选，元信息/指令) + 记忆(可选) + 用户消息 + 历史]
    ↓
LLM（大脑）→ 输出：tool_calls 或 最终回复
    ↓
若有 tool_calls → 执行工具 → 得到 Observation
    ↓
Observation 追加到 messages → 再调 LLM → 重复直到无 tool_calls
    ↓
最终回复返回用户；（可选）写记忆
```

### 6. 小结表

| 组成部分        | 在数据流中的位置                                                           |
| ----------- | ------------------------------------------------------------------ |
| **大脑（LLM）** | 每轮根据当前 messages 推理并输出 tool_calls 或最终回复。                            |
| **工具**      | 根据 LLM 的 tool_calls 执行，结果作为 Observation 追加到 messages。              |
| **技能**      | 可选；技能元信息/指令注入 Context，指导“如何做成一类事”；技能内脚本可注册为工具。                     |
| **记忆与上下文**  | 上下文 = 本拍 messages（含历史与工具结果）；记忆在需要时检索注入，决策后可写回。                     |
| **循环**      | 有 tool_calls → 执行 → 追加 Observation → 再调 LLM，直到无 tool_calls 或达终止条件。 |

## 小结

| 学习点            | 要点                                                                                   |
| -------------- | ------------------------------------------------------------------------------------ |
| **大脑（LLM）**    | 负责推理与决策；输入为 Context（System、用户、历史、工具结果），输出为文本和/或 tool_calls。                          |
| **工具（Tools）**  | 感知与行动的外延；通过名称+描述+参数暴露给 LLM，运行时执行 tool_calls 并将结果作为观察回填。                              |
| **技能（Skills）** | 工具之上的“会做事”能力模块；含元信息、指令与资源，按任务相关性加载，指导多步执行与交付；与 Day 27 衔接。                            |
| **记忆与上下文**     | 上下文承载本拍可见状态与历史；记忆承载跨会话信息，检索后注入、决策后可写入。                                               |
| **规划与执行循环**    | ReAct 为“推理与行动交织”；Plan-and-Execute 为“先规划再执行”；可结合反思或多 Agent。                           |
| **协同与数据流**     | 用户输入 → 拼 Context（含技能可选、记忆）→ LLM 决策 → 若有 tool_calls 则执行并追加 Observation → 再调 LLM，直至结束。 |
