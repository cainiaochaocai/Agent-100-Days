# 53. Agent 的失败模式

Day 52 提到要“处理不确定性、失败与重试”，并让 Agent 可观测、可约束、可纠错。本节集中梳理 **Agent 的典型失败模式**：**幻觉与错误工具使用**、**循环与死锁**、**上下文与记忆问题**，以及**如何通过日志、trace、人工兜底与 guardrail 进行观测与缓解**。

## 一、幻觉与错误工具使用：错误参数、错误时机、错误工具选择

### 1. 幻觉（Hallucination）

- **含义**：模型输出与事实或当前上下文不符的内容，例如编造不存在的工具返回值、虚构用户未提供的信息、或把上一步工具结果“记错”。
- **在 Agent 中的表现**：在最终回复中夹杂未验证的信息；或根据“自以为的”观察做下一步决策，导致选错工具或参数。
- **成因**：模型能力边界、上下文过长导致“看漏”、或工具结果未被清晰呈现，模型依赖“猜”而非真实观察。

### 2. 错误工具选择

- **含义**：该用 A 工具却选了 B，或不该用工具时调用了工具（反之亦然）。
- **典型**：任务只需查一次知识库，却先调了“发邮件”；或应用场景没有“写文件”能力，模型却输出了写文件调用。多与**工具描述不清、场景边界在 System Prompt 里未写清**有关。
- **后果**：轻则多一步无效调用（延迟与成本），重则误触敏感能力（如误发邮件、误删数据）。

### 3. 错误参数

- **含义**：工具选对了，但参数填错——类型不对、必填漏填、取值超出范围或语义错误（如城市名拼错、日期格式不对）。
- **典型**：查天气传了 `city: "北京省"`；查订单传了 `order_id: "最近一个"` 而非真实 ID。模型有时会“发明”参数格式或把自然语言直接当参数。
- **后果**：工具报错或返回空/异常，若未做重试或纠错提示，Agent 可能卡住或基于错误结果继续推理。

### 4. 错误时机

- **含义**：在还不该调用某工具时就调了（如未拿到必要前置信息），或该先确认再执行时直接执行了（如危险操作未二次确认）。
- **典型**：用户说“帮我订一张票”，模型未先查余票或未确认日期就调“下单”；或在不具备用户身份时调用了需要鉴权的工具。
- **后果**：业务失败、重复下单、或权限/合规问题。

### 5. 小结表

| 失败类型       | 表现             | 常见成因               | 缓解方向                         |
| ---------- | -------------- | ------------------ | ---------------------------- |
| **幻觉**     | 编造信息、记错观察      | 上下文噪音、结果呈现不清       | 强调“仅依据工具结果”、结构化呈现            |
| **错误工具选择** | 选错工具、多余/遗漏调用   | 工具描述与场景边界不清        | 清晰描述、只暴露必要工具、System Prompt约束 |
| **错误参数**   | 类型/格式/取值错误、漏填  | 模型“猜”参数、schema 不清晰 | 明确 schema、示例、工具内校验           |
| **错误时机**   | 前置条件未满足就调用、未确认 | 缺少“先查再动”的规则说明      | 在 System 中规定顺序与确认策略          |

## 二、循环与死锁：重复调用、无法结束

### 1. 重复调用（循环）

- **含义**：多轮中反复执行相同或等效的 tool_call（同一工具、同一或等价参数），始终得不到“任务完成”的结论，或一直重复失败的操作。
- **典型**：模型每次都说“再查一次天气”，或工具已返回“无此订单”，模型仍反复用同一参数查订单。有时是**未把“上一步已失败/已无结果”有效注入上下文**，或模型未理解“此时应结束或换策略”。
- **后果**：延迟与成本上升，用户体验差；若没有最大步数，可能长时间不结束。

### 2. 无法结束（死锁 / 不终止）

- **含义**：每轮都输出 tool_calls，从不输出“最终回复”；或逻辑上已应结束，但模型一直认为“还需要再调一次”。
- **典型**：任务本可一步回答，模型却不断“查资料 → 再查 → 再查”；或工具链中某一步永远返回“需要更多信息”，模型又无法从用户输入中提取，形成僵局。
- **成因**：缺少“何时结束”的明确规则；或工具返回过于模糊，模型误以为未完成；也有模型本身倾向“多做事”的偏差。

### 3. 缓解思路

- **最大步数**：硬性上限（如最多 10 步），到步数即强制结束并返回当前结果或“任务未完成”的说明。
- **重复检测**：若检测到相同 tool_call（工具名 + 参数）在最近 N 步内已出现，可拒绝执行并注入“上一步已执行过相同调用，请换策略或结束”的提示。
- **结束条件**：在 System Prompt 中明确“当……时请直接回复用户、不再调用工具”（如已得到答案、或某工具返回“无结果”且无需其他工具时）。
- **超时**：单步或总时长超时则终止，避免长时间挂起。

### 4. 小结表

| 现象       | 表现                   | 缓解手段                            |
| -------- | -------------------- | ------------------------------- |
| **重复调用** | 同/等价 tool_call 反复执行  | 重复检测 + 注入“已执行过，请换策略或结束”         |
| **无法结束** | 始终有 tool_calls、无最终回复 | 最大步数、超时、在 System Prompt 中写清结束条件 |

## 三、上下文与记忆问题：丢状态、记错、检索不到

### 1. 丢状态

- **含义**：多轮中之前某步的关键信息（如用户刚说的日期、上一步工具返回的 ID）在后续轮次中“没被看到”或未被正确引用。
- **典型**：因 **token 限制** 对历史做了截断，早期轮次被裁掉；或拼接 messages 时漏掉了某条 tool result；或短期/会话状态未正确写入记忆、下一轮未注入。
- **后果**：模型基于“不完整”的上下文决策，重复提问、用错参数、或给出与之前承诺矛盾的回复。

### 2. 记错

- **含义**：记忆系统里存了错误内容（如抽取错误、用户口误被记下、或冲突未按 Day 45 策略处理），检索后注入 Context，导致模型“记错”用户偏好或事实。
- **典型**：用户说“不要推荐 A”，被记成“要推荐 A”；或旧地址未在用户更新后覆盖，推荐仍按旧地址。
- **后果**：个性化错误、违反用户意愿、或给出错误结论。

### 3. 检索不到

- **含义**：本该用到的记忆（如用户偏好、历史结论）因**检索条件过严、向量不匹配、或未触发检索**而没有进入本拍 Context，模型“不知道”已有信息。
- **典型**：用户问“和上次一样”，但“上次”的结论未被检索到；或记忆按 user_id 隔离，但当前请求未带 user_id，导致查不到。
- **后果**：重复问用户、重复计算、或无法延续历史会话。

### 4. 小结表

| 问题       | 表现              | 缓解方向                             |
| -------- | --------------- | -------------------------------- |
| **丢状态**  | 历史被截断或漏拼，关键信息丢失 | 控制单轮长度、重要信息摘要/写入记忆、拼 message 时校验 |
| **记错**   | 记忆内容错误或过时       | 写入校验、冲突策略、用户可查看/更正记忆             |
| **检索不到** | 该用的记忆未进 Context | 检索触发条件、过滤与排序、user_id 等 scope 正确  |

## 四、如何观测与缓解：日志、trace、人工兜底与 guardrail

### 1. 日志（Logging）

- **目的**：记录每一轮的输入（messages 摘要或 hash）、LLM 输出（含 tool_calls）、工具执行与结果、以及最终回复，便于事后排查与复现。
- **要点**：对敏感字段脱敏；为每次“任务”或会话分配 trace_id，便于串起多轮；可对 token 数、延迟、工具调用次数做简单统计，发现异常模式（如某任务总是超步数）。

### 2. Trace（追踪）

- **目的**：在单次请求或单次任务内，把“多轮推理 → 工具 → 观察”的**完整轨迹**记录下来，形成可浏览的 DAG 或时间线。
- **要点**：每步的 prompt 片段、模型输出、tool_calls、tool results 可逐步展开；便于定位“第几步选错了工具、哪一步参数错了、哪一步开始循环”。可与 LangSmith、OpenTelemetry 等集成。

### 3. 人工兜底（Human in the Loop）

- **目的**：在关键节点或异常时引入人工确认或修正，避免错误动作直接生效。
- **典型**：敏感操作（如付款、删数据）前必须人工确认；或 Agent 返回“不确定”时转人工客服；或对低置信度输出做人工抽检并反馈，用于改进提示词或模型。
- **要点**：明确哪些操作必须经过人、超时或无人响应时的降级策略（如取消操作、仅返回信息不执行）。

### 4. Guardrail（护栏）

- **含义**：在 Agent 输入或输出侧加一层**规则或模型**，用于过滤、改写或拦截明显违规或危险内容。
- **输入侧**：对用户输入做敏感词过滤、意图分类或路由，避免把明显恶意或离题请求交给 Agent。
- **输出侧**：对模型输出的 tool_calls 做校验——如禁止某些工具在未授权时被调用、参数白名单或格式校验、重复调用拦截；对最终回复做 PII 脱敏、禁止输出某些类型信息等。
- **要点**：guardrail 本身要可靠且可维护，避免误拦正常请求；与“可观测”结合，便于分析被拦案例并调参。

### 5. 小结表

| 手段            | 作用            | 典型做法                                 |
| ------------- | ------------- | ------------------------------------ |
| **日志**        | 事后排查、复现、统计    | 每轮输入输出与 tool 结果留痕，trace_id 串联，敏感信息脱敏 |
| **Trace**     | 看清多轮轨迹、定位错误步骤 | 完整“推理 → 工具 → 观察”链可浏览，与可观测平台集成        |
| **人工兜底**      | 关键操作确认、异常转人   | 敏感操作需确认、低置信度转人工、超时降级                 |
| **Guardrail** | 输入输出过滤与校验、防误用 | 输入过滤与路由、tool_calls 校验与拦截、输出脱敏与合规     |

## 小结

| 学习点           | 要点                                                                                    |
| ------------- | ------------------------------------------------------------------------------------- |
| **幻觉与错误工具使用** | 幻觉：编造或记错信息；错误工具选择/参数/时机：选错工具、填错参数、或在不满足前置条件时调用。缓解靠清晰描述、schema、System 约束与“仅依据工具结果”的提示。 |
| **循环与死锁**     | 重复调用同一/等价工具；或从不输出最终回复。缓解靠最大步数、超时、重复检测、以及在 System 中明确结束条件。                             |
| **上下文与记忆问题**  | 丢状态（截断或漏拼）、记错（错误或过时记忆）、检索不到（未注入该用的记忆）。缓解靠上下文管理、记忆写入与冲突策略、检索触发与 scope。                 |
| **观测与缓解**     | 日志留痕与 trace 串联多轮；人工兜底用于关键操作与异常；guardrail 用于输入输出过滤与 tool_calls 校验，与可观测结合迭代。            |
