# 52. Agent 开发者的“思维模式”转变

Day 50、51 把 Agent 的定义、组成与数据流讲清楚了。从“传统应用开发”或“单次 LLM 调用”转向 **Agent 开发**，除了多一套组件，更需要**心智模型的转变**：你不再完全控制每一步，而是**设定目标与边界，把“下一步做什么”交给模型在运行中决定**。概括成一句话：开发者需要从**“线性流程”**转向**“方法与策略地图”**——以前做软件，脑子里是“一步接一步的流程图”；现在做 Agent，脑子里必须是**“根据目标自主决策的方法与策略”**。本节从四个维度展开：**从写死流程到设定目标与边界**、**从单次调用到多轮循环**、**从追求确定输出到接受不确定性并设计失败处理**、以及**提示词与工具设计如何让 Agent 可观测、可约束、可纠错**。

## 一、从“写死流程”到“设定目标与边界、让模型决策”

### 1. 传统方式：写死流程（“流程思维”）

- **做法**：业务逻辑用 if/else、状态机、工作流引擎写死。先调 A、再根据 A 的结果调 B 或 C，分支与顺序都在代码里；LLM 若出现，通常只负责其中某一步的“生成一段文本”，不参与“选哪条分支、选哪个接口”。
- **思考方式**：往往是“**我需要实现哪些功能？**”——把功能拆成步骤，每步输入输出写死，流程不能出错就算完成。
- **特点**：行为可预测、易测试；但路径一多、需求一变，就要改代码、发版，扩展成本高，也难以应对“用户意图开放、下一步依赖上下文”的场景。**核心关注是流程正确性**，体验容易僵硬。

### 2. Agent 方式：设定目标与边界，让模型决策（“方法与策略思维”）

- **做法**：你定义**目标**（如“帮用户完成订票”）、**边界**（可用工具列表、禁止行为、最大步数等），以及**规则**（在 System Prompt里说明“何时用哪个工具、如何判断完成”）。具体“先查航班还是先查用户偏好、参数填什么、何时结束”，由 **LLM 根据当前上下文在运行时决定**。
- **思考方式**：变成“**如何让系统自主选择最优策略来解决用户问题？**”——你赋予它工具和目标，让它自己去“走位”；设计的重点不再是“功能点”，而是“**决策链**”。
- **特点**：同一套目标与边界可应对多种用户说法和中间状态；你从“写步骤”变成“写约束与能力”，模型在约束内**自主选路径**。**核心关注是策略最优性**，系统更灵活、更像有经验的员工。代价是行为不再逐行确定，需要靠提示词、工具设计、日志与测试来收窄和验证。

### 3. 一个具体对比：智能客服系统

| 维度       | 传统“流程思维”                         | Agent“方法与策略思维”                                              |
| -------- | -------------------------------- | ----------------------------------------------------------- |
| **思考方式** | “我需要实现哪些功能？”                     | “如何让系统自主选择最优策略来解决用户问题？”                                     |
| **输入**   | 用户必须填订单号 + 问题类型（下拉菜单）            | 用户自然语言：“我的那个红色鞋子订单能退吗？”（非结构化）                               |
| **处理方式** | 固定 If…Then…Else 规则匹配答案           | Agent 用 LLM 解析意图（退货、目标=红色鞋子订单），再**自主决策**：查历史、查库存、判断是否满足一键退货 |
| **缺信息时** | 容易卡死或直接转人工                       | 主动追问用户，补全信息后再继续                                             |
| **开发感受** | 重点是“流程不能出错”，订单号能输、工单能生成就算完成；体验僵硬 | 重点是“决策链”：赋予工具和目标，让系统自己走位；系统更灵活、更像有经验的员工                     |
| **核心关注** | **流程正确性**                        | **策略最优性**                                                   |

### 4. 心态上的转变

- **以前**：“这一步之后一定是那一步” → 代码里写死；关注**过程**与流程正确性。
- **现在**：“在这一步，模型**可以**做 A/B/C，但不可以做 D；最终要达成目标，具体顺序和参数由模型根据当前信息选。” → 用 **System Prompt、工具列表、返回格式、禁止项** 等表达目标与边界，用**观测与回归**验证模型是否在边界内、是否趋向目标；关注**方法与策略**、策略最优性。

> **核心转变**：从“我控制每一步”到“我设定目标与边界，并设计好模型做决策所需的输入（上下文、工具），把执行路径交给模型。”这种从“关注过程”到“关注方法策略”的思维升级，是 AI 时代对开发者的基本要求。

## 二、从“单次调用”到“多轮推理与工具调用循环”

### 1. 传统方式：单次调用

- **做法**：用户输入 → 拼好 prompt（含必要信息）→ 调一次 LLM → 返回回复。没有“根据回复再调工具、再调 LLM”的循环。
- **局限**：无法完成“先查再算再答”的多步任务；若把多步都塞进一次 prompt，要么超长要么需要你事先写好所有分支，又回到“写死”。

### 2. Agent 方式：多轮推理与工具调用循环

- **做法**：每一轮把**当前状态**（用户目标、历史、上一轮工具结果）交给 LLM；LLM 输出 tool_calls 或最终回复。若有 tool_calls，执行后把结果**追加到对话**，再调 LLM；如此循环直到无 tool_calls 或达终止条件。
- **心态**：你设计的是**循环的规则**（何时停、最多几步、如何把工具结果呈现给模型），而不是“第一轮说什么、第二轮说什么”。单次调用只是循环中的**一步**，调试和优化要放在“多轮轨迹”上看。

### 3. 小结

| 维度       | 单次调用思维         | 多轮循环思维                    |
| -------- | -------------- | ------------------------- |
| **单位**   | 一次请求 = 一次回复    | 一次“任务” = 多轮“推理 → 工具 → 观察” |
| **设计重点** | 把本步 prompt 写完整 | 设计每轮输入结构、终止条件、步数上限        |
| **调试**   | 看单次输入输出        | 看整条轨迹：哪一步选错工具、参数错了        |

## 三、从“追求确定输出”到“处理不确定性、失败与重试”

### 1. 传统方式：追求确定输出

- **做法**：同一输入期望同一输出（或有限几种）；用单元测试断言“输入 A → 输出 B”。LLM 若只做文本生成，可通过严格格式、少分支来逼近确定性。
- **局限**：Agent 的“下一步”由模型决定，**同一用户问题可能走出不同轨迹**（先查 A 还是先查 B、某步失败后重试还是换路），输出存在**合理范围内的不确定性**。

### 2. Agent 方式：接受不确定性，并设计失败处理

- **做法**：
  - **接受**：在目标与边界内，允许多种“正确路径”和表述差异；用**结果正确性、边界遵守**来验收，而不是逐字对比。
  - **失败处理**：工具超时、返回错误、模型选错工具或参数时，要有**重试、回退、降级或明确报错**的策略（如“某步失败则提示用户并停止”“最多重试 2 次”）。Day 53 会细讲失败模式。
  - **约束**：用最大步数、超时、禁止重复调用同一参数等，避免无限循环或明显浪费。

### 3. 心态上的转变

- **以前**：“必须可重复、可断言。”
- **现在**：“在给定边界内，允许路径与表述的多样性；同时**明确哪些算失败、失败时怎么处理**，让系统在不确定下仍可运维、可改进。”

## 四、提示词与工具设计如何影响 Agent 行为：可观测、可约束、可纠错

要让“交给模型决策”可控，**提示词**和**工具设计**是两大杠杆；目标可以归纳为：**可观测、可约束、可纠错**。

### 1. 可观测（Observability）

- **含义**：能看清 Agent 在每一轮“想了什么、选了谁、传了什么、得到了什么”，便于排查与优化。
- **做法**：
  - **提示词**：若框架支持，可要求模型在输出中带简短“推理摘要”或“本步意图”，便于日志和 trace 解读。
  - **工具**：工具名称、参数、返回结构清晰；日志中记录每笔 tool_call 与 result，必要时对敏感字段脱敏。
  - **架构**：每轮 messages、tool_calls、tool results 留痕，便于复现与回归。

### 2. 可约束（Constraining）

- **含义**：通过说明与结构，把 Agent 的决策空间收窄到“安全、可用”的范围内。
- **做法**：
  - **提示词**：在 System Prompt中明确角色、目标、禁止行为（如“不得编造数据”“不得调用未列出的工具”）；规定输出格式（如“若无法完成须说明原因”）；可给出“优先使用某类工具”的指引。
  - **工具**：只暴露当前场景需要的工具，避免误选；描述写清“适用场景、参数含义、典型用法”；参数用 schema 约束类型与必填，减少乱填。
  - **运行时**：最大步数、超时、禁止重复调用等，防止失控。

### 3. 可纠错（Correctability）

- **含义**：出错或偏离时，能定位原因并有机会修正（通过改提示词、改工具、加规则或人工兜底）。
- **做法**：
  - **提示词**：在 System 中写“若某步失败，应如何反应”（如重试一次、换工具、或向用户说明）；给模型“纠错上下文”（如“上一步调用失败，原因是……”），引导下一步行为。
  - **工具**：工具返回错误时带上**可读原因或错误码**，便于模型或上层逻辑做分支；避免工具“静默失败”导致模型误以为成功。
  - **产品**：关键操作前确认、敏感操作留审计日志、支持人工介入或回滚，形成闭环。

### 4. 小结表

| 目标      | 提示词侧           | 工具侧                         |
| ------- | -------------- | --------------------------- |
| **可观测** | 要求推理/意图摘要（若支持） | 名称与参数清晰、调用与结果留痕             |
| **可约束** | 角色、目标、禁止项、输出格式 | 只暴露必要工具、描述与 schema 清晰、步数/超时 |
| **可纠错** | 失败时的应对说明、纠错上下文 | 错误信息可读、少静默失败；人工兜底与审计        |

## 小结

| 学习点               | 要点                                                              |
| ----------------- | --------------------------------------------------------------- |
| **从线性流程到方法与策略地图** | 以前想的是“一步接一步的流程图”，现在要想“根据目标自主决策的方法与策略”；从关注**流程正确性**到关注**策略最优性**。 |
| **从写死流程到设定目标与边界** | 不再控制每一步，而是定义目标、边界与规则，把“下一步做什么”交给模型在运行中决定；用提示词与工具表达约束。           |
| **从单次调用到多轮循环**    | 设计单位是“多轮推理 → 工具 → 观察”的循环；关注每轮输入结构、终止条件与步数上限，调试看整条轨迹。            |
| **从追求确定到处理不确定性**  | 接受合理范围内的路径与表述差异；明确失败定义与处理策略（重试、降级、报错），用边界与结果验收。                 |
| **可观测、可约束、可纠错**   | 提示词与工具设计要支持：看清每步决策与结果（可观测）、收窄决策空间（可约束）、出错可定位与修正（可纠错）。           |

**一点延伸**：Agent 不只是一个新工具，更是一种**新的架构范式**，它将改变我们设计、构建和评估软件系统的方式。未来，成功的 AI 开发者，往往不再是写出最复杂代码的人，而是能设计出**最精妙、最高效、最能自我优化的智能策略**的人。
