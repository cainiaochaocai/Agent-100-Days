# 46. 记忆如何进入上下文

Day 45 讨论了记忆的更新、遗忘与冲突：覆盖还是追加、时间衰减、冲突策略、以及“忘记”的价值。记忆只有**在合适的时机被检索出来，并以合适的形式放进 Context**，模型才能真正“用上”。本节聚焦**记忆如何进入上下文**：**什么时候触发检索**、**如何按任务/用户/时间做相关性过滤**、**记忆放在 Context 的什么位置、用什么形式**、以及**注入失败的常见原因**。

## 一、记忆检索的触发条件：什么时候“需要去翻记忆”

不是每一轮都要查记忆；要在**需要跨会话/跨轮信息**时再查，避免无谓开销和噪音注入。

### 1. 典型触发时机

- **会话开始或用户身份确定时**：新会话建立、或请求里带上 user_id/session_id 后，可**主动查一次**该用户/会话的长期记忆或用户画像（如偏好、重要事实），在首轮回复前就注入，使“从第一句话起就个性化”。
- **每轮调用前（可选）**：若希望每轮都考虑记忆，可在**每次调用 LLM 前**做一次检索，用当前 query（或 query 的 embedding）做语义检索，取 Top-K 条相关记忆再注入。适合对话主题会跳转、需要“按问题找相关记忆”的场景。
- **任务/会话恢复时**：用户说“继续”“接着上次的”，或检测到同一 task_id/session_id 的延续，触发**任务态势或该会话相关记忆**的检索，把进度、待办、中间结果取回并注入。
- **写入记忆之后（可选）**：刚写入一条新记忆后，若本轮就要用上（例如“用户刚说了偏好，本轮回复就要遵守”），可在同一轮内**把刚写的记忆一并加入 Context**，不必等下一轮再检索。

### 2. 不必触发的场景

- **无用户/会话标识的匿名单次请求**：没有 user_id 时，通常不查用户级记忆（或只查全局/任务级）。
- **明确的无状态单次任务**：例如“翻译这句话”“查一次天气”，若业务上不需要个性化与历史，可跳过记忆检索以降低延迟与成本。
- **本会话历史已足够**：若当前会话很短、且对话历史里已经包含所需信息，可策略性少查或不查长期记忆，避免重复与 token 浪费。

### 3. 小结表

| 触发时机                  | 典型做法                                               |
| ------------------------- | ------------------------------------------------------ |
| 会话开始 / 用户身份确定   | 查该用户/会话的长期记忆、用户画像，首轮前注入          |
| 每轮调用前                | 用当前 query 做语义检索，取 Top-K 相关记忆注入（可选） |
| 任务/会话恢复（“继续”等） | 查任务态势、该会话相关记忆，注入进度与待办             |
| 本轮刚写入记忆            | 可将新记忆直接加入本轮 Context，保证本轮即生效         |
| 匿名/无状态单次请求       | 不查用户记忆，或只查任务/全局记忆                      |

## 二、相关性过滤：按任务 / 用户 / 时间筛选合适记忆

检索时不能“把所有记忆都塞进 Context”，需要**先过滤、再排序**，只取与本轮最相关的子集。

### 1. 按用户 / 会话 / 任务隔离

- **用户维度**：只查与当前 `user_id` 绑定的记忆（用户画像、用户级长期记忆），避免把 A 的偏好注入给 B。
- **会话维度**：短期记忆、任务态势往往与 `session_id` 或 `task_id` 绑定，检索时限定 scope，只取当前会话/任务相关的记忆，避免无关会话的旧状态干扰。
- **多租户/多应用**：若有 `app_id`、`tenant_id`，检索时一并过滤，保证隔离。

这是**硬过滤**：不在当前主体范围内的记忆直接排除，不参与排序。

### 2. 按时间筛选与衰减

- **时间范围**：只查“最近 N 天”或“某会话/任务时间窗内”的记忆，减少过旧信息参与排序与注入。
- **时间衰减**：在排序时对每条记忆按 Day 45 的遗忘曲线降权，越旧权重越低，这样即使被检索到，旧记忆也更容易排在后面或被截断在 Top-K 之外。

### 3. 按语义/任务相关性排序

- **语义相似度**：用当前 query（或当前轮意图）的 embedding 与记忆的 embedding 做相似度计算，取 Top-K。适合“用户问的是 X，就优先看和 X 相关的记忆”。
- **任务/类型标签**：若记忆带 type（如偏好、事实、任务状态）或 topic，可根据当前任务类型优先取某类记忆（例如订票流程中优先取任务态势和偏好，少取无关历史摘要）。
- **综合打分**：相关性分数 = 语义相似度 × 时间衰减 × 置信度（若有），再按分数排序取 Top-K。

### 4. 小结表

| 维度               | 做法                                                                              |
| ------------------ | --------------------------------------------------------------------------------- |
| **用户/会话/任务** | 硬过滤：只查与当前 user_id、session_id、task_id 绑定的记忆                        |
| **时间**           | 时间窗过滤（如最近 N 天）+ 排序时时间衰减，降低过旧记忆权重                       |
| **语义/任务**      | 用 query embedding 做相似度检索；或按 type/topic 优先某类记忆；综合打分后取 Top-K |

## 三、记忆摘要如何进入上下文：放在什么位置、用什么形式

检索到的记忆要**变成 Context 里的一段（或几段）文本**，模型才能看到。**放哪里、写什么样**，会影响模型是否真的“用上”。

### 1. 放在什么位置

- **system prompt 块内或紧接其后**：把“关于当前用户的记忆摘要”放在 system prompt 里（或 system prompt 后的第一段），让模型在生成前就明确“用户是谁、有什么偏好/约束”。适合用户画像、长期偏好。
- **对话历史之前、当前问题之后**：若希望模型在“看到当前问题”之后还能参考记忆，可把记忆放在**当前轮 user 消息之后**、assistant 回复之前，作为“本轮可参考的补充信息”。部分框架用单独 role（如 `context`/`memory`）或在一段说明文字里列出。
- **与 RAG 检索结果一起**：若架构上已有“参考段落”区块（RAG 结果），可把**记忆块与 RAG 块并列**，并加小标题区分，如“用户记忆”“参考文档”，避免模型混淆来源。

常见做法：**用户级/会话级记忆放系统提示紧跟 system prompt**；**本轮按 query 检索到的相关记忆**可放在当前问题附近或统一“参考信息”区块。原则是**位置一致、模型容易形成固定“阅读习惯”**。

### 2. 用什么形式

- **结构化列举**：用简短条目列出，例如“用户偏好：英文回复；不吃辣；喜欢简洁。”便于模型快速扫描，也省 token。
- **自然段摘要**：若记忆条数多，可先合并成一段话，如“根据历史记录，该用户偏好英文、不喜欢长回复，曾在 3 月提到项目 A。”适合需要一点“背景叙述”的场景。
- **带标签/来源**：每条记忆前加类型或来源，如 `[偏好]`、`[事实]`、`[任务]`，帮助模型区分“要遵守的约束”和“可参考的事实”。
- **控制长度**：总 token 要有上限（受 Context 预算约束），优先保留高相关、高置信度的记忆，必要时做截断或再摘要。

### 3. 小结表

| 维度     | 建议                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **位置** | 用户画像/长期偏好 → system prompt 或紧跟 system prompt；本轮检索记忆 → 当前问题附近或统一“参考信息”区块；与 RAG 并列时用标题区分 |
| **形式** | 结构化列举（偏好/事实/任务）；或自然段摘要；可带 [偏好]/[事实] 等标签；总长度受 Context 预算限制                                 |

## 四、记忆注入失败的常见原因：记错 / 塞错位 / 被截断 / 被噪音稀释

即使用了记忆，有时模型行为仍像“没看到”，多半是**注入环节**出了问题。常见四类原因如下。

### 1. 记错（写入阶段就错了）

- **内容错误**：模型抽取或规则解析时把“不要推荐 X”记成“要推荐 X”，或把用户说的 A 项目记成 B 项目。检索到的记忆本身就是错的，注入再准也没用。
- **应对**：提高写入时的校验（用户显式确认优先）、冲突与覆盖策略（Day 45）、以及必要时允许用户查看/更正记忆。

### 2. 塞错位（位置或格式不当）

- **位置不当**：记忆被放在 Context 很靠后、或夹在大量无关内容中间，模型注意力不足，实际未参考。
- **格式混乱**：与对话历史、RAG 混在一起没有分隔或标题，模型不知道哪段是“必须遵守的记忆”、哪段是“参考文档”。
- **应对**：固定记忆块的位置（如 System 后或当前问题前）、用明确标题和格式（如“用户记忆：…”），并控制该块长度，让模型容易定位。

### 3. 被截断（超出 Context 或单块限制）

- **总 Context 超长**：system prompt + 历史 + RAG + 记忆总 token 超过模型窗口，后端或中间件从某处截断，若截断的是“记忆块”或记忆在尾部，就会整块丢失。
- **单块过长**：记忆块本身过长，在“取 Top-K 条”时单条过长导致总 token 超预算，其他重要内容被挤掉。
- **应对**：为记忆单独设 token 预算（如最多 500 token），检索到的记忆做长度控制或再摘要；并保证记忆块在拼接顺序中尽量靠前，减少被从尾部截断的风险。

### 4. 被噪音稀释（记忆被大量无关信息冲淡）

- **记忆条数过多或过杂**：检索到很多条，但大量与当前问题无关，模型被无关记忆分散注意力，真正关键的一两条反而不突出。
- **RAG 与记忆比例失衡**：若 RAG 段落很多、记忆很少，模型可能更依赖 RAG，忽略记忆中的偏好与约束。
- **应对**：提高检索相关性（更严的过滤、更小的 K、更好的排序）；在 prompt 中明确要求“优先遵守用户记忆中的偏好与约束”；或适当提高记忆块在 Context 中的权重（如位置靠前、重复关键约束一句）。

### 5. 小结表

| 失败原因       | 表现                                     | 应对思路                                                                   |
| -------------- | ---------------------------------------- | -------------------------------------------------------------------------- |
| **记错**       | 写入内容就错了，检索到即错               | 写入校验、用户确认优先、冲突与覆盖策略、用户可查看/更正                    |
| **塞错位**     | 位置靠后或格式混乱，模型未参考           | 固定记忆块位置、明确标题与格式、控制块长度                                 |
| **被截断**     | 总 Context 或单块超长，记忆被截掉        | 为记忆设 token 预算、检索结果再摘要/截断、记忆块尽量靠前                   |
| **被噪音稀释** | 记忆条数多/杂或 RAG 过多，关键记忆不突出 | 提高检索相关性、减小 K、在 prompt 中强调遵守记忆、记忆块靠前或重复关键约束 |

## 小结

| 学习点                 | 要点                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **记忆检索的触发条件** | 会话开始/用户确定时查用户记忆；每轮前可按 query 检索（可选）；任务恢复时查任务态势；本轮写入的记忆可本轮即注入。匿名/无状态请求可不查。           |
| **相关性过滤**         | 按 user/session/task 硬过滤；按时间窗 + 时间衰减；按语义相似度或 type/topic 排序，综合打分取 Top-K。                                              |
| **记忆如何进入上下文** | 位置：用户级记忆放 System 或紧跟 System，本轮检索记忆放当前问题附近或统一区块；形式：结构化列举或自然段摘要，可带标签，总长度受预算限制。         |
| **注入失败的常见原因** | 记错（写错）→ 校验与覆盖；塞错位（位置/格式）→ 固定位置与格式；被截断（超长）→ 记忆 token 预算与靠前放置；被噪音稀释 → 提高相关性、强调遵守记忆。 |
