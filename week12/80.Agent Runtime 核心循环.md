# 80. Agent Runtime 核心循环

Day 79 讲了路由策略与决策。本节讲 **Agent Runtime**：**职责**（上下文组装、LLM 调用、工具执行、流式响应、状态持久化）、**与 Week 8-11 的衔接**（在 Runtime 中嵌入反思节点、任务分解、HITL 能力），以及**一次请求在 Runtime 中的完整流程**（接收 → 组装上下文 → 推理 → 工具 → 反思 → 响应）。实现上可参考 OpenClaw 的智能体执行主链：围绕 **run / attempt / subscribe** 形成可复刻的执行链路，并由**状态机**驱动流程。

## 一、Agent Runtime 的职责：上下文组装、LLM 调用、工具执行、流式响应、状态持久化

### 1. 上下文组装

- **含义**：从 Gateway 传入的请求、会话历史、记忆检索结果、工具调用历史等，**组装成 LLM 可用的上下文**（messages 列表：SystemMessage、UserMessage、AssistantMessage、ToolMessage）。
- **策略**：按 Week 6 的上下文工程原则：优先级（System > 用户请求 > 历史 > 工具结果）、时间窗口、摘要与压缩。

### 2. LLM 调用

- **含义**：调用 LLM（通过 ProviderPlugin，Week 13 会讲），传入组装好的上下文，获取模型响应（可能包含 tool_calls）。
- **流式支持**：若 Gateway 要求流式响应，Runtime 应支持流式调用 LLM 并透传给 Gateway。

### 3. 工具执行

- **含义**：若模型返回 tool_calls，Runtime 根据 tool_calls 找到对应工具（通过 ToolPlugin，Week 13 会讲），执行并收集 ToolMessage，再回传给模型继续推理。
- **循环**：模型 → tool_calls → 工具执行 → ToolMessage → 模型，直到模型返回最终回复或无 tool_calls。

### 4. 流式响应

- **含义**：Runtime 应支持**流式返回**：模型生成 token 时立即返回给 Gateway，而不是等全部生成完再返回。
- **实现**：LLM 调用时开启流式模式，Runtime 逐 token 或逐 chunk 返回给 Gateway。

### 5. 状态持久化

- **含义**：将本次请求的**执行过程**（LLM 调用、工具调用、反思结论、HITL 决策）持久化，供后续查询、审计或恢复。
- **作用**：支持断线重连、历史查询、trace 与监控（Week 15 会接入 Langfuse）。

### 6. 小结表

| 职责         | 含义                           | 作用            |
| ---------- | ---------------------------- | ------------- |
| **上下文组装**  | 从请求、历史、记忆等组装 messages        | 为 LLM 提供完整上下文 |
| **LLM 调用** | 调用模型，获取响应（含 tool_calls）      | 核心推理能力        |
| **工具执行**   | 执行 tool_calls，收集 ToolMessage | 扩展 Agent 能力   |
| **流式响应**   | 逐 token 返回模型生成内容             | 提升用户体验        |
| **状态持久化**  | 记录执行过程（调用、工具、反思、HITL）        | 支持查询、审计、恢复    |

## 二、与 Week 8-11 的衔接：在 Runtime 中嵌入反思节点、任务分解、HITL 能力

### 1. 反思节点（Week 9）

- **嵌入位置**：在 Runtime 的**工具执行循环**中，每轮工具执行后判断是否触发反思（失败、超时、每 N 步等）。
- **衔接方式**：Runtime 调用 `reflection.run_reflection(state, history, error)`，根据返回的 `decision`（continue/adjust/stop）做分支：continue 继续、adjust 注入 suggestion、stop 终止或转 HITL。

### 2. 任务分解（Week 10）

- **嵌入位置**：Runtime 接收请求后，若判定为“复杂任务”，先调用**任务分解模块**，将目标拆成子任务，再按序执行每个子任务。
- **衔接方式**：Runtime 调用 `decompose_goal(goal)` 得到子任务列表，然后对每个子任务调用 `run_subtask(subtask, context)`，最后 `summarize(goal, results)`。

### 3. HITL（Week 11）

- **嵌入位置**：在**工具执行前**（审批型）或**执行后**（修正型），或**异常时**（接管型），触发 HITL。
- **衔接方式**：Runtime 调用 `hitl.request_approval(action, params)` 或 `hitl.request_correction(result)`，等待人决策，再根据决策继续/修正/接管。

### 4. 小结

| Week 内容  | 在 Runtime 中的位置 | 衔接方式                 |
| -------- | -------------- | -------------------- |
| **反思**   | 工具执行循环中，每轮后判断  | 调用反思模块，按 decision 分支 |
| **任务分解** | 接收请求后，复杂任务先分解  | 分解 → 执行子任务 → 汇总      |
| **HITL** | 工具执行前/后，或异常时   | 调用 HITL 接口，等待人决策     |

## 三、一次请求在 Runtime 中的完整流程：接收 → 组装上下文 → 推理 → 工具 → 反思 → 响应

### 1. 接收请求

- Gateway 调用 Runtime 的 `run(user_input, context, session_id)`，传入用户输入、上下文摘要、会话 ID。

### 2. 组装上下文

- Runtime 从 MemoryPlugin（Week 13）检索相关记忆，从 SessionManager 获取会话历史，组装成 messages 列表。

### 3. 推理与工具循环

- **第 1 轮**：调用 LLM，若返回 tool_calls，执行工具并追加 ToolMessage。
- **第 2+ 轮**：继续调用 LLM，直到返回最终回复或无 tool_calls。
- **每轮后**：判断是否触发反思；若触发，调用反思模块，按 decision 分支。

### 4. 任务分解（可选）

- 若请求为“复杂任务”，先分解成子任务，再对每个子任务执行“推理与工具循环”。

### 5. HITL（可选）

- 若工具为“需审批”或结果异常，触发 HITL，等待人决策后再继续。

### 6. 响应与持久化

- 将最终回复返回给 Gateway；同时持久化本次执行过程（LLM 调用、工具调用、反思结论、HITL 决策）。

### 7. 流程图示意

```
接收请求 → 组装上下文 → [可选：任务分解] → 
推理 → tool_calls? → 工具执行 → [可选：反思] → [可选：HITL] → 
继续推理 → ... → 最终回复 → 持久化 → 返回 Gateway
```

## 四、实战经验分享

- **max_steps 设多少**：工具调用循环要有上限（如 10～20），防止模型陷入重复调用或死循环。可根据业务设定：简单问答 5～10 步足够，复杂任务可 15～20；超限后返回「已达最大步数」并打日志，便于发现异常对话。
- **tool_calls 与 ToolMessage 的顺序**：不少 LLM API 要求「带 tool_calls 的 Assistant 消息必须紧接对应的 ToolMessage，中间不能插入其他 role」（Week 9 Day 62 已强调）。若在中间插入反思建议等 HumanMessage，必须先追加完本轮所有 ToolMessage，再追加反思内容，否则会报 400。
- **流式与超时**：流式响应体验好，但 Gateway 和通道侧都要支持「边收边转发」；若先做 MVP，可只做非流式，超时用请求级总超时（如 60s）即可；后续再加流式时，注意长生成下的超时与中断（用户取消）要能正确传递。
- **状态机 vs 裸 while 循环**：用状态机（如「等待 LLM / 等待工具 / 等待 HITL」）能更清晰处理多种分支和异常；若当前只有「LLM → 工具 → LLM」一条线，用简单循环即可，等接入反思、HITL、任务分解后再考虑显式状态机，避免过度设计。
- **Runtime 失败如何反馈给 Gateway**：Runtime 内异常（如 LLM 超时、工具连续失败）建议返回结构化结果（如 `{ "ok": false, "error": "...", "partial": "..." }`），由 Gateway 统一转成用户可见提示和日志，便于排查与降级。

## 五、代码示例：Runtime 核心循环

以下来自 **`week12/83_code/gateway_runtime_demo.py`**，展示「组装上下文 → LLM → tool_calls → 执行工具 → 再 LLM」的完整循环；注意 **ToolMessage 必须紧接 AIMessage**，中间不插入其他 role。

```python
def run_runtime(user_input: str, context: list[dict], session_id: str, session_manager, max_steps: int = 10) -> str:
    messages = build_context(user_input, context, session_id)  # System + 历史 + 当前 UserMessage

    for step in range(max_steps):
        llm_with_tools = llm.bind_tools(TOOLS)
        response = llm_with_tools.invoke(messages)
        messages.append(response)

        if not getattr(response, "tool_calls", None):
            reply = (response.content or "").strip() or "（无回复）"
            session_manager.append_history(session_id, "user", user_input)
            session_manager.append_history(session_id, "assistant", reply)
            return reply

        # 执行工具并追加 ToolMessage（必须紧接 AIMessage）
        for call in response.tool_calls:
            name = call.get("name", "")
            args = call.get("args") or {}
            tid = call.get("id", "")
            content = execute_tool(name, args)
            messages.append(ToolMessage(content=content, tool_call_id=tid))

    return "达到最大步数，未得到最终回复。"
```

工具执行封装（统一错误格式，便于模型纠错）：

```python
def execute_tool(name: str, args: dict) -> str:
    tool_fn = TOOL_MAP.get(name)
    if not tool_fn:
        return f"错误：未知工具 {name}"
    try:
        result = tool_fn.invoke(args or {})
        return str(result) if result is not None else ""
    except Exception as e:
        return f"执行失败: {e}"
```
