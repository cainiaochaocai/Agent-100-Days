# 79. 路由策略与决策

Day 78 讲了 Gateway 的架构与职责。本节具体讲**路由策略**（规则路由、Embedding 相似度路由、LLM 决策路由、混合路由）、**Router 的职责边界**（只负责“去哪”，不做业务细节），以及**误路由检测与降级**（重路由、回退到通用 Agent、转人工）。

## 一、路由策略：规则路由、Embedding 相似度路由、LLM 决策路由、混合路由

### 1. 规则路由

- **含义**：基于**关键词、正则表达式或业务规则**做路由决策。例如：包含“研究”“分析” → DeepResearch Agent；包含“查询”“数据”“报表” → ChatBI Agent。
- **优点**：规则清晰、可预测、性能高（无需调用 LLM 或向量检索）。
- **缺点**：规则难以覆盖所有 case，边界情况容易误路由；规则维护成本高。

### 2. Embedding 相似度路由

- **含义**：将用户请求**向量化**，与各 Agent 的“能力描述向量”做**相似度计算**，选相似度最高的 Agent。例如：各 Agent 有“能力描述”（如“擅长深度研究、多来源验证”），用户请求向量与这些描述向量比较。
- **优点**：能处理语义相似但关键词不同的请求（如“帮我了解一下 AI 的最新发展”与“研究 AI 进展”语义相近）。
- **缺点**：需要维护各 Agent 的能力描述向量；相似度阈值需要调优；可能受向量模型偏差影响。

### 3. LLM 决策路由

- **含义**：将用户请求与**可用 Agent 列表**交给 LLM，让模型决定“应该路由到哪个 Agent”，并可选输出理由。
- **优点**：模型能理解复杂意图、考虑上下文与历史，路由准确率通常更高。
- **缺点**：每次路由都需要调用 LLM，延迟与成本较高；模型决策不可控，可能路由错误。

### 4. 混合路由

- **含义**：**先规则**（快速路径）→ 若规则不匹配，再 Embedding 或 LLM（慢路径）。或**多策略投票**：规则、Embedding、LLM 各给一个结果，按优先级或多数表决决定。
- **优点**：兼顾性能与准确率；规则覆盖常见 case，LLM 处理复杂 case。
- **缺点**：实现复杂度较高，需要处理策略间的冲突与优先级。

### 5. 小结表

| 策略               | 优点          | 缺点                 |
| ---------------- | ----------- | ------------------ |
| **规则路由**         | 清晰、可预测、性能高  | 规则维护成本高、边界 case 易错 |
| **Embedding 路由** | 语义理解、灵活     | 需要维护能力描述向量、阈值调优    |
| **LLM 决策**       | 准确率高、理解复杂意图 | 延迟与成本高、不可控         |
| **混合路由**         | 兼顾性能与准确率    | 实现复杂度高             |

## 二、Router 的职责边界：只负责“去哪”，不做业务细节

### 1. Router 只做路由决策

- **输入**：用户请求（文本、可选上下文、会话历史）、可用 Agent 列表、路由策略配置。
- **输出**：目标 Agent 标识（如 `"deep_research_agent"` 或 `"chatbi_agent"`），可选置信度或理由。
- **不做**：不执行 Agent 逻辑、不调用工具、不生成回复；只决定“去哪”，不决定“做什么、怎么做”。

### 2. 职责边界的好处

- **解耦**：Router 与 Agent Runtime 解耦，Router 只需知道“有哪些 Agent、它们的能力是什么”，不需要知道 Agent 内部实现。
- **可替换**：可以替换路由策略（从规则改为 LLM）而不影响 Agent Runtime；可以新增 Agent 而不需要改 Router 核心逻辑（只需更新 Agent 列表与能力描述）。

### 3. 与 Agent Runtime 的接口

- Router 输出 `agent_id`，Gateway 根据 `agent_id` 调用对应 Runtime；Runtime 接收请求后自己处理上下文、工具调用、反思等，不依赖 Router。

## 三、误路由检测与降级：重路由、回退到通用 Agent、转人工

### 1. 误路由检测

- **检测方式**：
  - **Agent 反馈**：Runtime 执行后发现“不适合我”，返回 `wrong_route` 信号，Gateway 触发重路由。
  - **置信度阈值**：路由决策的置信度低于阈值（如 Embedding 相似度 < 0.7），视为不确定，走降级策略。
  - **用户反馈**：用户明确说“不对”“换一个”，触发重路由。

### 2. 降级策略

- **重路由**：用不同策略或更宽泛的规则重新路由（如第一次用 LLM 路由失败，第二次用规则路由到“通用 Agent”）。
- **回退到通用 Agent**：若所有专用 Agent 都不匹配或失败，路由到“通用 Agent”（能处理各类请求，但可能不如专用 Agent 精准）。
- **转人工**：连续误路由或用户明确要求时，触发 HITL（Week 11），由人决定路由或直接接管。

### 3. 代码示例：规则路由实现

以下来自 **`week12/83_code/gateway_runtime_demo.py`**，演示规则路由 + 回退到通用 Agent。

```python
ROUTE_RULES = [
    (["研究", "分析", "调查", "深度"], "research_agent"),
    (["查询", "数据", "报表", "销售额", "订单"], "general_agent"),
]

def route(message: str, session: dict) -> str:
    """根据用户消息和会话做路由决策。返回 agent_id。"""
    msg_lower = (message or "").strip().lower()
    for keywords, agent_id in ROUTE_RULES:
        if any(kw in msg_lower for kw in keywords):
            return agent_id
    return "general_agent"  # 默认回退
```

若要用 LLM 兜底，可在规则未命中时调用模型（并加缓存）：

```python
def route_with_llm(message: str, session: dict, llm_route_fn: callable = None) -> str:
    msg_lower = (message or "").strip().lower()
    for keywords, agent_id in ROUTE_RULES:
        if any(kw in msg_lower for kw in keywords):
            return agent_id
    if llm_route_fn:
        return llm_route_fn(message, session)  # 例如返回 "general_agent" 或 "research_agent"
    return "general_agent"
```

### 4. 实战中的实现

在 **`week12/83_code/gateway_runtime_demo.py`** 中，Router 会：

- 实现一个简单的**规则 + LLM 混合路由**：先规则匹配，不匹配则调用 LLM 决策。
- 支持**误路由检测**：Runtime 返回 `{"status": "wrong_route", "reason": "..."}` 时，Gateway 触发重路由或降级。
- **降级逻辑**：重路由失败或置信度低时，路由到“通用 Agent”（一个能处理各类请求的基础 Agent）。

## 四、实战经验分享

- **规则优先还是 LLM 优先**：线上若对延迟敏感，建议「规则优先、LLM 兜底」：规则能命中的直接走规则，命中不了的再调 LLM 路由，并给 LLM 路由加缓存（相同/相似问题短时间复用路由结果），避免每次请求都调一次模型。
- **路由日志一定要打**：每条请求建议记录：原始消息、路由结果（agent_id）、置信度或规则命中键、耗时。便于后续看误路由 case、调规则或调阈值，也便于做路由准确率统计。
- **置信度阈值怎么定**：Embedding 或 LLM 路由的置信度阈值（如 0.7）不要拍脑袋，用一批标注好的「用户消息 → 期望 Agent」样本，看不同阈值下的准确率与召回，再定；同时保留「低置信度走通用 Agent」的降级，避免硬选错。
- **误路由的监控与复盘**：对 Runtime 返回的 `wrong_route`、用户重复追问或换说法再问，可视为潜在误路由信号；定期抽样复盘，把典型 case 加入规则或加入路由评测集，迭代路由策略。
- **规则的可维护性**：规则尽量用配置（如 YAML/JSON）表达「关键词/正则 → agent_id」，避免写死在代码里；这样产品或运营可以一起维护规则，无需发版。
