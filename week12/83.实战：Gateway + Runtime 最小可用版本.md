# 83. 实战：Gateway + Runtime 最小可用版本

Day 82 讲了工具系统与执行引擎。本节动手**实现 Gateway + Runtime 的最小可用版本**：实现 Gateway 核心接口（接收请求、路由决策、会话管理）、实现 Agent Runtime（上下文组装、工具调用循环、流式响应），以及**端到端跑通**（用户请求 → Gateway → Runtime → 工具执行 → 返回结果）。完整可运行代码见 **`week12/83_code/gateway_runtime_demo.py`**。

## 一、实现 Gateway 核心接口：接收请求、路由决策、会话管理

### 1. Gateway 类设计

- **核心方法**：`handle_request(user_id, channel, message, session_id=None)` → 路由决策 → 调用 Runtime → 更新会话 → 返回响应
- **依赖模块**：Router（路由决策）、SessionManager（会话管理）、RuntimeClient（调用 Runtime 的客户端）

### 2. Router 实现（简化版）

- **策略**：先用**规则路由**（关键词匹配），不匹配则用**LLM 决策路由**（调用 LLM 决定路由到哪个 Agent）。
- **输出**：返回目标 Agent 标识（如 `"general_agent"` 或 `"deep_research_agent"`），可选置信度。

### 3. SessionManager 实现

- **存储**：先用**内存字典**（简化版），后续 Week 13 可扩展为数据库。
- **操作**：`create_session(user_id, channel)` → 生成会话 ID、初始化状态；`get_session(session_id)` → 查询会话；`update_session(session_id, updates)` → 更新状态（如当前 Agent、工具调用次数）。

### 4. RuntimeClient 实现

- **接口**：`run(user_input, context, session_id)` → 调用 Runtime 的 `run` 方法，传入用户输入、上下文摘要、会话 ID，返回响应。

## 二、实现 Agent Runtime：上下文组装、工具调用循环、流式响应

### 1. Runtime 类设计

- **核心方法**：`run(user_input, context, session_id)` → 组装上下文 → LLM 调用 → 工具执行循环 → 返回响应
- **依赖模块**：ContextBuilder（上下文组装）、ToolRegistry（工具池）、ToolExecutor（工具执行引擎）

### 2. ContextBuilder 实现

- **输入**：用户输入、会话 ID（用于加载历史）、可选记忆检索结果。
- **输出**：messages 列表（System、历史对话、当前 UserMessage）。
- **简化**：Day 83 先实现基础版本（System + 历史对话 + 当前请求），Week 13 再接入 MemoryPlugin。

### 3. 工具调用循环

- **流程**：调用 LLM → 若有 tool_calls，执行工具并追加 ToolMessage → 再调用 LLM，直到返回最终回复或无 tool_calls。
- **工具执行**：用 ToolExecutor 执行 tool_calls，参数校验 → 执行 → 错误处理 → 结果格式化。

### 4. 流式响应（可选）

- **简化**：Day 83 先实现**非流式**（一次性返回），Week 13 再扩展流式支持（逐 token 返回）。

## 三、端到端跑通：用户请求 → Gateway → Runtime → 工具执行 → 返回结果

### 1. 完整流程

1. **用户请求**：用户通过 CLI 或 Web 发送请求（如“查一下北京天气”）。
2. **Gateway 接收**：Gateway 的 `handle_request` 接收请求，生成或获取会话 ID。
3. **路由决策**：Router 决定路由到哪个 Agent（如 `"general_agent"`）。
4. **调用 Runtime**：Gateway 调用 Runtime 的 `run(user_input, context, session_id)`。
5. **Runtime 执行**：Runtime 组装上下文 → LLM 调用 → 工具执行（如调用 `get_weather("北京")`）→ 返回结果。
6. **Gateway 返回**：Gateway 更新会话状态，返回响应给用户。

### 2. 完整代码结构（week12/83_code/gateway_runtime_demo.py）

脚本包含以下模块，与 Day 78～82 一一对应：

| 模块 | 职责 | 对应章节 |
|------|------|----------|
| **Gateway** | `handle_request(user_id, channel, message, session_id)`：会话获取/创建 → 路由 → 调 Runtime → 更新会话 → 返回 | Day 78 |
| **route()** | 规则路由：关键词 → agent_id，未命中回退 `general_agent` | Day 79 |
| **SessionManager** | `create_session` / `get_session` / `update_session` / `get_history` / `append_history`，内存存储 | Day 78, 81 |
| **build_context()** | System + 历史（user/assistant）+ 当前 UserMessage → messages | Day 81 |
| **run_runtime()** | 组装上下文 → LLM 绑定工具 → 循环（LLM → tool_calls → execute_tool → ToolMessage）→ 返回最终回复 | Day 80 |
| **TOOLS / TOOL_MAP** | 工具定义与按名查找；**execute_tool()** 统一执行并返回可读错误 | Day 82 |
| **main()** | CLI 循环：输入 → `gateway.handle_request()` → 打印 response 与 agent_id | Day 83 |

工具与 Week 8/9 一致：`get_weather`、`get_current_time`、`search_order`（仅 ORD001 成功）。

## 四、实战经验分享

- **MVP 优先做对再做完**：第一版用内存存会话、非流式返回、单 Agent 即可；确认「请求 → 路由 → 调用工具 → 回显」全链路无误后，再加持久化、流式、多 Agent。避免一上来就做全，导致 bug 不知道出在 Gateway、路由还是 Runtime。
- **关键节点打日志**：建议在以下位置打日志（含 request_id 或 session_id）：Gateway 收请求、路由结果、调用 Runtime 入参、Runtime 每轮 LLM/工具调用、返回前。出问题时用 request_id 串起一整条链路，比盲目加 print 高效得多。
- **常见报错与排查**：
  - **400 / tool_calls 相关**：多半是消息顺序问题——带 tool_calls 的 AIMessage 后必须紧跟对应 ToolMessage，检查是否在中间插了 HumanMessage 或 SystemMessage（如反思建议）。
  - **路由到错误 Agent**：看路由日志里规则命中了哪条、或 LLM 返回的 agent_id；用典型误路由 case 补规则或调 prompt。
  - **工具不执行或参数错**：看模型给的 tool_calls 的 name/args 是否和 schema 一致；工具描述不清时模型容易传错类型（如传数字而非字符串）。
- **本地跑通的最小环境**：准备好 API Key（如 OpenAI 或 DashScope），在 `gateway_runtime_demo.py` 里写死一个 test 用户与一条「查天气」类请求，从 Gateway 入口单步或断点跟到 Runtime 返回，确认每一步数据结构符合预期，再接真实前端或 CLI。
