# 60. 反思的输入与输出设计

Day 59 讲了何时触发反思。本节讨论**反思输入**应包含什么（当前状态、执行历史、错误信息、上下文片段）、**反思输出**如何设计（结论类型与结构化格式），以及**输出如何反馈到主循环**（改计划、换工具、重试或交给人）。

## 一、反思输入：当前状态、执行历史、错误信息、上下文片段

### 1. 当前状态

- **含义**：反思被触发时 Agent 的“快照”：当前目标或子目标、已完成与未完成的部分、可用工具列表、当前轮次或步数等。
- **用途**：让反思模块知道“我们正在做什么、做到哪了”，才能判断“是否该继续、调整还是停止”。
- **形式**：结构化字段（如 `goal`、`current_step`、`max_steps`）或一段简短摘要，避免把整段对话全塞进去。

### 2. 执行历史

- **含义**：近期（或相关）的步骤序列：每步的意图、调用的工具与参数、工具返回结果（或摘要）。
- **用途**：反思需要“刚才发生了什么”才能判断“哪里出了问题、是否重复、是否该换策略”。
- **建议**：只保留**最近 N 步**或**自上次反思以来的步骤**，必要时对更早的历史做摘要，控制 token 与噪音。

### 3. 错误信息

- **含义**：当因失败或异常触发时，**明确的错误内容**：工具返回的 error message、业务校验失败原因、超时说明等。
- **用途**：反思模块据此判断“是重试、换参数、换工具还是停止”，而不是猜。
- **形式**：原始错误文本 + 可选的结构化码（如 `tool_error`、`timeout`、`validation_failed`）。

### 4. 上下文片段

- **含义**：与当前决策强相关的上下文摘要：用户原始请求、关键 RAG 结果、或记忆检索到的相关条目（若与 Week 7 结合）。
- **用途**：在“是否调整策略”时，可能需要回顾任务初衷或关键约束，避免反思脱离任务上下文。
- **建议**：只取必要片段并控制长度，反思 prompt 不宜过长。

### 5. 小结表

| 输入项       | 内容概要            | 主要用途             |
| --------- | --------------- | ---------------- |
| **当前状态**  | 目标、进度、步数、可用工具等  | 判断“做到哪了、该不该继续”   |
| **执行历史**  | 近期步骤：意图、工具、结果摘要 | 分析“刚才发生了什么、为何失败” |
| **错误信息**  | 工具/业务错误、超时等     | 决定重试/换策略/停止      |
| **上下文片段** | 用户请求、关键 RAG/记忆  | 在调整策略时保持任务约束     |

## 二、反思输出：结论类型（继续 / 调整 / 停止）与结构化格式

### 1. 结论类型

- **继续（continue）**：当前无问题或问题可接受，主循环按原样继续执行（下一轮正常推理）。
- **调整（adjust）**：当前路径有问题，需要改变策略；输出中应包含**调整建议**（如换工具、改参数、换分解方式），主循环据此更新计划或上下文后再执行。
- **停止（stop）**：不应继续自主执行；可细分为“正常结束”（任务已完成或无法完成）或“需人工介入”（交给人）。主循环终止并返回当前结果或转 HITL。

### 2. 结构化格式

- **最低要求**：结论枚举（`continue` / `adjust` / `stop`） + 可选的理由（reason）或建议（suggestion）。便于代码分支，而不是解析长段自然语言。
- **推荐**：用固定 schema（如 JSON）约束输出，例如：
  - `decision`: `"continue"` | `"adjust"` | `"stop"`
  - `reason`: 简短原因（便于日志与调试）
  - `suggestion`: 当 `decision === "adjust"` 时的具体建议（如“改用工具 B”“先查 X 再执行 Y”）
  - `stop_type`: 当 `decision === "stop"` 时可选 `"done"` | `"failed"` | `"human_required"`
- **实现**：可通过 prompt 要求模型按 schema 输出，或用结构化输出（如 JSON mode、function calling）直接解析。

### 3. 小结表

| 结论     | 含义     | 主循环行为                     |
| ------ | ------ | ------------------------- |
| **继续** | 无需改变   | 正常进入下一轮推理与执行              |
| **调整** | 需改变策略  | 根据 suggestion 更新计划/上下文再执行 |
| **停止** | 不再自主执行 | 结束并返回结果或转人工               |

## 三、输出如何反馈到主循环：改计划、换工具、重试或交给人

### 1. 继续（continue）

- **反馈**：主循环不做额外动作，把反思结论可选用一句话注入下一轮上下文（如“经反思，上一步结果可信，继续执行”），然后按原流程继续推理与工具调用。

### 2. 调整（adjust）

- **反馈**：主循环根据 `suggestion` 做**计划或上下文的更新**，例如：
  - **改计划**：若使用显式计划（Plan-and-Execute），用建议替换或插入后续步骤。
  - **换工具/参数**：在下一轮推理前，通过 System 或额外 message 注入“建议使用工具 B 而非 A”“建议先查 X”；或临时禁用某工具、强调某工具。
  - **重试**：若建议是“同一操作可再试一次”（如网络临时失败），可带“重试一次”的标记再执行上一步，并设重试上限。
- **重要**：调整后的行为仍由**主推理**生成（模型根据更新后的上下文决定下一步），反思只提供“建议”，不直接替代主推理。

### 3. 停止（stop）

- **反馈**：主循环**不再继续**多轮推理与工具调用，而是：
  - **正常结束**：返回当前已得到的结果或“任务无法在当前条件下完成”的说明。
  - **交给人（HITL）**：若 `stop_type === "human_required"`，将当前状态、历史与反思原因呈现给人，由人决定下一步（见 Week 11）。
- **日志**：记录反思的 decision、reason 与 stop_type，便于观测与后续分析。

### 4. 小结

| 反思输出         | 主循环动作                          |
| ------------ | ------------------------------ |
| **continue** | 正常继续；可选注入一句“经反思继续”到上下文         |
| **adjust**   | 按 suggestion 改计划/换工具/重试，再继续主推理 |
| **stop**     | 终止执行；返回结果或转人工，并记录原因            |
